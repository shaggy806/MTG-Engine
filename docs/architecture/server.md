# Server architecture reference (`server/src/`)

Reference detail, **not loaded automatically**: read the entry for a file before changing it. The short, always-relevant version is `server/CLAUDE.md`; this is the per-file detail it points into. Keep it current when a file's shape changes, but it is a map of the code as it is, not a changelog.

## The workspace

- `server/` — a Node + `ws` package: the authoritative multiplayer room host. Owns the one real `Game` instance per room, keyed by a room code; every connected device gets its own redacted `viewFor(seat)` pushed after each dispatch. Imports `engine` the same way `client` does.
- `protocol/` — a types-only package: the wire contract between `server` and `client`, imported by both rather than restated on each. Emits no runtime code (`export {}` and comments), which is why it can sit between a Node process and a browser bundle for free. Depends on `engine` for the types that cross the wire (`Action`, `LegalAction`, `PlayerView`).

## Architecture

The authoritative multiplayer host. One process can run many rooms; each room owns exactly one
real `Game` and pushes every connected seat its own `viewFor` after each settle. Transport-agnostic
at the `Room` level (a `Connection` is just "something we can push a `ServerMessage` to"), so it's
unit-testable without a real WebSocket — `ws-server.ts` is the only place that touches `ws` itself.

**Rooms have a host** (`host.ts`'s `HostRole`, shared by both stages and carried across promotion): whoever created the room. `create-room` carries a `hostToken` the creating tab keeps in `sessionStorage`, and a `join-room` presenting it binds that connection as host, seated or not. Only the host may `add-seat`/`remove-seat`/`add-bot`/`set-bot-deck`/`start-game`/`set-bot-speed`/`set-room-settings`/`rematch` (`requireHost` in `ws-server.ts`); your own seat, deck and ready state stay yours. While the host is disconnected the role falls to the first connected human seat, and returns when they reconnect — computed on demand, so there's no hand-off state to go stale. With nobody eligible (no token, nobody seated — scripts and tests) no one is excluded. `room-joined`/`state` carry the recipient's `isHost` and the room's `botSpeed`, and `SeatStatus.isHost` marks the host's seat. **Room settings** (`RoomSettings`: starting life, and who goes first — `"random"`, the highroll, or a seat) are the host's before the game starts: `PendingRoom.setSettings` checks each change (a whole life of 1–999, a first player who is a seat here) and refuses the lot if any is wrong, `removeSeat` puts a removed first player back to `"random"`, every `room-joined` of a waiting room carries them, and `toGameConfig` builds the game from them (the life into the rules, the first player, or one drawn at random). A promoted `Room` keeps only `firstPlayerChosen`, which every `state` push carries so the client doesn't announce a highroll nobody won. **An engine throw stops one room, not the server**: `Room.settle` — every path that advances the game, a bot's timer-driven move included — catches it, and `Room.stop` sets `stopped`, clears the gate's timers, refuses further `dispatch`es and publishes once more, so each seat's `state` carries `stopped` (the reason) and the client shows it as a toast that doesn't go away.

A room has **two lifecycle stages**, because a seat's deck isn't known until whoever claims it
connects (the deck builder sends it with `claim-seat`) and `Game.create` shuffles and deals
immediately for every seat: a `PendingRoom` (a code, seat claims, no `Game`) is **promoted** into a
real `Room` the moment every seat is claimed or bot-filled.

- **`room.ts`** — `Room` wraps one `Game` plus a `Seat` per `turnOrder` entry (`clientToken`, `connection`, `autoPassUntil`, `pass` (its `PassSettings`, mana-only skipping among them), `displayName`, `ackedSeq`/`acksFrames`). `claimSeat(player, clientToken, connection, displayName?)` binds a connection to a seat — a token mismatch is rejected even while offline, the same token reclaims it. `addBot(player, deck?, displayName?)` fills an open seat with `RoomOptions.botController` (the name is the one `PendingRoom` gave the bot, carried over at promotion), defaulting to `DEFAULT_BOT` — the v2 searching bot — under `BOT_DECISION_BUDGET_MS` (300ms) per priority window, set a shade under `BOT_MIN_THINK_MS` so the search finishes inside the pause the room is already taking for animations (rejecting a seat already claimed or botted). `botController` exists so the pacing tests can pin v1 and stay about the frame machinery rather than about how well a bot plays; `seatStatuses()` reports `isBot`. `dispatch(connection, action)` forwards to `Game.dispatch` then calls `settle()`, which auto-passes dead priority windows / mana-only windows / whole turns per-seat, one stopping point at a time (built on `isSettled`, deliberately not `autoSettle` — see `auto-settle.ts`). **Bots live in `settle()`**, not in `Game`'s `config.controllers` (`nextBotDecider` is seat-by-seat across `awaiting.hands` for the parallel mulligan, otherwise the single `awaiting.player`), so a mixed bot/human table composes for free. **`concede(connection)`**: the seat's player concedes (`Game.concede`, rule 104.3a) and stays connected to watch; a decision they owe is first answered by a one-off bot (`makeBot`), as they could have answered it themselves before conceding. **Passing preferences** (`setPassSettings`, the seat's `pass`: `PassSettings` from its device): in `autoAdvanceHumanSeat`, *pass to main* passes the seat's own upkeep and draw windows and *pass through combat* every combat-step window, each only with an empty stack (`passesByPreference`); *skip mana stops* (`skipManaOnly` — on unless the device turns it off, off for a seat whose device hasn't sent its settings) passes any window where tapping for mana is all the seat could do, stops included, like one with nothing to do at all; and a **stop** (`holdsForStop`) holds the first window of a flagged step — on the seat's own turns or others', `stops.mine`/`.theirs` — against those, Auto-pass and Pass Turn (and keeps an `attackers` decision Auto-pass would have answered), though not a window with nothing to do in it or a resolve-all; `Seat.stoppedAt` is the step already held, set too when Pass Turn or Auto-pass is armed so a stop on the current step doesn't hold the pass just asked for. **`setBotTakeover(connection, on)`** puts the seat in `bots` (or takes it out) while its token and connection stay, so the player keeps watching, can reconnect (`claimSeat` lets the seat's own token back in), and still counts as a person for the host role (`humanSeats`); `dispatch` refuses their own actions meanwhile. **For the scenario builder** (`builder.ts`): `RoomOptions.frozen` makes `settle()` only publish (no bot moves, no auto-pass), `dispatch` refuse, and `broadcast` send no legal actions; `RoomOptions.startSeq` counts frames on from a replaced room's, since the client drops a frame numbered no higher than the last it saw; `humanClaims()` hands the human seats' claims to a room built to replace this one, and `switchSeat(connection, player)` moves a connection to a seat no one else holds and no bot plays. `room.builder` is the `BuilderInfo` `broadcast` adds to each `state`. **For a rematch** (`RoomManager.rematch`): `RoomOptions.recipe` (a `GameRecipe`: the `GameConfig` the waiting room built, and its `firstPlayer` setting) is what the next game is dealt from — `null` on a builder's or a hand-built room, which can't be rematched — and `RoomOptions.gameNumber` (1, then one more per rematch) travels on every `state` as `game`; `botSeats()` lists the bot-played seats no human holds, with their names, and `reserveSeat(player, clientToken, displayName)` holds a seat for a token with nobody connected.
  **Frames and the animation gate.** Every push is a numbered **frame** (`publish()` bumps `seq` and calls `onUpdate`; the transport fans it out, and `seq` travels on the `state` message). A bot used to take its whole turn inside one `settle()` call, so clients only ever saw the board *after* all of it and played the arrival animations over an outcome already on screen — a land shown flying in was already tapped for the spell after it. Now `settle()` stops at each bot action: it publishes a frame, parks the move behind `holdForClients`, and releases it once every *acking* seat reports finishing that frame (`ack(connection, seq)`) and `BOT_MIN_THINK_MS` (350ms) has passed, with `FRAME_ACK_TIMEOUT_MS` (12s, above the client's 11s cap on one frame) as a backstop for a seat that has gone quiet — then pauses a further `BOT_LINGER_MS[botSpeed]` (the host's setting: fast 0 / normal 700ms / slow 1.6s) before the move, so a string of moves with little to animate still reads one at a time. Once that pause starts the ack timeout is cleared, so a slow client catching up late doesn't cut it short. A seat that has never acked never gates anything, so no client can deadlock a room; a disconnect re-checks the gate. A resolve-all gets the same treatment one object at a time: while a seat's resolve-all is armed, `settle()` publishes and holds as soon as anything has resolved, been countered or fizzled since the last frame (`resolvedUnshown`, counted in those events rather than stack depth, since a resolution that adds a trigger leaves the depth unchanged), and — `showStackArrivals`, on by default — when something has gone on the stack since the last frame (`stackArrivalUnshown`), so a trigger nobody could answer is seen there before it resolves; that frame is held for its animation but not the bot-speed pause (about +2% watching time on seeded precon games), so clients see the stack come down one object per frame instead of vanishing in one. The host can **pause the bots** (`set-bots-paused`, `Room.setBotsPaused`): the gate then stays shut whatever the clients say — the ack timeout, if it fires, only stops it waiting on the quiet seat (`FrameGate.timedOut`) — until resumed; `step-bots` (`Room.stepBots`) opens it for one move, skipping the bot-speed linger. Every `state` carries `botsPaused`. A bot move nobody could watch is dispatched without a frame — a plain `pass-priority`, or any window where `isDeadForMana` says passing and tapping for mana are the only options. That isn't just tidiness: a beat spent on one of those lands *between* a spell being cast and that spell resolving, which is what made a creature seem to arrive long after its own play animation had finished. Whatever the move lets through is paced in the next frame. `RoomOptions.pacing: "immediate"` opts out of all of it (bots run to completion, one push at the end) and is what tests and scripts use; `RoomOptions.timers` swaps in a fake clock. `dispose()` drops a parked move's timers.
- **`pending-room.ts`** — `PendingRoom`: the same seat-claiming bookkeeping as `Room` (claim/reclaim semantics, `addBot`, `connectedSeats`, idle tracking) with no `Game`, no dispatch, no settle. `claimSeat(..., deck?)` stores the seat's deck, falling back to its positional starter deck from `decks.ts` so a bare room-code link still works. `isReady()` = every seat claimed or bot-filled; `toGameConfig()` assembles the `DeckList[]` and rolls the starting player (the "highroll") *at promotion time*, since turn order isn't settled before then. Deliberately a separate class, not a nullable-`game` variant of `Room`. **The table is also sized here, not at creation**: `addSeat()`/`removeSeat(player)` grow and shrink it between 2 and `SEATS.length`, which is what the seat board's add/remove controls drive. `addSeat` takes the first unused `SEATS` entry and re-sorts, so the seat array stays in printed seating order however the table was assembled — turn order comes straight off that array, and must not depend on the order seats were added. `removeSeat` refuses a seat a human has claimed (leaving is that player's own call) but lets the host remove an open or bot-filled one. **`takeSeat(clientToken, connection, displayName?, deck?)`** is what joining does: the token's own seat if it holds one, else the first seat nobody holds, else (every seat taken, fewer than four) a seat added for it — un-readied, named "Player N" when no name is given; a full four-seat table refuses. `disconnect` frees an un-readied seat (a tab opened and closed would otherwise hold a chair the host can't remove) and only unbinds a readied one. **A bot seat is named** by `addBot` (and renamed by `setBotDeck` only when the new deck's colours no longer suit the old name) after a character of its deck's colours — `bot-names.ts`, read off the commanders' colour identity, or every card's without one; `botSeats()` hands the names to `RoomManager.promote`. **`RoomSettings.commanderLegalOnly`** (the seat board's "Decks", off by default) admits only decks `validateCommanderDeck` passes: `setReady(true)`, a readied `claimSeat`, `addBot` and `setBotDeck` refuse any other (`assertDeckAllowed`, saying why), turning it on un-readies a human seat holding one, and `allReady` needs every deck legal; each `SeatStatus.deckProblem` carries the first reason (`null` in a promoted `Room`).
- **`bot-names.ts`** — `botNameFor(identity, taken)`: a random one of the well-known characters (Jace, Vraska, Nicol Bolas, …) whose colours are most alike `identity` (shared over all colours between them), skipping names other seats already use. `botNameFits` says whether a name is still a best match.
- **`room-manager.ts`** — `RoomManager.createPending(players, config)` mints a room code and a `PendingRoom`; `promote(id)` builds the real `Game`/`Room` for a ready one (wiring its `onUpdate` to the manager's own `onRoomUpdate`), replays its connected claims and bot fills onto it, then `room.start()` settles it to the first real decision and publishes the opening frame. `get(id)` returns a `Room | PendingRoom`. **`rematch(id, {restart?})`** deals a new game into a promoted room whose game is over (or, with `restart`, the host's mid-game "Restart game", one still going), under the same code: `Game.create` from the room's `recipe` with a fresh seed and, if the first player was `"random"`, a fresh highroll; a new `Room` (same host, bot speed and `firstPlayerChosen`, `gameNumber` + 1, frames counted on from the old room's `frameSeq`) replaces the old one, which is disposed — a new `Room` rather than swapping the `Game` inside the old one, because everything a `Room` keeps (seats' auto-pass, acks, the frame gate, the bots' memory, the capture log) belongs to one game, and the constructor clears it all at once, as a scenario builder's rebuild relies on too. Every human claim comes across (`humanClaims`): a connected one bound to the same seat, so they're in the new game with no seat board between; a dropped one held for its token (`reserveSeat`) to reclaim on reconnect, the game waiting on their opening hand as it would after any disconnect; a player who had handed their seat to a bot plays it again. Bots (`botSeats`) keep their seats and names, added last as in `promote`. Refused for a pending room, a room with no recipe, or a game not over. The constructor's `pacing` option is handed to every room it builds (the rematch tests run whole games on `"immediate"`). `reapIdle(maxIdleMs)` disposes and drops abandoned rooms. No player-count assumption. `createBuilder(hostToken)` opens a scenario builder (`builder.ts`) under a fresh code — its session installs each rebuilt `Room` in the map under that code — and `builder(id)` finds it; `reapIdle` drops a builder with its room.
- **`ws-server.ts`** — `attachRoomServer(wss, manager)` wires a `WebSocketServer` to a `RoomManager`: parses messages as `ClientMessage`s, dispatches to the matching `Room`/`PendingRoom`/`RoomManager` call, pushes `ServerMessage`s back. **`broadcast` is never called from a message handler** — a room publishes its own frames on its own clock now (one per bot action), so it's wired up as `manager.onRoomUpdate` and as `room.onUpdate` on any room `requireRoom` is handed, and anything wanting a push calls `room.publish()`. That second binding is what keeps the hand-built-`Room` `scratch.mjs` pattern working without a real `RoomManager`. `create-room` clamps `players` (2-4, default 2) — the client always takes the default now and sizes the table from the seat board instead, so that parameter is for scripts and tests. `add-bot` mirrors `claim-seat`'s error shape and also sends a direct `room-joined` refresh, since the caller may not hold a seat yet and so isn't in `connectedSeats()`; `add-seat`/`remove-seat` need the same follow-up for the same reason, and are pending-room-only (`requirePendingRoom`) because a promoted room's turn order is already dealt. `ack` is exempt from the per-IP rate limit (it's automatic traffic, one per frame shown, with no effect beyond releasing a bot). A connection's first `state` frame of a game also carries `artManifest` (every card in every deck, `Game.artManifest`, worked out once per room) for the client to load the art of ahead of time — naming every deck's cards, accepted for games among friends (not again after a rematch, which deals the same decks). `rematch` is host only (`requireHost`), its `restart: true` the mid-game restart (refused without it while the game is on), and calls `manager.rematch`, which publishes the new game's opening frame to every seat. A connection closing on a finished game publishes one more frame, since the room has none of its own left to send: whoever the host role fell to is told, and offered the rematch. `attachRoomServer`'s third argument, `{ builder: true }`, turns on the scenario builder's messages (`builder-create`, answered with `room-created`; `builder-update`/`builder-start`/`builder-stop`/`builder-snapshot`, host only; `builder-seat`) — `index.ts` passes it only for `--builder`, dev-rooms always. A connection closing disconnects from whichever room is under its code now, since a builder replaces its room with each rebuild. **`spectate-room`** watches a room without a seat (refused to a connection seated in it): the connection joins `spectators`, keyed by room code so it carries across promotion and rematch, and gets the waiting room's `room-joined` refreshes and then every frame of the game (`spectatorFrame`: `viewFor(SPECTATOR)`, every hand hidden, no actions, `seat` the first in turn order, `spectating: true`). A spectator never acks, so it never holds up a bot; `leave-room` or the connection closing ends it.
- **the wire protocol** lives in the `protocol/` workspace, not here — `server` and `client` both `import type { … } from "protocol"`. It was two hand-synced copies (`server/src/protocol.ts` and `client/src/net/protocol.ts`) until it became clear the reason given for that — Node package vs browser bundle — never applied to a file that compiles to nothing. `protocol/src/room.ts` holds the room protocol; `protocol/src/import-deck.ts` holds the `POST /import-deck` shapes, a separate surface (stateless, no room) that was mirrored just as silently. `ClientMessage`: `create-room {seed?, players?, hostToken?}`, `join-room {roomId, hostToken?}`, `claim-seat {seat, clientToken, displayName?, deck?}`, `add-bot {seat}`, `set-bot-deck {seat, deck}`, `add-seat`, `remove-seat {seat}`, `take-seat {clientToken, displayName?, deck?}` (a waiting room's seat for whoever arrives), `set-ready {ready}`, `start-game`, `rematch` (host only, once the game is over), `concede`, `bot-takeover {on}`, `set-pass-settings {settings}`, `set-bot-speed {speed}`, `dispatch {action}`, `pass-turn`, `auto-pass`, `resolve-all` (a **one-shot**, unlike the two standing modes beside it: pass this seat's priority until the stack drains, stopping the moment anything real happens — a decision for this seat, an opponent casting or activating, or something this seat owns being targeted or leaving the battlefield), `ack {seq}`. `ServerMessage`: `room-created`, `room-joined {seats, isHost, botSpeed, seat, pending}`, `state {seq, game, seat, view, actions, seats, autoPassing, autoPassPaused, isHost, botSpeed, canRematch?}` (`game` is which game of the room the frame is from — `seq` keeps counting across a rematch, so this is how a client knows a new game; `canRematch` marks a room that was started from a waiting room), `error`. A `WireDeck` carries `cards`/`commanders`/`name`/`printings` — one commander or a Partner pair, with the lone `commander` a client from before pairs sends still read (`engine`'s `commandersOf`). `SeatStatus` carries `claimed`/`online`/`displayName`/`isBot`, and its `deck` carries `commanders` as `{name, printing}` — just those cards, since the seat board only draws the commanders (a pair splits the art box in two); the whole map rides with the deck itself. Doesn't cover `/import-deck` (a plain HTTP route, not a WS message).
- **`decks.ts`** — `SEATS: SeatDeck[]`, up to four named seats (`ALICE`/`BOB`/`CAROL`/`DAVE`) in seating order, sliced by `create-room`'s `players` count — a seat's fallback deck when nobody brought their own. The deck contents are the first four of `engine`'s `BENCH_DECKS` (the `bench`-flagged `SAMPLE_DECKS`, since 2026-10-04).
- **`import-deck.ts`** — the decklist-import backend, unrelated to any room: `parseDecklistText(text)` parses a pasted Moxfield-style export (a card listed under its flavor name — "Princess Sarah" — is read as the card it's printed on, `nameForFlavorName`, so every later lookup sees the Oracle name), honouring a `Commander` section header and keeping each line's `(SET) collector-number` suffix as a `printing`; `evaluateDecklist(entries, registry, onProgress?, {commanders, tags, cardData})` cross-references each name against the local `CardRegistry` (implemented cards reported from their `CardDefinition`), reads anything else from the engine's checked-in Oracle snapshot (`cardData`, `card-data.ts`), and falls back to Scryfall only for a name the snapshot lacks — a card printed since it was made, a misspelling, a card that isn't Commander-legal (throttled, 429-aware retry), and gives each unimplemented card `replacements` (up to three, via `engine`'s `assignReplacements`) plus `suggestedReplacement` (the first). Stand-ins are chosen *for this deck*: the commander first (a legendary for a legendary), inside the commander's colour identity — read from Scryfall's `color_identity` when the commander itself is unimplemented — and never a card the list already has or another card's first choice. `lookupPrintingIds` resolves those suffixes to Scryfall card ids (`printingId`) so an imported deck arrives wearing the art it was exported with — batched by `{set, collector_number}` identifiers, which match back exactly, and only for *implemented* cards, since a substituted one is a different card whose art the suffix says nothing about. A returned card whose name doesn't match the line's is discarded: a stale collector number resolves to some other card, and pinning its art here would be worse than no printing at all. `formatCheck(...)` runs `validateCommanderDeck` over the result, reporting the `commanders` it settled on — two when a `Commander` section names two, or when Moxfield's trailing block is a pair the registry can't rule out. Scryfall lookups go through `lookupScryfallMany`, which **batches**: `POST /cards/collection` takes 75 names at a time, so a 100-card list costs two round-trips rather than a hundred throttled ones (~1s instead of ~35s). Responses carry no echo of which identifier produced which card, so they're matched back by name — each returned card is indexed under its own name, its `"Front // Back"` name rewritten in the single-slash form decklists use, and each face name. A name that misses is retried once per alternate spelling (`scryfallNameVariants`), one extra batched round each. Results (misses included) are cached process-wide for the life of the process. Wired up as `POST /import-deck` in `index.ts`, which answers with **newline-delimited JSON, not one object**: `{type:"progress", done, total, name}` lines as `evaluateDecklist`'s `onProgress` fires (implemented cards land at once, then a line per lookup batch), then exactly one terminal `{type:"result", cards, format}` or `{type:"error"}` line. Streamed so the deck builder's import panel can render a progress bar off those lines rather than sit silent. Live-fetching a Moxfield URL server-side was tried and abandoned (403s) — pasted export text only.

- **`card-data.ts`** — `loadCardData()`: every Commander-legal (or banned) card's mana cost, type line, power/toughness, keywords and colour identity, read once (~0.2s, the first time an import needs it) from the engine's Oracle snapshot `engine/data/oracle/cards.jsonl` (`npm run gen:oracle -w engine`, from Scryfall's bulk data; the file card authoring reads) and reduced exactly as `summarize` reduces a Scryfall answer, under the same names a Scryfall answer is matched back by (the card's, its single-slash form, each face's). `lookupScryfallMany` asks it before Scryfall, so an import of cards it has makes no request at all and works with Scryfall down; null if the file is missing, when every unimplemented card goes to Scryfall as before. Regenerating the snapshot keeps it current with new sets.
- **`oracle-tags.ts`** — `loadOracleTagIndex()`: the card replacer's oracle-tag index, read once from `server/data/oracle-tags/index.json` (null if missing — imports then match on type, cost and body alone). That file is **generated** by `npm run gen:oracle-tags -w server` from `server/data/oracle-tags/allowlist.txt`, the curated list of ~260 tags describing what cards *do* (removal, sweeper, edict, tutor, ramp, draw engine, recursion, tokens, anthem, evasion, punisher, …) — trivia tags (card names, cycles, typal, errata) are left out on purpose, since they're rare and would dominate an IDF-weighted score. The generator uses only Scryfall's public API: one paged `oracletag:<slug> legal:commander` search per tag (a parent tag's search includes its children, so listing both broad and specific tags gives graded credit), after checking every slug against scryfall.com/docs/tagger-tags — search answers an unknown tag exactly like an empty one. A card's own tags aren't in Scryfall's API; Tagger's GraphQL has them, but it's undocumented and nothing here uses it. Slow (~2s per page, most of an hour), so it's a checked-in, occasionally-regenerated file.

- **`capture.ts`** — saving a bot's blunder as a training scenario, a developer's tool: a room built with `RoomOptions.capture` (from `RoomManager`'s, set by `index.ts` only when started with **`--capture`** — the local `dev` script passes it, dev-rooms always has it, the production service never does) keeps a `CaptureLog` of the state just before each of its bots' last `CAPTURE_KEEP` (200, or `--capture-keep N` — `CaptureConfig.keep`) real decisions (`Room.botAction`; a dead-for-mana window isn't kept). With each, what the bot's own search said (`CaptureDiagnosis`: the path it took — a search or a named shortcut — whether its clock ran out, and every candidate it scored, best first, scored on arrival so no states are kept), from the trace the room gives its default bots while capturing; a saved capture carries it as `diagnosis`, and `bot:captures` prints it beside v2's answer today. Late in a four-player game that's 5–30 turns back, at ~0.4 MB of memory a state. Its host picks one from the game's **Capture** button (`client/src/ui/CapturePanel.tsx`, shown only when a `state` message carries `capture`; it lists them newest first under a heading per turn, narrowed to one bot or with passes hidden), then the right answer from `captureOptions` or "anything but what it did", and the log writes a `ScenarioCapture` JSON to the git-ignored **`captures/`** at the repo root (a late four-player one is ~0.7 MB) over the `capture-list` / `capture-options` / `capture-save` messages. The panel's other tab files a **bug report** (`CaptureLog.report`, the `capture-report` message, answered with `capture-saved`): the game as it stands, its event log cut to the last `BUG_REPORT_EVENTS` (300), the reporting seat, a title and description, and optionally a photo (a PNG, JPEG, GIF or WebP data URL up to `BUG_REPORT_IMAGE_MAX`, 10 MB, picked or pasted in the panel and written beside the JSON under the same name), as a `BugReport` JSON in `captures/bugs/` — out of the scenario loaders' way, which read only `captures/*.json`; its `state` is a snapshot `bot:replay --from` starts from. Off the public site because a capture is the whole state, every hand and library included.
- **`builder.ts`** — the **scenario builder**, a developer's tool (on only with `--builder`; the client offers it only in a dev build): build a board from scratch, then play it. The board is a `ScenarioSpec` (`protocol/src/scenario.ts`); `validateScenario` checks one from a client, `buildScenario` builds a fresh `Game` from it — turn 1, the active player's, at the chosen step, opening hands of none, cards placed with `debugSpawn` (a commander by `debugMove`, or directly for a zone where moving it would ask rule 903.9's question), pending triggers dropped — and returns which scenario card each object is; `snapshotScenario` turns a game back into a scenario (the stack, control changes, transformed faces and damage are left behind; each library's run of basics at the bottom comes back as its fill). A `BuilderSession` holds the spec and the mode, and rebuilds on every edit into a new `Room` under the same code — frozen while building, with bots in the seats the spec names once playing — carrying the connected humans across (`humanClaims`) and the frame count on (`startSeq`). Why it's shaped this way: `docs/plans/scenario-builder.md`.
- **`status.ts`** — the operator endpoint, for reading over SSH with `curl`: `GET /status` (an aligned text table of rooms, seats, turn, step and idle time), `/status.json`, `/healthz`. It runs as a **second HTTP server bound to 127.0.0.1** (`STATUS_PORT`, default 4010) rather than a route on the game port, and that is load-bearing rather than tidy: a room code is a join credential, port 4000 is published to the internet by the Cloudflare tunnel, and a loopback *check* on 4000 would be worthless anyway because `cloudflared` makes every public request arrive from 127.0.0.1. Don't add it to the tunnel's ingress list.

## Server commands, in full

- `npm run test -w server` / `test:watch` / `build` / `typecheck`
- `npm run start -w server` — runs the built `dist/index.js`: a real room server on `ws://localhost:4000` (or `$PORT`)
- `npm run dev -w server` — `tsc --watch` + `node --watch dist/index.js` together
- `npm run dev-rooms -w server` — a room server (in place of the real one, on port 4000) preloaded with the board states in `server/scripts/dev-scenarios.mjs`. There is one room per entry, joined at `localhost:5173/?room=<CODE>`, with the first player as the human seat and scripted bots that attack, block and cast only as the scenario says, so the decision under test comes up on cue. A loopback-only command port, `127.0.0.1:4099`, takes JSON `list`, `state`, `reset`, `spawn`, `move`, `life`, `objects` (read-only: the objects named in `names` as the engine holds them — `stackCount`, counters — without pushing a frame, for a test polling a board mid-animation) and an `eval` escape hatch (`curl -s localhost:4099 -d '{"op":"state","room":"FOURP"}'`). The same commands reach a room a browser started there (a blitz, a seat board's game, whichever game a rematch has put under its code), all but `reset`, which needs a scenario — how `e2e/rematch.spec.ts` ends a game without playing it out. Every change pushes to the room's browsers at once. `reset` rebuilds a room from its scenario and drops the connections, and each tab reconnects and reclaims its seat by itself. Build `engine` first.
- `npm run gen:oracle-tags -w server` — rebuilds `server/data/oracle-tags/index.json` from `allowlist.txt` via Scryfall's search API (most of an hour; run it in the background and watch its stderr)

**To check a client change against a known board, use `npm run dev-rooms -w server`** (below) rather than playing up to the position. A git-ignored `scratch.mjs` at the repo root is still the scratch pad for one-off exploration (`node scratch.mjs` after building `engine`/`server`): build a `Game` (often spawning objects directly onto the battlefield), wrap it in a `Room`, and serve it over a raw `ws` `WebSocketServer` on port 4000 for a browser (or `claude-in-chrome`) to connect to at the client dev server's URL with `?room=<CODE>`. `dev-rooms` is that pattern made permanent.
