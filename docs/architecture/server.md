# Server architecture reference (`server/src/`)

Reference detail, **not loaded automatically**: read the entry for a file before changing it. The short, always-relevant version is `server/CLAUDE.md`; this is the per-file detail it points into. Keep it current when a file's shape changes, but it is a map of the code as it is, not a changelog.

## The workspace

- `server/` — a Node + `ws` package: the authoritative multiplayer room host. Owns the one real `Game` instance per room, keyed by a room code; every connected device gets its own redacted `viewFor(seat)` pushed after each dispatch. Imports `engine` the same way `client` does.
- `protocol/` — a types-only package: the wire contract between `server` and `client`, imported by both rather than restated on each. Emits no runtime code (`export {}` and comments), which is why it can sit between a Node process and a browser bundle for free. Depends on `engine` for the types that cross the wire (`Action`, `LegalAction`, `PlayerView`).

## Architecture

The authoritative multiplayer host. One process can run many rooms; each room owns exactly one
real `Game` and pushes every connected seat its own `viewFor` after each settle. Transport-agnostic
at the `Room` level (a `Connection` is just "something we can push a `ServerMessage` to"), so it's
unit-testable without a real WebSocket — `ws-server.ts` is the only place that touches `ws` itself.

**Rooms have a host** (`host.ts`'s `HostRole`, shared by both stages and carried across promotion): whoever created the room. `create-room` carries a `hostToken` the creating tab keeps in `sessionStorage`, and a `join-room` presenting it binds that connection as host, seated or not. Only the host may `add-seat`/`remove-seat`/`add-bot`/`set-bot-deck`/`start-game`/`set-bot-speed` (`requireHost` in `ws-server.ts`); your own seat, deck and ready state stay yours. While the host is disconnected the role falls to the first connected human seat, and returns when they reconnect — computed on demand, so there's no hand-off state to go stale. With nobody eligible (no token, nobody seated — scripts and tests) no one is excluded. `room-joined`/`state` carry the recipient's `isHost` and the room's `botSpeed`, and `SeatStatus.isHost` marks the host's seat.

A room has **two lifecycle stages**, because a seat's deck isn't known until whoever claims it
connects (the deck builder sends it with `claim-seat`) and `Game.create` shuffles and deals
immediately for every seat: a `PendingRoom` (a code, seat claims, no `Game`) is **promoted** into a
real `Room` the moment every seat is claimed or bot-filled.

- **`room.ts`** — `Room` wraps one `Game` plus a `Seat` per `turnOrder` entry (`clientToken`, `connection`, `autoPassUntil`, `skipManaOnly`, `displayName`, `ackedSeq`/`acksFrames`). `claimSeat(player, clientToken, connection, displayName?)` binds a connection to a seat — a token mismatch is rejected even while offline, the same token reclaims it. `addBot(player)` fills an open seat with `RoomOptions.botController`, defaulting to `DEFAULT_BOT` — the v2 searching bot — under `BOT_DECISION_BUDGET_MS` (300ms) per priority window, set a shade under `BOT_MIN_THINK_MS` so the search finishes inside the pause the room is already taking for animations (rejecting a seat already claimed or botted). `botController` exists so the pacing tests can pin v1 and stay about the frame machinery rather than about how well a bot plays; `seatStatuses()` reports `isBot`. `dispatch(connection, action)` forwards to `Game.dispatch` then calls `settle()`, which auto-passes dead priority windows / mana-only windows / whole turns per-seat, one stopping point at a time (built on `isSettled`, deliberately not `autoSettle` — see `auto-settle.ts`). **Bots live in `settle()`**, not in `Game`'s `config.controllers` (`nextBotDecider` is seat-by-seat across `awaiting.hands` for the parallel mulligan, otherwise the single `awaiting.player`), so a mixed bot/human table composes for free.
  **Frames and the animation gate.** Every push is a numbered **frame** (`publish()` bumps `seq` and calls `onUpdate`; the transport fans it out, and `seq` travels on the `state` message). A bot used to take its whole turn inside one `settle()` call, so clients only ever saw the board *after* all of it and played the arrival animations over an outcome already on screen — a land shown flying in was already tapped for the spell after it. Now `settle()` stops at each bot action: it publishes a frame, parks the move behind `holdForClients`, and releases it once every *acking* seat reports finishing that frame (`ack(connection, seq)`) and `BOT_MIN_THINK_MS` (350ms) has passed, with `FRAME_ACK_TIMEOUT_MS` (6s) as a backstop for a seat that has gone quiet — then pauses a further `BOT_LINGER_MS[botSpeed]` (the host's setting: fast 0 / normal 700ms / slow 1.6s) before the move, so a string of moves with little to animate still reads one at a time. Once that pause starts the ack timeout is cleared, so a slow client catching up late doesn't cut it short. A seat that has never acked never gates anything, so no client can deadlock a room; a disconnect re-checks the gate. A bot move nobody could watch is dispatched without a frame — a plain `pass-priority`, or any window where `isDeadForMana` says passing and tapping for mana are the only options. That isn't just tidiness: a beat spent on one of those lands *between* a spell being cast and that spell resolving, which is what made a creature seem to arrive long after its own play animation had finished. Whatever the move lets through is paced in the next frame. `RoomOptions.pacing: "immediate"` opts out of all of it (bots run to completion, one push at the end) and is what tests and scripts use; `RoomOptions.timers` swaps in a fake clock. `dispose()` drops a parked move's timers.
- **`pending-room.ts`** — `PendingRoom`: the same seat-claiming bookkeeping as `Room` (claim/reclaim semantics, `addBot`, `connectedSeats`, idle tracking) with no `Game`, no dispatch, no settle. `claimSeat(..., deck?)` stores the seat's deck, falling back to its positional starter deck from `decks.ts` so a bare room-code link still works. `isReady()` = every seat claimed or bot-filled; `toGameConfig()` assembles the `DeckList[]` and rolls the starting player (the "highroll") *at promotion time*, since turn order isn't settled before then. Deliberately a separate class, not a nullable-`game` variant of `Room`. **The table is also sized here, not at creation**: `addSeat()`/`removeSeat(player)` grow and shrink it between 2 and `SEATS.length`, which is what the seat board's add/remove controls drive. `addSeat` takes the first unused `SEATS` entry and re-sorts, so the seat array stays in printed seating order however the table was assembled — turn order comes straight off that array, and must not depend on the order seats were added. `removeSeat` refuses a seat a human has claimed (leaving is that player's own call) but lets the host remove an open or bot-filled one.
- **`room-manager.ts`** — `RoomManager.createPending(players, config)` mints a room code and a `PendingRoom`; `promote(id)` builds the real `Game`/`Room` for a ready one (wiring its `onUpdate` to the manager's own `onRoomUpdate`), replays its connected claims and bot fills onto it, then `room.start()` settles it to the first real decision and publishes the opening frame. `get(id)` returns a `Room | PendingRoom`. `reapIdle(maxIdleMs)` disposes and drops abandoned rooms. No player-count assumption.
- **`ws-server.ts`** — `attachRoomServer(wss, manager)` wires a `WebSocketServer` to a `RoomManager`: parses messages as `ClientMessage`s, dispatches to the matching `Room`/`PendingRoom`/`RoomManager` call, pushes `ServerMessage`s back. **`broadcast` is never called from a message handler** — a room publishes its own frames on its own clock now (one per bot action), so it's wired up as `manager.onRoomUpdate` and as `room.onUpdate` on any room `requireRoom` is handed, and anything wanting a push calls `room.publish()`. That second binding is what keeps the hand-built-`Room` `scratch.mjs` pattern working without a real `RoomManager`. `create-room` clamps `players` (2-4, default 2) — the client always takes the default now and sizes the table from the seat board instead, so that parameter is for scripts and tests. `add-bot` mirrors `claim-seat`'s error shape and also sends a direct `room-joined` refresh, since the caller may not hold a seat yet and so isn't in `connectedSeats()`; `add-seat`/`remove-seat` need the same follow-up for the same reason, and are pending-room-only (`requirePendingRoom`) because a promoted room's turn order is already dealt. `ack` is exempt from the per-IP rate limit (it's automatic traffic, one per frame shown, with no effect beyond releasing a bot).
- **the wire protocol** lives in the `protocol/` workspace, not here — `server` and `client` both `import type { … } from "protocol"`. It was two hand-synced copies (`server/src/protocol.ts` and `client/src/net/protocol.ts`) until it became clear the reason given for that — Node package vs browser bundle — never applied to a file that compiles to nothing. `protocol/src/room.ts` holds the room protocol; `protocol/src/import-deck.ts` holds the `POST /import-deck` shapes, a separate surface (stateless, no room) that was mirrored just as silently. `ClientMessage`: `create-room {seed?, players?, hostToken?}`, `join-room {roomId, hostToken?}`, `claim-seat {seat, clientToken, displayName?, deck?}`, `add-bot {seat}`, `set-bot-deck {seat, deck}`, `add-seat`, `remove-seat {seat}`, `set-ready {ready}`, `start-game`, `set-bot-speed {speed}`, `dispatch {action}`, `pass-turn`, `auto-pass`, `toggle-mana-skip`, `resolve-all` (a **one-shot**, unlike the three standing modes beside it: pass this seat's priority until the stack drains, stopping the moment anything real happens — a decision for this seat, an opponent casting or activating, or something this seat owns being targeted or leaving the battlefield), `ack {seq}`. `ServerMessage`: `room-created`, `room-joined {seats, isHost, botSpeed}`, `state {seq, seat, view, actions, seats, autoPassing, autoPassPaused, skipManaOnly, isHost, botSpeed}`, `error`. A `WireDeck` carries `cards`/`commanders`/`name`/`printings` — one commander or a Partner pair, with the lone `commander` a client from before pairs sends still read (`engine`'s `commandersOf`). `SeatStatus` carries `claimed`/`online`/`displayName`/`isBot`, and its `deck` carries `commanders` as `{name, printing}` — just those cards, since the seat board only draws the commanders (a pair splits the art box in two); the whole map rides with the deck itself. Doesn't cover `/import-deck` (a plain HTTP route, not a WS message).
- **`decks.ts`** — `SEATS: SeatDeck[]`, up to four named seats (`ALICE`/`BOB`/`CAROL`/`DAVE`) in seating order, sliced by `create-room`'s `players` count — a seat's fallback deck when nobody brought their own. The deck contents come from `engine`'s `SAMPLE_DECKS`.
- **`import-deck.ts`** — the decklist-import backend, unrelated to any room: `parseDecklistText(text)` parses a pasted Moxfield-style export, honouring a `Commander` section header and keeping each line's `(SET) collector-number` suffix as a `printing`; `evaluateDecklist(entries, registry, onProgress?, {commanders, tags})` cross-references each name against the local `CardRegistry` (implemented cards reported from their `CardDefinition`), falls back to Scryfall for anything else (throttled, 429-aware retry), and gives each unimplemented card `replacements` (up to three, via `engine`'s `assignReplacements`) plus `suggestedReplacement` (the first). Stand-ins are chosen *for this deck*: the commander first (a legendary for a legendary), inside the commander's colour identity — read from Scryfall's `color_identity` when the commander itself is unimplemented — and never a card the list already has or another card's first choice. `lookupPrintingIds` resolves those suffixes to Scryfall card ids (`printingId`) so an imported deck arrives wearing the art it was exported with — batched by `{set, collector_number}` identifiers, which match back exactly, and only for *implemented* cards, since a substituted one is a different card whose art the suffix says nothing about. A returned card whose name doesn't match the line's is discarded: a stale collector number resolves to some other card, and pinning its art here would be worse than no printing at all. `formatCheck(...)` runs `validateCommanderDeck` over the result, reporting the `commanders` it settled on — two when a `Commander` section names two, or when Moxfield's trailing block is a pair the registry can't rule out. Scryfall lookups go through `lookupScryfallMany`, which **batches**: `POST /cards/collection` takes 75 names at a time, so a 100-card list costs two round-trips rather than a hundred throttled ones (~1s instead of ~35s). Responses carry no echo of which identifier produced which card, so they're matched back by name — each returned card is indexed under its own name, its `"Front // Back"` name rewritten in the single-slash form decklists use, and each face name. A name that misses is retried once per alternate spelling (`scryfallNameVariants`), one extra batched round each. Results (misses included) are cached process-wide for the life of the process. Wired up as `POST /import-deck` in `index.ts`, which answers with **newline-delimited JSON, not one object**: `{type:"progress", done, total, name}` lines as `evaluateDecklist`'s `onProgress` fires (implemented cards land at once, then a line per lookup batch), then exactly one terminal `{type:"result", cards, format}` or `{type:"error"}` line. Streamed so the deck builder's import panel can render a progress bar off those lines rather than sit silent. Live-fetching a Moxfield URL server-side was tried and abandoned (403s) — pasted export text only.

- **`oracle-tags.ts`** — `loadOracleTagIndex()`: the card replacer's oracle-tag index, read once from `server/data/oracle-tags/index.json` (null if missing — imports then match on type, cost and body alone). That file is **generated** by `npm run gen:oracle-tags -w server` from `server/data/oracle-tags/allowlist.txt`, the curated list of ~260 tags describing what cards *do* (removal, sweeper, edict, tutor, ramp, draw engine, recursion, tokens, anthem, evasion, punisher, …) — trivia tags (card names, cycles, typal, errata) are left out on purpose, since they're rare and would dominate an IDF-weighted score. The generator uses only Scryfall's public API: one paged `oracletag:<slug> legal:commander` search per tag (a parent tag's search includes its children, so listing both broad and specific tags gives graded credit), after checking every slug against scryfall.com/docs/tagger-tags — search answers an unknown tag exactly like an empty one. A card's own tags aren't in Scryfall's API; Tagger's GraphQL has them, but it's undocumented and nothing here uses it. Slow (~2s per page, most of an hour), so it's a checked-in, occasionally-regenerated file.

- **`capture.ts`** — saving a bot's blunder as a training scenario, a developer's tool: a room built with `RoomOptions.capture` (from `RoomManager`'s, set by `index.ts` only when started with **`--capture`** — the local `dev` script passes it, dev-rooms always has it, the production service never does) keeps a `CaptureLog` of the state just before each of its bots' last `CAPTURE_KEEP` (12) real decisions (`Room.botAction`; a dead-for-mana window isn't kept). Its host picks one from the game's **Capture** button (`client/src/ui/CapturePanel.tsx`, shown only when a `state` message carries `capture`), then the right answer from `captureOptions` or "anything but what it did", and the log writes a `ScenarioCapture` JSON to the git-ignored **`captures/`** at the repo root (a late four-player one is ~0.7 MB) over the `capture-list` / `capture-options` / `capture-save` messages. The panel's other tab files a **bug report** (`CaptureLog.report`, the `capture-report` message, answered with `capture-saved`): the game as it stands, its event log cut to the last `BUG_REPORT_EVENTS` (300), the reporting seat, a title and description, and optionally a photo (a PNG, JPEG, GIF or WebP data URL up to `BUG_REPORT_IMAGE_MAX`, 10 MB, picked or pasted in the panel and written beside the JSON under the same name), as a `BugReport` JSON in `captures/bugs/` — out of the scenario loaders' way, which read only `captures/*.json`; its `state` is a snapshot `bot:replay --from` starts from. Off the public site because a capture is the whole state, every hand and library included.
- **`status.ts`** — the operator endpoint, for reading over SSH with `curl`: `GET /status` (an aligned text table of rooms, seats, turn, step and idle time), `/status.json`, `/healthz`. It runs as a **second HTTP server bound to 127.0.0.1** (`STATUS_PORT`, default 4010) rather than a route on the game port, and that is load-bearing rather than tidy: a room code is a join credential, port 4000 is published to the internet by the Cloudflare tunnel, and a loopback *check* on 4000 would be worthless anyway because `cloudflared` makes every public request arrive from 127.0.0.1. Don't add it to the tunnel's ingress list.

## Server commands, in full

- `npm run test -w server` / `test:watch` / `build` / `typecheck`
- `npm run start -w server` — runs the built `dist/index.js`: a real room server on `ws://localhost:4000` (or `$PORT`)
- `npm run dev -w server` — `tsc --watch` + `node --watch dist/index.js` together
- `npm run dev-rooms -w server` — a room server (in place of the real one, on port 4000) preloaded with the board states in `server/scripts/dev-scenarios.mjs`. There is one room per entry, joined at `localhost:5173/?room=<CODE>`, with the first player as the human seat and scripted bots that attack, block and cast only as the scenario says, so the decision under test comes up on cue. Seeded with `TWOAA`/`TWOPW` (2-player combat, with and without a planeswalker), `FOURP` (4-player goad), `KWALL` (every keyword icon and every loyalty badge), `STACK` (token makers in hand to cast for real, since `debugSpawn` can't make a token), `LURES` (a Lure-enchanted attacker, for the block bar), `TOPLB`/`TOPL4` (Oracle of Mul Daya with a land revealed on top of the library, and Summon: Titan, a portrait-art Saga creature, in hand), `SWARM`/`HORDE`/`HORDE4` (one trampler blocked by a crowd: sixteen mostly different creatures, and a twenty-token stack plus three others, at two players and from the four-player seat the decision panel covers), `HORDB` (the other way round: a six-Goblin stack attacks, to block several of it — with three folded Soldiers and part of an engine-compacted stack of ten Zombies — and then to attack with part of that stack) `COUNT` (permanents carrying counters, for the tiles' counter chips) and `ENTAT` (four players: tokens entering tapped and attacking — Leonin Warleader, Hanweir Garrison, Adeline and General Kreat — each asking what it attacks, Adeline's only where the opponent has a planeswalker) and `MYRAD` (four players: Kaalia, Winota and Goldlust Triad's myriad — cards put onto the battlefield attacking, and token copies exiled at end of combat) and `DISCD`/`DISC4` (a discard as an activation cost that wants a creature card: Tortured Existence and Fauna Shaman, with lands in hand that can't be picked). A loopback-only command port, `127.0.0.1:4099`, takes JSON `list`, `state`, `reset`, `spawn`, `move`, `life` and an `eval` escape hatch (`curl -s localhost:4099 -d '{"op":"state","room":"FOURP"}'`). Every change pushes to the room's browsers at once. `reset` rebuilds a room from its scenario and drops the connections, and each tab reconnects and reclaims its seat by itself. Build `engine` first.
- `npm run gen:oracle-tags -w server` — rebuilds `server/data/oracle-tags/index.json` from `allowlist.txt` via Scryfall's search API (most of an hour; run it in the background and watch its stderr)

**To check a client change against a known board, use `npm run dev-rooms -w server`** (below) rather than playing up to the position. A git-ignored `scratch.mjs` at the repo root is still the scratch pad for one-off exploration (`node scratch.mjs` after building `engine`/`server`): build a `Game` (often spawning objects directly onto the battlefield), wrap it in a `Room`, and serve it over a raw `ws` `WebSocketServer` on port 4000 for a browser (or `claude-in-chrome`) to connect to at the client dev server's URL with `?room=<CODE>`. `dev-rooms` is that pattern made permanent.
