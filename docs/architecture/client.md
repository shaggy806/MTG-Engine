# Client architecture reference (`client/src/`)

Reference detail, **not loaded automatically**: read the entry for a file before changing it. The short, always-relevant version is `client/CLAUDE.md`; this is the per-file detail it points into. Keep it current when a file's shape changes, but it is a map of the code as it is, not a changelog.

## The workspace

- `client/` — a Vite + React 19 + TypeScript app: a **networked** client — each device is one seat, connected over WebSocket to a `server` room, never running a local `Game` or a controller loop itself. Imports the engine (`"engine": "*"`, the workspace symlink) as **`engine/client`** — `engine/src/client.ts`, a second package entry with every type but only the values a page uses, none of which reaches a card definition (`test/client-entry.test.ts` walks its imports to keep it so). The main `engine` barrel exports `BUILTIN_CARDS`, which imports every card file, and Vite's dev server doesn't tree-shake, so a page importing the barrel fetched all ~5,500 card modules on every load (16 s warm). No page imports `engine` itself. Consumes the engine's public seam — the `Action`/`LegalAction`/`PlayerView` types, plus pure helpers such as the combat validators — indirectly, via the wire protocol `server` speaks. Needs `engine/dist/` and `protocol/dist/` built (`npm run build` does engine, protocol, server, then client).

## Architecture

A **networked** client: each device is one seat, connected over WebSocket to a `server` room. It
never owns a `Game` or runs a controller loop itself. 2-player rooms render a classic vertical
layout; 3-4 player rooms render a 2x2 quadrant grid, with you always bottom-left.

**Three pages, branched by path in `main.tsx`** before `<App/>` is chosen, so `useNetworkGame`'s
eager WebSocket never opens for the two network-free ones: `/library` → `LibraryPage`,
`/deck-builder` → `DeckBuilderPage`, everything else → `App` (the game itself). The two
network-free pages are `React.lazy` chunks, each fetched **together with the whole card pool**
and rendered once both are in; the game's own download holds no card definitions at all (see
`cards/cardData.ts` below).

- **`cards/cardData.ts`** — the client's only way to card definitions, which the engine ships as
  32 name-hashed shards, each its own file in the build (engine `cards/card-shards.ts`). A
  **lookup by name** — `peekCard` (sync: the definition, `null` for no such card, `undefined`
  while its shard isn't loaded), `loadCard`, `requestCards` and the `useCardData` hook (re-renders
  as each shard arrives) — fetches only the shard that name hashes to. That serves the game page's
  two extras: an event-log name's tooltip (fetched as the pointer reaches it) and a double-faced
  card's other face in `ZoneViewer`. Everything a game needs to be *played* comes in the server's
  views instead. The **whole pool** — `loadCardPool`, then `cardPool()` (`cards`, `tokens`,
  `byName`, and a `CardRegistry` for the engine's deck rules) — is what the library and the deck
  builder read, synchronously, since `main.tsx` has loaded it before they render. A commander's art
  in the lobby needs no definition at all: the engine's generated `PINNED_ART` holds the few
  printings the pool pins, and everything else resolves on Scryfall by name. A shard that fails
  to load (the network, or a deploy replacing the build while a tab is open) reads as not loaded
  and is asked for again next time. While the pool loads, the lazy pages show
  `cards/PoolLoading.tsx`: a progress bar (`role="progressbar"`, shards loaded of
  `CARD_SHARD_COUNT`) fed by `usePoolProgress` — `poolProgress()`'s `{loaded, total}`, a snapshot
  replaced as each shard arrives, counting shards a lookup by name fetched first and never a failed
  one. A failed shard rejects `loadCardPool`, and `PoolLoadBoundary` swaps the bar for a reload
  offer; a shard that never answers leaves the bar still, so after 15 s without a new shard it
  says "This is taking longer than usual" with a Reload button, hung below the bar so the bar
  doesn't move, inside a `role="status"` region that's there (empty) from the start so a screen
  reader announces it. The bar's fill and the screen's fade-in follow `motionPrefs`
  (`--anim-scale`; neither moves under `[data-reduce-motion]`, set by the viewer's own setting or
  the browser's); `cards/cardData.test.ts` covers the accounting and
  `e2e/pool-progress.spec.ts` the page, holding the shard responses to read the bar part-way
  (`E2E_SHOTS_DIR` saves screenshots). `engine/client` doesn't export `BUILTIN_CARDS`,
  `POOL_CARDS`, `TOKEN_CARDS` or `createDefaultRegistry`, and must not start to: any of them puts
  the whole pool back into whichever chunk imported it.

- **`net/useNetworkGame.ts`** — owns the WebSocket connection and the current seat's latest `frame` (`{seq, view, actions}` — one server push, whole), with `view`/`actions` derived from it for bookkeeping that has to be current. Reconnects with exponential backoff; a previously-claimed seat (`clientToken` in `sessionStorage`, per-tab) is reclaimed automatically. `ConnectionStatus` is `connecting` → `no-room`/`room-not-found` → `choosing-seat` → `waiting-for-players` (my seat is claimed but the room is still a `PendingRoom` — other seats are open) → `playing`/`disconnected`. `spectating` is a connection watching a full room without a seat (`spectate()` sends `spectate-room`): `waiting-for-players` with no seat while the room waits, then `playing` on frames whose `seat` is only whose side is drawn nearest, no actions and every hand hidden; leaving clears it. `opponents: readonly PlayerId[]` is every other seat in turn order starting right after your own, wrapping around. `createRoom()` (mints and stores this tab's host token), `isHost`/`botSpeed`/`setBotSpeed(speed)`, `claimSeat(seat, displayName?, deck?)`, `addBot(seat)`, `addSeat()`/`removeSeat(seat)`, `dispatch(action)`, `passTurn()`/`autoPass()`/`toggleManaSkip()`, `ackFrame(seq)`, `nameOf(id)`. `everConnected` distinguishes a first visit to a server that isn't up from a connection actually lost mid-game — both land on `disconnected` (a failed initial socket fires `onerror` then `onclose` without ever reaching `no-room`), and only the wording differs. In a scenario builder room (a dev build against a `--builder` server) it also exposes `builder` (the `state` push's `BuilderInfo`) and `createBuilder` (which claims the room's first free seat as soon as it's joined, there being no seat board), `builderUpdate`, `builderStart`, `builderStop(snapshot)` and `builderSeat`; a seat switch re-stores the tab's claim under its new seat. **Blitzing** is `blitz(deck, report)`: a four-seat `create-room`, and on its `room-joined` the first seat claimed with the deck and readied, the other three filled with `add-bot` on `randomBotDecks` (the upgraded precons, all different), and `start-game` — one burst, since the server handles a socket's messages in order. `pendingBlitzRef` keeps every `room-joined` until the first `state` from moving the status, so the landing page stays up ("Shuffling up…", `blitzing`) and no seat board flashes past; an `error` on the way in drops back to that room's seat board with the error. `blitzReport` (what the import swapped or dropped) is kept for the game until `dismissBlitzReport`, and cleared by any other room move and by a rematch; `blitzRoom` says the joined room is one this tab blitzed into (remembered per tab, not across a reload), so its rematch reads "Blitz again". **A rematch** (`rematch()`, the host's; `rematch(true)` the Game menu's mid-game *Restart game*, after which `restarted` tells everyone but the host, as a toast, that the host restarted it) comes back as frames with the next `state.game`: `gameNumber` follows it, `canRematch` follows `state.canRematch`, and `lastGameRef` with `net/rematch.ts`'s `isRematch` tells a rematch's first frame from a new room's.
- **`net/rematch.ts`** — the rematch's pure logic, unit-tested: `isRematch(prev, next)` (the same room, a later `game` — not a first frame, nor another room's game) and `rematchOffer({canRematch, isHost, blitz, seats})`, what the end-of-game panel offers beside Main menu: the host's button ("Rematch", or "Blitz again" in a blitz room), everyone else a wait on the host's seat, nothing in a room that can't be rematched.
- **`net/`** — no `protocol.ts` of its own: the wire types come from the `protocol` workspace (`import type { ServerMessage } from "protocol"`), exactly as on the server.
- **`App.tsx`** — `App` picks a screen off `NetworkGame.status`: `LandingScreen` → `SeatPickerScreen` → `GameScreen`. A full room's `SeatPickerScreen` offers Spectate beside "Room is full."; a spectator's waiting room says so, and its `GameScreen` tags the top strip "· spectating", sends no pass settings and draws no Pass/Pass Turn/Auto-pass buttons (`SeatMenu` drops Concede and the bot takeover too). `GameScreen` renders the topbar/history popup, seat banner, `<Table>`, plus the floating `<Stack>` overlay and `<AnimationLayer>` as siblings. **Everything it draws comes from `usePlayback`'s `shown` view, never `game.view`** — the two differ for as long as an animation is running, and mixing them is what put a card's arrival animation over a board that already had the card on it. `Table` (keyed on `shown.revision`, i.e. one remount per frame actually shown) classifies `actions` into a `mode` (mulligan → commander-replacement → pay-life-for-untapped → reveal-for-untapped → choose-copy → choose-enchant → legend-rule → choose-modes → sacrifice → scry → assign-combat-damage → put-on-bottom → discard → attackers → blockers → choose-from-zone → choose-x → choose-sacrifice → targeting → cast-now → priority — `cast-now` last, so once one of its cast buttons is clicked the ordinary X / modes / targets steps take over, and `useNetworkGame`'s `dispatch` sends the finished `via: "effect"` cast as the decision's answer; a land on offer (hideaway's "you may play the exiled card" — the offer's `lands`) is a Play button that answers with a `play-land` directly; with several cards on offer, or `looked` cards to look at first, the card is picked in a `ZoneViewer` popup — "Don't cast" as its none — and a card with more than one way to cast it, kicked or not (a multikicker once per number of kicks, its `kickCount` echoed back), a face, or one X each when its target reads X (`xCost.minX` = `maxX`, which skips the X prompt), gets a button per way with a Back; an X spell's targeting runs on `specsAtX(targetSpecs, X)`, so an "X target …" group's Done waits for X members — `mayFinishGroup`) and builds the matching `Action` from click handlers. Each decision kind gets its own small UI (e.g. `commander-replacement` shows a move-to-command-zone prompt; `choose-modes` shows Yes/No, one-button-per-mode, or toggle+Confirm depending on shape (a choice among players, Tasigur's "you choose an opponent", labels each mode "Choose <name>" off the offer's `modePlayers`), plus "Yes to all N" / "No to all N" when identical triggers wait under a trigger's "you may" (`sameForAll`, answered with `forAll`); `choose-x`/`choose-sacrifice` run before targeting and thread through it; an escape cast's exiled cards and then a delve cast's are picked before those, each in a `ZoneViewer` (`pendingEscape`, `pendingDelve` — delve between its offer's `minCards` and `maxCards`), carried on as `CastPicks`). `renderPlayerPanel`/`renderHandAndControls` are shared between the 2-player and quadrant-grid layouts. What a spell or ability on the stack targets is marked on the board (`Table`'s `aim`: the top of the stack's targets, or the hovered entry's via `Stack`'s `onFocusEntry` — and while a frame plays out over the board, whatever is resolving in it, an entry that has already resolved marking nothing: `aimedEntry` in `game/resolveAims.ts`, off the bus's `aims`, which `Table` subscribes to as `resolve`): a red frame and a reticle (`ui/TargetedMark.tsx`) on a permanent, a red frame and a "Targeted" chip on a player's panel, a red glow on a targeted spell's stack card — its own channel, since the border ring and the attack outline are both in use while a player responds. **`setState` updaters must stay pure** — dispatch happens after `setTargeting`, not inside its updater. State that must *not* reset per frame lives in `GameScreen` and comes in as props — the peekable hand tray's raised flag, which as `Table`-local state slammed the hand shut every time you played a card. For the same reason, anything measured off the layout that changes what's drawn is measured in a `useLayoutEffect` or a callback ref (as the boards' tile width is), never a plain `useEffect`: a freshly mounted `Table` would paint one frame at the default first. The hand's card spacing did exactly that, and the hand jittered through the mulligan each time a bot decided. The division step (`pendingDivision`) serves an ability as well as a cast: an `activate-ability` offer's or a `choose-targets` decision's `divide` is carried on the `Targeting`, and the answer goes out as that action's `division`. A `Targeting` also carries `facts` (`viewTargetFacts(view)` — who controls a target, its power, off the view), which `slotOptions` narrows "controlled by different players" and "total power N or less" by; the off-board group popup's Confirm waits on `groupPowerExceeded`. The escape-exile picker serves a graveyard permission's "exile N other cards" too (Kotis), worded by the cast's `via`. A modal cast's mode chooser (`choose-cast-modes`) draws each mode's text through `Symbols`, and for a spree spell (rule 702.172a) keeps to the offer's `castModal.modeSets`: a mode is open while some payable set holds it beside the picks, and Confirm waits for picks that are one of those sets. A gift spell's promised variant is its `kickerKeyword: "gift"` button; the opponent is asked afterwards, one at a time, as an optional `choose-modes` with `about`. `zoneChoiceTitle` says whose hand the cards go to when a `choose-from-zone` offer's `forPlayer` is someone else. `zoneChoiceTitle` has a line for an `"exile"` destination (Necropolis Fiend's cost). `GameScreen` works out the seats around the player (`opponents`) from the frame being *shown*, not `NetworkGame.opponents` (the newest frame's): a scenario builder can change the number of players between frames, and the table must only ask the board it's drawing about players on it. It lazy-loads `builder/BuilderPanel.tsx` behind `import.meta.env.DEV`, so a production build doesn't contain it. A `choose-enchant` offer with `players` (an "Enchant player" Aura entering without being cast, rule 303.4f) lights up those players' panels, and a click on one answers it. Space never passes while a `.zone-viewer-overlay` popup (History, a graveyard) is open, and those popups close on Escape (`ui/useEscape.ts`). A finished game gets `GameResultPanel` over the final board (who won and how, how many turns, a table of each player's game from `game/gameStats.ts` — result, life, damage dealt and taken, life gained, spells cast, cards drawn — "View the board" to put it aside — Escape or a click outside too — and "Main menu"; the old corner line stays, with a "Main menu" button) and, from `rematchOffer`, the host's **Rematch** ("Blitz again" in a blitz room — held down from the click until the new game arrives or a refusal does, by the `errorSeq` it was clicked at) or everyone else's "Waiting for <host> to rematch…". `App` keys `GameScreen` on `gameNumber`, so a rematch starts the screen afresh: playback seeded from the new game's first frame (rather than animating it as what the old game did next — its event log is shorter, not a continuation), the old game's panels and dismissals gone, and the pass settings sent again to the new room. The bots' speed is in the Settings panel (`MotionControl`'s `botSpeed`, host only, a table with bots), not the top strip, where its three buttons squeezed the phase track to a few steps at laptop widths; both speed rows read slowest to fastest (`ui/botSpeeds.ts`). The waiting room has `lobby/InviteLink.tsx` under the room code ("Copy invite link", `/?room=CODE`, shown as text to copy where the clipboard is unavailable).
- **`lobby/`** — the two screens before a game. **`LandingScreen`** (`landing.css`) is the front door: a hero, then "Start a game" and "Join a game" as two separated panels, then the library/deck-builder pages as footer cards, and at the very bottom **`BlitzPanel`** — blitzing (goldfishing against three bots) as one full-width button, "Have a deck copied? Click here to blitz!", its label the only explanation: it reads the clipboard on the click (`navigator.clipboard.readText`), and a clipboard it can't read or with no "N Card Name" line (`looksLikeDecklist`) opens a box to paste into instead; the list goes through the deck import (`importDecklist`/`resolveImport`, stand-ins taken as-is), is saved as the active deck (`createDeckFromImport`), and `NetworkGame.blitz` starts the game; a list with no commander stops there with an error under the button. The page's sizes are px, laid out for a ~1440x860 window, so on a bigger one the whole page scales up with it (`useLandingZoom`: CSS `zoom` on every block but the backdrop, 1 up to that size, then by a fifth of the growth of whichever of width and height runs out first, at most 1.15: about 1.05 at 1080p and 1.13 at 1440p, where full step, 1.67, and half, 1.34, were both too large) rather than sitting as a small island of small text on a 1440p monitor; the buttons' and panels' own text is sized to fill them. `App.tsx`'s `BlitzReportToast` lists a blitz's stand-ins and dropped cards over the board until clicked (`.toast-sticky`, no fade). It is a real page, not `.overlay`/`.overlay-box` — reusing the same box the "Connecting…" dialog draws is why the app's first impression used to be a 368x277 modal on an empty scrim. It asks **no** player count: three "N players" buttons above the CTA left nothing tying the counts to the button under them (all four read as one menu), and the *selected count* was the only accent-coloured thing on the page, so a setting outranked the primary action. The count moved to `SeatBoard` — see below. The join field carries no `maxLength`: the browser applies that to pasted text, which would chop a pasted room *link* to five characters before `parseRoomCode` could read the code out of it; the cap lives in `normalizeCode` instead, and a complete five-character code submits itself. Behind it all, `client/public/menu-backdrop.webp` (a seamlessly-tiling 10x10 grid of the top 100 commanders) drifts diagonally: an outer element holds the angle and clips while an inner one, exactly one tile wider, slides exactly one tile — which lands on an identical repeat, so only a transform animates and no edge is ever dragged into view. Two things there are easy to get wrong and are commented in `landing.css`: the oversize has to add *half the opposite axis* rather than a flat percentage (a fixed 160% covers 16:9 and fails on a wide, short window), and the blur is baked into the image rather than applied as a CSS `filter` — blur strips exactly the high-frequency detail that costs bytes, which took the same 2048px export from 1278KB to 263KB. The shipped file is 1536x2128 at 152KB, from a 241MB 7680x10640 source: `magick src.png -background "#12171b" -alpha remove -alpha off -filter Lanczos -resize 1536x -gaussian-blur 0x3 -quality 72 menu-backdrop.webp`. **`SeatBoard`** (`lobby.css`) is the seat-picker/waiting room. It draws two boxes: the room's own, with `App.tsx`'s header (room code, invite link, the way back) passed in as `children` over the seats and sized to them, and beside it a box of its own for the settings and Start Game, the two centred as one group — one box holding both ran the screen's width, a long empty panel around a small table. Its table-shaping controls (seats, bots and their decks, Start Game) render only for the host; in that settings box (under the room box, its fields as one row, on a board narrower than ~1060px: a container query in `lobby.css`), **`RoomSettingsPanel`** shows the room's settings, above Start Game, (starting life as 20/30/40 presets plus a box that sends on Enter or blur, the first player as "Random (highroll)" or a seat, "Decks" as Any deck or Commander-legal — `RoomSettings.commanderLegalOnly`, which turns a seat's deck that fails `validateCommanderDeck` into a "Not Commander-legal: <reason>" line (`SeatStatus.deckProblem`) and greys its Ready, "Bot decks" as Precons or Upgraded — `RoomSettings.botDecks`, the pool "Add bot (random deck)" deals from (`randomBotDeck.ts`'s `botDecksOf`) — bot speed), editable by the host and plain text for everyone else (`NetworkGame.roomSettings`/`setRoomSettings`); everyone else sees a Host badge on the host's seat, and "Waiting for <host> to start". An open seat's "Add bot (random deck)" sends a deck with the `add-bot` (`randomBotDeck.ts`: any deck of the room's pool — `SAMPLE_DECKS`, or `UPGRADED_DECKS` with "Bot decks" on Upgraded — at random, one no other seat plays while there is one), so the server's positional fallback deck is only for scripts and tests. It owns table size via "Add player" tiles the size of a seat in every place the table doesn't fill — the board always has four places, so nothing moves as seats come and go (an empty dashed place for anyone but the host) — plus a × on any seat nobody is sitting in (2-4, enforced server-side by `PendingRoom`). A seat is the same width at every table size — the width it has when four share the row — and a smaller table is a narrower row of them, and with the four places always drawn the room box is one width, so it and the settings box centre together (the board runs the screen's width, `96vw`, and `--seat-w` is capped at 1.45 `--card-w` so the seats don't grow with it): letting two seats take half the row each made the two-player lobby a different screen (450px deck art, Start Game below the fold at 768px). An empty seat's deck slot is laid out like a filled one (an art-shaped box, then the name and commander lines), so the row doesn't go ragged as decks are picked. Its grid gap, the gap between the two boxes and the room box's own side padding share one `--seat-gap` token declared on `.seat-board`, because the grid runs the full width of the room box and two different numbers there read as an uneven row. A seat's deck starts as the deck builder's active one (`getActiveDeck()`) and can be swapped per seat in `DeckPickerModal`; `claimSeat`/`addBot`/`setBotDeck` send it as a `WireDeck`. **A device takes a seat as it arrives** in a waiting room (`SeatBoard`'s effect → `takeSeat` → the server's `take-seat`, un-readied, named "Player N"; `room-joined` carries the `seat` it got and whether the room is `pending`), so two people who haven't readied no longer both draw themselves in the first open seat. A full table under four grows a seat for the arrival. My own seat's name heading is itself the name field (the seat's current name as its placeholder) until Ready, which sends a typed name with it. A rejoin to a waiting room goes through `take-seat` too (it reuses the stored token), since an un-readied seat is freed when its device drops. In a dev build only (`import.meta.env.DEV`), `LandingScreen` adds a dashed "Scenario builder" card under the two page links (`.landing-nav-dev`).
- **`builder/`** — the **scenario builder's drawer**, a dev build only (see `docs/plans/scenario-builder.md`). `BuilderPanel.tsx` (`builder.css`) sits over the table's right edge, above `--bottom-band`, and edits the scenario (`protocol`'s `ScenarioSpec`): seats (2–4, life, poison, bot, whose turn, "Sit" to act for a seat), the starting step and library fill, a search of the whole card pool (`loadCardPool`; cards by their front face, and tokens) to add cards to any seat's zone, and the selected card's owner, zone, commander flag, tapped, summoning sickness, counters, attachment and place in its zone. It never changes the board itself: each control makes a new spec with `spec.ts` (pure, unit-tested) and sends it, and the server's rebuilt board comes back. While building, a press on a card of the board selects it here, caught on `pointerdown` in the capture phase — a tile's hover popover can be under the pointer by the time a click arrives. Scenarios save to `localStorage`, copy or download as JSON, and paste back in. While playing: "Back to start" and "Edit from here". Its **Manual checks** list (`ManualChecksSection.tsx`) goes through `docs/manual-checks.md` entry by entry: the text read from the doc itself (`manualChecksDoc.ts`, a Vite `?raw` import, parsed by heading), and a Load button for each board `manualChecks.ts` gives that heading (written with its `board()` shorthand; `server/src/test/manual-check-presets.test.ts` builds every one and fails on a heading without one). Your place and the entries ticked off are kept in `localStorage`.
- **`deck-builder/`** — `DeckBuilderPage` (`/deck-builder`, no room server needed to browse/build): search the pool, most played first by EDHREC rank, unranked cards last alphabetically (`cardPool().cards` filtered by `isDeckableCard` — no tokens, no back faces; the result list pages at `POOL_PAGE_SIZE` 100, larger than the library's because a row here is text rather than an image), build a 100-card deck with a commander or a Partner pair (`SavedDeck.commanders` — a deck saved with the older single `commander`, or holding a card under its flavor name, is migrated on its first read and written back, so the migrations can eventually go; starring a card pairs it with a commander it can partner with, and otherwise replaces them), and see live `validateCommanderDeck` legality — run in-browser from `engine` over `cardPool().registry`, no round-trip. **Right-clicking a card row** opens `CardContextMenu` (portalled to `<body>` and placed from JS, like the hover preview, since the lists are scroll boxes); its one unique item is "Change printing…", which opens `PrintingPicker` over Scryfall's `unique=prints` search (`printings.ts`, a direct browser call — one search for one card, unlike the import's hundred-name batch that needs the server). The choice is stored on `SavedDeck.printings` (card name → Scryfall card id) and travels `WireDeck.printings` → `DeckList.printings` → `viewFor`'s `art`. The server only accepts a bare card id there (`assertPrintingsAreSafe`): the value ends up as an `<img src>` in *every* seat's browser, and `resolveArtUrl` would otherwise take any absolute URL verbatim. Also hosts the **decklist import** panel ("Paste from clipboard" fills its box with `navigator.clipboard.readText`, saying to press Ctrl+V where the browser won't allow it), which POSTs pasted text to `/import-deck` (`importDeck.ts`'s `importDecklist`, shared with the landing page's blitz, as is `resolveImport`, the report-to-deck step), streams that endpoint's NDJSON progress lines into a live per-card progress bar, substitutes each unimplemented card's first suggested stand-in, and then opens `ReplacementReview` — a popup that walks the substitutions one at a time as real card faces (the original from Scryfall by name on the left, the up-to-three stand-ins on the right with a match-strength badge and the oracle tags each shares), where clicking a face (or 1-3, with ←/→ between cards) swaps it into the saved deck on the spot; a card the deck already holds is blocked. The report banner above the editor summarises the swaps and reopens the popup, and carries each kept card's `printingId` into the new deck's `printings` — so an imported list keeps the art it was exported with, without anyone opening the picker. `decks.ts` is per-browser persistence in `localStorage` (not `sessionStorage` — a deck should outlive the tab): a named `SavedDeck` list plus an `ActiveRef` pointing at either a saved deck or one of `engine`'s `STARTER_DECKS` (the precons, then their upgrades) directly, so a starter deck is playable without duplicating it first. A starter deck is shown through the same `DeckEditor` as a saved one, read-only (no `onChange`): no card pool, no row buttons, drag target or right-click menu, its groups in two columns, with its description and stand-ins above (`StarterIntro`) and each stand-in row marked with an asterisk; "Duplicate to edit" is how one changes. Server-side deck save/share doesn't exist yet. Delete asks first ("Delete this deck? It can't be undone.", Cancel focused): a deck lives only in this browser. With a commander, the pool keeps to its colour identity by default (`DeckEditor`'s "Only cards in the commander's colours", `colorIdentityOf`/`withinIdentity`, each card's identity cached once). The starter list names each deck's commander.
- **`library/`** — `LibraryPage` (`/library`): the public, read-only card gallery, shaped like a Scryfall search result — a sticky search/filter bar (text — name, flavor names, type line and rules text, type, colour, sort and its direction — unranked cards stay last either way —, a "Tokens" toggle) over a **paginated** responsive grid of whole printed card faces (`PAGE_SIZE` 60, rounded to a whole number of rows of the grid's current column count — `pageSizeFor`, measured by `useGridColumns` — so only the last page ends in a short row; `loading="lazy"` keeps images off the wire but does nothing about node count, which is what costs layout time as the pool grows into the thousands). Its rows are built once from `cardPool()`, the first time the page renders. - **`ui/art.ts`** — `resolveArtUrl(art, name, version?, opts?)`: a `CardDefinition.art` link (a bare card id, a Scryfall page/API link, or a direct `cards.scryfall.io` file, whose first path segment is the size and so gets re-pointed at the one asked for) or a by-name Scryfall fallback. `opts.backFace` appends `face=back`, which is the only way to address a DFC's second image when the reference is a card id — pass `VisibleObject.faceIsBack` for it. Names without a pinned printing resolve through a batched `/cards/collection` lookup (`queueArtLookup`), and that name → image-URL cache is **persisted to `localStorage`** (`mtg-engine:art-cache:v1`, 14-day expiry, capped at 4,000 entries) — so a repeat visit to the library renders the faces it has shown before from the browser's HTTP cache without re-asking Scryfall for every URL first. Blocked or full storage just means a cold start. **Every emitted URL is host-checked against `ALLOWED_ART_HOSTS`**, and anything else falls back to the by-name lookup: `art` is also where another player's chosen printing lands after crossing the wire, and this function is what turns a value into an `<img src>`, so an arbitrary host here would be a request from every viewer's browser to whoever picked it. `cssUrl(url)` wraps one for a `background-image` — **always use it there**: an unquoted `url()` token may not contain a quote character and `encodeURIComponent` leaves an apostrophe alone, so every card whose name has one ("Atraxa, Praetors' Voice") silently lost its art. `prefetchArt(manifest)`, from the first frame's `artManifest`, loads every card's art crop quietly: 1.5 s after that frame, names through the batched lookup, a pinned printing's API redirect paced under Scryfall's rate limit, four images at a time at low priority, nothing under the browser's data saver.

- **`game/blockGroups.ts`** — the block bar's model where one tile is several creatures, pure. A click on a folded tile takes a fitting member rather than the first: one of your blockers not yet blocking (`freeBlocker`), or the attacker with the fewest blockers so far (`leastBlocked`) — a stack of attacking tokens is woken into one attacker per token and folds right back into one tile, and before this every blocker landed on the same token. `blockPairs` gives the bar a count row per (your folded tile → the attacker tile it blocks), drawn with `ui/CountStepper.tsx` (− / a number field / + / "of N"; a `symbol` shown in place of the label, and `showMax` off leaving that fifth grid cell empty rather than gone, or every row after it shifts), and `setPairCount` adds or frees blockers to hit a count, keeping blocks spread. An engine-compacted stack takes part through **`game/stackMembers.ts`**: while a declaration is built, the offer is expanded so each stack is one member id per token (`<id>#<k>` — `expandAttackOffer` up to `ATTACK_MEMBER_CAP` (2000), since the engine attacks with every token declared, a stack past its wake-up cap as one counted attacker; `expandBlockOffer` up to the engine's blocking cap of 100), everything above works on members, the engine's own `blockingViolations`/`attackingViolations` run on the expanded offer, and Confirm folds them back into counted entries (`collapseAttacks`/`collapseBlocks` — a stack that all goes one way is sent without a count, as a whole stack, which a must-attack stack needs). `game.nameOf` resolves a member id to its stack. **A click on a tile of several attackers** (an engine stack or folded tokens) in the attack declaration opens the **attack split** beside it (`renderAttackSplitMenu`, on `AbilityMenu`'s `children` slot; the user's ask, 2026-10-07): a row per defender any of them may attack, each a `CountStepper` and "All", over the same assignments as the bar's count rows (`setAttackPairCount`); Done, Escape or a click elsewhere closes it. The blockers on it go to tokens that many at a time in the order they were assigned (`stackMembers.ts`'s `blockEntries`, the engine's `attackerMember`), which is what Confirm sends (`collapseBlocks`) and what the client's own menace and Lure check reads. The **`enter-attacking`** decision (what creatures put onto the battlefield attacking attack — rule 508.4) is answered with the same attack bar: `Table` reshapes its offer into a `declare-attackers` one where every creature must be sent somewhere (`mustAttack`), the banner reads "<card>: choose what each attacks — n of m" with Confirm, and `confirmAttackers` sends the `enter-attacking` action instead. A creature still waiting for its answer is attacking a placeholder in the view, so its tile shows no target until one is picked. - **`game/damageAssignment.ts`** — the `assign-combat-damage` bar's model, pure. `groupBlockers` folds the offer's blockers into rows of interchangeable ones (the same in everything the view shows bar summoning sickness, the same lethal, nothing attached), because a token stack blocks as one creature per token and one input each made a twenty-Goblin block taller than the quadrant under it. The rows scroll past a few, and the board takes clicks for the same choice (`clickMembers`: one more to lethal, else spare), each blocker badged with its damage. A click or a row's `+` that needs more than is free takes it from other blockers wherever that kills least: damage past lethal, then damage too little to kill, then the cheapest kills. The answer is still one amount per blocker in offer order, checked by the engine's `damageAssignmentViolations`. Indestructible blockers take lethal (trample needs it) but aren't drawn as dying.
- **`game/usePlayback.ts` + `game/animationBus.ts` + `game/animationSchedule.ts` + `game/resolveAims.ts`** — the animation pipeline, Hearthstone-style: **one thing at a time, and nothing may act until it finishes**. `usePlayback(frame, bus, onShown)` queues the server's frames and plays them one at a time — each frame's animations run against the board *before* it (the previous frame's, still on screen), and only when they finish does the new board replace it. It reports `{view, actions, revision, busy}`; `busy` empties `Table`'s action list (`game/tableActions.ts`, unit-tested: all but the mulligan, which stays up with its buttons locked — `Table`'s `locked` — while the newest frame still asks it, so an opponent's shuffle or your own redraw doesn't take the popup away and bring it back), and `onShown` (wired to `ackFrame`) is what lets the server hold its bots to the same rule. `scheduleEvents` gives each animate-worthy event its slot (`CARD_STEP_MS` 1800 / `HIT_STEP_MS` 720 / `DEATH_STEP_MS` 420 / `DRAW_STEP_MS` 520 / `TURN_STEP_MS` 1300 / `PHASE_STEP_MS` 700 / `TAP_STEP_MS` 260 — the same numbers `AnimationLayer`'s overlay timeouts and App.css's `animation-duration`s are written to, so nothing outlives its slot), with `MAX_FRAME_MS` (6s) as a backstop: the first paced slot that won't fit ends the frame, and it and everything after it are shown without animating rather than clustered past the ceiling. **A frame has two halves.** `before` plays over the old board (everything above); `after` plays over the new one once it's shown — a tile tilting to tapped or back upright (`permanent-tapped`/`permanent-untapped`, each kind one shared beat) — and the frame isn't acked, nor `busy` cleared, until it finishes. `usePlayback` publishes the `after` cues from a layout effect, once the new board is in the DOM and before it's painted, and `AnimationLayer` starts them in that same task with the wait handed to `.animate({ delay, fill: 'backwards' })`, so the new pose never paints first; a timer there would flash it. **The viewer's settings** (`game/motionPrefs.ts`, set from `ui/MotionControl.tsx`, the "Settings" button in the top strip, per device in `localStorage`): `animScale` (0.5–2) multiplies every slot, every overlay timeout and — as `--anim-scale` on `:root` — every overlay's CSS duration; reduced motion (the setting *or* `prefers-reduced-motion`) sets `:root[data-reduce-motion]`, which every reduced-motion rule in App.css keys on instead of the media query, drops the pure-movement slots (draws, taps), and turns the rest into fades and flashes (a hit flashes the target without the lunge, a played card fades in place). Both halves together are capped at `FRAME_CEILING_MS` (11s) however slow the viewer, under the server's 12s `FRAME_ACK_TIMEOUT_MS`. A hidden tab (`document.visibilityState`) animates nothing and acks each frame at once, so a backgrounded player never holds the bots up. **Only the animations in `PACED` (a card play, a combat hit, a permanent leaving, a tap) hold the game up**; a turn or phase banner is a caption that plays over whatever the board has moved on to, costing nothing — otherwise a land the bot played hangs in the air for the length of an "End Phase" banner before reaching the table. Banners a frame merely passed *through* are dropped too (only the phase it lands in is announced), and `MAX_QUEUED_BANNERS` (3) keeps the banner queue from narrating a turn that finished several turns ago. `AnimationBus` carries cues sideways to `AnimationLayer` (a sibling, since `Table` remounts per frame), and **each cue carries the view it belongs to** — that's what makes a played land draw as it looked when played, rather than as it looks after the bot tapped it. A played card flies out of its owner's `.quadrant-cell` and shrinks back toward it (`flyOrigin` measures the cell off the live DOM and hands the offset to the CSS as `--fly-x`/`--fly-y`), so which side of the table a play came from is readable at a glance. A permanent leaving the board is shown where it stands (`runDeath`, on `permanent-left-battlefield`), by where it went: to a graveyard it drains of colour and sinks, to exile it flares white-blue and dissolves upward, anywhere else it fades; a run of them in one frame goes together on one beat. One returned to hand (`toZone: 'hand'`) flies to its *owner's* hand edge (`runBounce`), the owner read off the old board — every cue carries `prev`, the board the frame started from, for what only it knows. Cards leaving a library from the top (`cards-milled`, `cards-put-into-exile` from a library — each arrival names its `owner`, so a face-down card or one already back in the library still finds its pile) peel off the pile's card (`libraryCardOf`: its cardback, or the revealed top card — never the `data-library-of` box, which stretches to the rail's height) as cardbacks turning over (`runMill`: one after another, `MILL_STAGGER_MS` 150 apart, up to `MAX_PEELED` 8, each a `MILL_STEP_MS` 560 peel; the pile's count, the panel's `data-library-count-of` and the `data-graveyard-count-of` / `data-exile-count-of` it lands in tick in step on the old board, and "−N exiled" / "−N milled" floats off the top of the card): darkening as they drop for a mill, flaring white-blue for an exile. All the cards shown sit on the pile from the start, each put in *under* the one before it so the card peeling is always on top of the ones still waiting (appended in order, a later one covered each peel), and each carries the number the pile's cardback shows while it's the top card, so the count on the pile itself runs down rather than hiding under the peels and jumping. Each peel's keyframe filters are one list of functions: lists that differ animate discretely, and Chromium painted the mill's last filter (`grayscale brightness(0.4)`) from the start, so its waiting cards came out black. **A run of them is one sequence**: the mill slots sharing a beat are merged per library (`libraryPeels` — "each player mills" or Pako's every-library exile peel side by side, one library's cards one after another), the beat lasting the whole run (`peelDurationMs`, laid out by `beatDuration`), and `AnimationLayer` gathers the run's cues by their shared delay into one `runMill`. That's what makes a cascade, a discover or an "exile cards until …" — which the engine announces one card per move — read as one library losing N cards like a mill of N, rather than N cards peeling at once under N "−1"s with the count dropping by one. Something leaving the stack (`spell-resolved`, `ability-resolved`, `spell-countered`, `spell-fizzled`) gets a paced `before` slot (`STACK_EXIT_MS` 520): a resolving permanent spell is **put down on its tile**: the schedule pairs a `spell-resolved` with the same object's `permanent-entered-battlefield` later in the frame (the engine keeps the id across zones) and gives the arrival a `putDown` slot (first in `AFTER_ORDER`, one beat each so several land in turn) instead of `enter` (`findLandings`, which also pairs a `land-played` with its arrival and a `spell-cast` nothing later in the frame takes off the stack with itself — see the cast spotlight below), marking both ends `putDown` only when both kept their slot under the ceiling (`scheduleEvents` lays the frame out again without any that didn't, since a held card's shorter first slot moves what follows) — never under reduced motion, which keeps the fade out and fade in. - Styling is `App.css` for the game table (plus a small `.css` beside each standalone page: `lobby/` — two files, `landing.css` and `lobby.css` — `deck-builder/`, `library/`) — legible dark table, no UI library. A library's card back is its owner's seat colour (the leather, glow and count ring mixed with `--seat`, inside a quadrant or on a draw/mill flight that copies the pile's `--seat` as `.seat-tinted`); any other face-down card keeps the plain leather. `index.css` holds the palette tokens (the "Mana" look since 2026-10-06 — a neutral near-black, a vivid gold accent, the seats as black, red, green and blue mana at full strength, Barlow for the body; the three faces — Barlow, Bebas Neue for headings (since 2026-10-07, over Cinzel; one weight, so `:root` turns off fake bold with `font-synthesis-weight: none`, and every rule using it sets `font-size-adjust: var(--font-display-adjust)` to size its capitals up to what Cinzel's read as), JetBrains Mono for codes and aligned numbers — are named only in `index.css`, as `--font-body`/`--font-display`/`--font-mono`, and every other rule reads those tokens; likewise the type scale `--text-2xs`…`--text-xl`, the elevations `--shadow-raised`/`--shadow-popover`/`--shadow-dialog`, the `--scrim*` veils (made from `--bg`), the card surfaces `--card-face`/`--card-bar`/`--card-well`, and `--on-accent` for text on a bright fill, and `--bevel`/`--bevel-pressed`: every button that looks like one carries a Minecraft-style bevel (a black outline, a light top-left edge, a deeper dark bottom-right one) that inverts while held and on a chosen option, through one `button:not(:where(…))` rule in `index.css` whose list names the buttons that stay flat (cards, list rows, text links, bare × icons, placeholders, round chips). Containers carry the same edges, softer: `--frame-raised` on dialogs, popovers, toasts and the action bar (ahead of their drop shadow), `--frame-sunk` on every text box and dropdown (one `:where()` rule in `index.css`) and on the scrolling lists you put things into (the deck builder's card pool and deck list, the History log, the builder's results and check text, the capture options). The game table's quadrants, boards and the lobby's seat panels stay flat on purpose, so the cards stay the raised things on the board. A colour still written as a literal elsewhere is a game colour — mana pips and tints, counters, card flags, the prompt blue — which a palette change leaves alone) and the corners are square everywhere but on cards and what is printed on them (mana pips, counters, P/T boxes); the palette and the corners are a commit each, so either reverts alone and the element-level baseline for `button` and for text `input`s; that input rule is written as `input:where(…)` so it weighs the same as a bare element selector and every per-page class rule still wins. Card art is the only network dependency. Out of scope: undo.

**Standing UI rules** (settled during the board redesign — see `client/BOARD_REDESIGN_PLAN.md`):

- **No fixed px.** Sizing is `clamp()`/`vw`/`vh`, derived from the shared `--card-w` token for anything card-sized — never a new hardcoded number.
- **`--card-w` is viewport-*width*-derived; cap it against height where height is the real constraint.** A card-shaped box inside a container whose height is a viewport fraction (the quadrants are roughly half of it) needs a height cap too, or it fits on a tall monitor and overflows a short one — the two scale independently, and `--card-w` sits at its 150px ceiling all the way down to a 1667px-wide viewport. `--card-w-max` is the ceiling and `--card-w` is what everything reads, so a height-constrained subtree narrows `--card-w` for itself against that ceiling (the command/library rail does exactly this: `.quadrant-body` is a `container-type: size` container and the rail caps at `32cqh`). That cap is set against the **commander slot alone**, because the library pile below it squashes to whatever is left rather than demanding a full card's height — stacking two full slots plus their labels needs about twice a card's height, which at 768px tall didn't fit at all (a 286px rail in a 269px quadrant, the library count clipped off every cell, and that overflow was what made the boards scroll). The rail also stretches to the quadrant's full height, so its seat-coloured divider runs down the whole board. Note that making `.quadrant-body` a size container also makes it the containing block for `position: fixed` descendants (`contain: layout`), which is why the board's hover popover has to leave the subtree entirely rather than just going fixed.
- **What a decision picks from the board is picked on the board**, never from a row of name buttons (two Forests, or two copies of one creature, are two identical buttons): the eligible permanents are highlighted and clicked, players by their panel (`PlayerPanel`'s `targetable`/`selected`). A `choose-from-zone` popup is titled by where the cards go (`zoneChoiceTitle` — `exile` for a graveyard-exile cost), and a choice that puts cards on the top or bottom of a library numbers its picks (`ZoneViewer`'s `selection.ordered`), the order picked being the order they go — an offer's `order` (library ordering: a scry's kept cards, "the rest on the bottom in any order") is titled as an order, the last pick lowest on the bottom; a discard with `orOneOf` takes one land card as an answer. A cast whose offer carries `divide` (Magma Opus) gets a division step once its targets are in (`pendingDivision`, mode `choose-division`): a `CountStepper` per target, at least 1 each, Cast enabled once they total the amount; a `split-mana` decision ("N mana in any combination of …", mode `split-mana`) is the same shape — a stepper per colour with its mana symbol, none past what's left to share out (`manaSplit`, cleared once sent), Add mana enabled at N/N; `finishTargets` is a named function so the step's `resume` can call back into it with the split. Buttons are for what isn't on the board — "Copy nothing", "All mine", Confirm, and "Keep …" when choosing new targets for a copy of a spell (the `choose-targets` action's `current`: the slot's target now, which may no longer be on the board to click; the prompt reads "Choose new targets for the copy of …"). And **every decision but the mulligan asks in the bottom-right `.decision-banner`**; one that picks from the hand (discard, put-on-bottom, a reveal land's reveal) holds the hand tray open under it rather than docking beside the hand, which pulled the strip out of its tray and squashed the board.
- **Mana symbols always go through `<Symbols text={…} />`**, which renders `{…}` tokens as sliced-artwork pips with a CSS fallback. Never hand-roll a coloured circle.
- **Columns that must be equal need `minmax(0, 1fr)`, not `1fr`.** A bare `1fr` is `minmax(auto, 1fr)`, so a track whose content has a wide minimum (a row of input-plus-button, a long unbreakable word, an image) takes more than its share and its neighbour takes less. On the landing page that silently gave the join panel 414px against the start panel's 387 while the footer nav below, having no such pressure, split evenly and lined up with neither. The same footgun is why the seat grid and the board rows are written with `minmax(0, 1fr)` too.
- **A child that names its own width inside a padded box will escape that padding.** `.seat-board` at `min(1180px, 90vw)` inside a `.seat-board-box` at `min(1180px, 94vw)` overran the box's content area on a wide screen and pushed the outer seat panels out through its side padding. Let the box own the width and the child fill it (`width: 100%`).
- **The client's automated tests are a few vitest unit tests for pure logic** (`src/**/*.test.ts`, `npm test -w client`, part of the root `npm test`: the animation scheduler, board order, event wording, the card pool's load progress, `game/resolveAims.ts`, `ui/arrowGeometry.ts` and `net/rematch.ts`) **and a Playwright smoke suite** (`client/e2e/`, `npm run test:e2e -w client`): the landing page, a 2- and a 4-player dev room at 1366x768, walking into combat, the library's and deck builder's card-loading bar (`pool-progress.spec.ts`), and exiling from the top of a library (`exile-from-library.spec.ts`: an impulse draw, a cascade and Ulamog's and Pako's exiles played in the EXILE / EXIL4 rooms, with the peels, floating totals and library counts sampled every animation frame, and the order and numbers of Ulamog's eight peels as they wait on bob's pile); `token-stack-counters.spec.ts` casts a token maker under Tribute to the World Tree in `TREES`/`TREE4` and checks the Warriors split off the stack end up one tile with their counters (it reads the engine through the `objects` command, and with `E2E_SHOTS_DIR` set saves screenshots at 1366x768, 1920x1080 and 2560x1440 and a frame sequence); and `resolve-arrows.spec.ts` (resolving arrows in the `ARRWS`/`ARRW4` dev rooms: landing on the right tiles and life totals and clear of the stack pile at three sizes, two targets, a Counterspell looping round the pile to the spell beneath it, an ability, two resolving in one frame, a bot's spell, reduced motion; `RESOLVE_ARROW_SHOTS=<dir>` films each resolution there), `e2e/put-down.spec.ts` (a resolving permanent spell put down on its tile in the `PUTDN`/`PUTD4` rooms at three sizes, sampled every animation frame: it starts at the stack, ends exactly on the tile — a tapped one too — the real tile isn't seen before the copy is on it, and the copy is gone straight after; `PUT_DOWN_SHOTS=<dir>` films each landing), `e2e/precon-last-cards.spec.ts` (the SLAUG, SHDRX and LOAMS rooms: Slaughter the Strong's banner counting total power with Confirm greyed out past 4, Shadrix Silverquill's "you may choose 2" with Choose none, and Life from the Loam's dredge offered before each draw — screenshots at the three desktop sizes), `e2e/hover-carry.spec.ts` (the pointer parked on a hand card, then on a tile, while an opponent casts in PUTDN at 1366x768 and 2560x1440 and PUTD4 at 1920x1080, sampled every animation frame: the card stays grown and the popover open through every remount, and both let go when the pointer leaves), and `e2e/rematch.spec.ts` (a blitz won by setting the bots' life to 0 through the command port, then "Blitz again": the same room code, a new opening hand, game 2 on the server, the import report not back; and a two-browser room where the host concedes, the guest's panel waits on the host, the host reopens the panel from the Game menu and rematches, and both land in the new game — screenshots of each at 1366x768 and 1920x1080 in the test's output folder). It catches a page that no longer loads or a flow that no longer reaches its decision, not a layout that got worse, so verify any UI change live in the browser, in *both* a 2-player and a 3-4 player room, since the layouts diverge — **and at a short viewport (~768px tall), not just whatever monitor you're on.** Several severe layout bugs (every battlefield tile crushed to its 40px floor, the command/library rail overflowing its quadrant, the hand fan hanging off the bottom of the screen) were invisible at 1440p and obvious at 768p.

## Client commands, in full

- `npm run dev -w client` — Vite dev server with HMR (build `engine`/`server` first); needs a room server reachable at `ws://<host>:4000` (override with `VITE_SERVER_URL`)
- `npm run build -w client` / `lint -w client` / `preview -w client`
- `npm run test:e2e -w client` — the Playwright smoke suite (`client/e2e/`, config `client/playwright.config.ts`, CI `.github/workflows/e2e.yml`). It starts `dev-rooms` and the Vite dev server itself, or reuses them if they're already up, and resets each dev room it uses through the command port. `E2E_WEB_PORT`, `E2E_SERVER_PORT` and `E2E_CONTROL_PORT` move it off 5173/4000/4099 — set any of them and it never reuses a running server (which could be another checkout's), so parallel worktrees each run their own: `E2E_WEB_PORT=5273 E2E_SERVER_PORT=4100 E2E_CONTROL_PORT=4199 npx playwright test`. Build `engine`, `protocol` and `server` first. Beside the list reporter, `e2e/progress-reporter.mjs` writes the run's progress (one unit per test, on its last attempt) through the engine's `scripts/progress.mjs`, for the job-progress bar. It runs one test at a time on purpose: a dev-rooms `reset` drops every open connection, not just that room's. `@playwright/test` is pinned to the version whose Chromium the cloud sessions' image ships; elsewhere run `npx playwright install chromium` once.
- To watch it run by hand: start a room server, then `npm run dev -w client` and open two tabs/devices to the same room code.
