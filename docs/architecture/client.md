# Client architecture reference (`client/src/`)

Reference detail, **not loaded automatically**: read the entry for a file before changing it. The short, always-relevant version is `client/CLAUDE.md`; this is the per-file detail it points into. Keep it current when a file's shape changes, but it is a map of the code as it is, not a changelog.

## The workspace

- `client/` — a Vite + React 19 + TypeScript app: a **networked** client — each device is one seat, connected over WebSocket to a `server` room, never running a local `Game` or a controller loop itself. Imports the engine (`"engine": "*"`, the workspace symlink) as **`engine/client`** — `engine/src/client.ts`, a second package entry with every type but only the values a page uses, none of which reaches a card definition (`test/client-entry.test.ts` walks its imports to keep it so). The main `engine` barrel exports `BUILTIN_CARDS`, which imports every card file, and Vite's dev server doesn't tree-shake, so a page importing the barrel fetched all ~5,500 card modules on every load (16 s warm). No page imports `engine` itself. Consumes the engine's public seam — the `Action`/`LegalAction`/`PlayerView` types, plus pure helpers such as the combat validators — indirectly, via the wire protocol `server` speaks. Needs `engine/dist/` and `protocol/dist/` built (`npm run build` does engine, protocol, server, then client).

## Architecture

A **networked** client: each device is one seat, connected over WebSocket to a `server` room. It
never owns a `Game` or runs a controller loop itself. 2-player rooms render a classic vertical
layout; 3-4 player rooms render a 2x2 quadrant grid, with you always bottom-left.

**Three pages, branched by path in `main.tsx`** before `<App/>` is chosen, so `useNetworkGame`'s
eager WebSocket never opens for the two network-free ones: `/library` → `LibraryPage`,
`/deck-builder` → `DeckBuilderPage`, everything else → `App` (the game itself). The two
network-free pages are `React.lazy` chunks, each fetched **together with the whole card pool**
and rendered once both are in; the game's own download holds no card definitions at all (see
`cards/cardData.ts` below).

- **`cards/cardData.ts`** — the client's only way to card definitions, which the engine ships as
  32 name-hashed shards, each its own file in the build (engine `cards/card-shards.ts`). A
  **lookup by name** — `peekCard` (sync: the definition, `null` for no such card, `undefined`
  while its shard isn't loaded), `loadCard`, `requestCards` and the `useCardData` hook (re-renders
  as each shard arrives) — fetches only the shard that name hashes to. That serves the game page's
  two extras: an event-log name's tooltip (fetched as the pointer reaches it) and a double-faced
  card's other face in `ZoneViewer`. Everything a game needs to be *played* comes in the server's
  views instead. The **whole pool** — `loadCardPool`, then `cardPool()` (`cards`, `tokens`,
  `byName`, and a `CardRegistry` for the engine's deck rules) — is what the library and the deck
  builder read, synchronously, since `main.tsx` has loaded it before they render. A commander's art
  in the lobby needs no definition at all: the engine's generated `PINNED_ART` holds the few
  printings the pool pins, and everything else resolves on Scryfall by name. A shard that fails
  to load (the network, or a deploy replacing the build while a tab is open) reads as not loaded
  and is asked for again next time. While the pool loads, the lazy pages show
  `cards/PoolLoading.tsx`: a progress bar (`role="progressbar"`, shards loaded of
  `CARD_SHARD_COUNT`) fed by `usePoolProgress` — `poolProgress()`'s `{loaded, total}`, a snapshot
  replaced as each shard arrives, counting shards a lookup by name fetched first and never a failed
  one. A failed shard rejects `loadCardPool`, and `PoolLoadBoundary` swaps the bar for a reload
  offer; a shard that never answers leaves the bar still, so after 15 s without a new shard it
  says "This is taking longer than usual" with a Reload button, hung below the bar so the bar
  doesn't move, inside a `role="status"` region that's there (empty) from the start so a screen
  reader announces it. The bar's fill and the screen's fade-in follow `motionPrefs`
  (`--anim-scale`; neither moves under `[data-reduce-motion]`, set by the viewer's own setting or
  the browser's); `cards/cardData.test.ts` covers the accounting and
  `e2e/pool-progress.spec.ts` the page, holding the shard responses to read the bar part-way
  (`E2E_SHOTS_DIR` saves screenshots). `engine/client` doesn't export `BUILTIN_CARDS`,
  `POOL_CARDS`, `TOKEN_CARDS` or `createDefaultRegistry`, and must not start to: any of them puts
  the whole pool back into whichever chunk imported it.

- **`net/useNetworkGame.ts`** — owns the WebSocket connection and the current seat's latest `frame` (`{seq, view, actions}` — one server push, whole), with `view`/`actions` derived from it for bookkeeping that has to be current. Reconnects with exponential backoff; a previously-claimed seat (`clientToken` in `sessionStorage`, per-tab) is reclaimed automatically. `ConnectionStatus` is `connecting` → `no-room`/`room-not-found` → `choosing-seat` → `waiting-for-players` (my seat is claimed but the room is still a `PendingRoom` — other seats are open) → `playing`/`disconnected`. `opponents: readonly PlayerId[]` is every other seat in turn order starting right after your own, wrapping around. `createRoom()` (mints and stores this tab's host token), `isHost`/`botSpeed`/`setBotSpeed(speed)`, `claimSeat(seat, displayName?, deck?)`, `addBot(seat)`, `addSeat()`/`removeSeat(seat)`, `dispatch(action)`, `passTurn()`/`autoPass()`/`toggleManaSkip()`, `ackFrame(seq)`, `nameOf(id)`. `everConnected` distinguishes a first visit to a server that isn't up from a connection actually lost mid-game — both land on `disconnected` (a failed initial socket fires `onerror` then `onclose` without ever reaching `no-room`), and only the wording differs. In a scenario builder room (a dev build against a `--builder` server) it also exposes `builder` (the `state` push's `BuilderInfo`) and `createBuilder` (which claims the room's first free seat as soon as it's joined, there being no seat board), `builderUpdate`, `builderStart`, `builderStop(snapshot)` and `builderSeat`; a seat switch re-stores the tab's claim under its new seat.
- **`net/`** — no `protocol.ts` of its own: the wire types come from the `protocol` workspace (`import type { ServerMessage } from "protocol"`), exactly as on the server.
- **`App.tsx`** — `App` picks a screen off `NetworkGame.status`: `LandingScreen` → `SeatPickerScreen` → `GameScreen`. `GameScreen` renders the topbar/history popup, seat banner, `<Table>`, plus the floating `<Stack>` overlay and `<AnimationLayer>` as siblings. **Everything it draws comes from `usePlayback`'s `shown` view, never `game.view`** — the two differ for as long as an animation is running, and mixing them is what put a card's arrival animation over a board that already had the card on it. `Table` (keyed on `shown.revision`, i.e. one remount per frame actually shown) classifies `actions` into a `mode` (mulligan → commander-replacement → pay-life-for-untapped → reveal-for-untapped → choose-copy → choose-enchant → legend-rule → choose-text → choose-modes → sacrifice → scry → assign-combat-damage → put-on-bottom → discard → attackers → blockers → choose-from-zone → choose-x → choose-sacrifice → targeting → cast-now → priority — `cast-now` last, so once one of its cast buttons is clicked the ordinary X / modes / targets steps take over, and `useNetworkGame`'s `dispatch` sends the finished `via: "effect"` cast as the decision's answer; a land on offer (hideaway's "you may play the exiled card" — the offer's `lands`) is a Play button that answers with a `play-land` directly; with several cards on offer, or `looked` cards to look at first, the card is picked in a `ZoneViewer` popup — "Don't cast" as its none — and a card with more than one way to cast it, kicked or not (a multikicker once per number of kicks, its `kickCount` echoed back), a face, or one X each when its target reads X (`xCost.minX` = `maxX`, which skips the X prompt), gets a button per way with a Back; an X spell's targeting runs on `specsAtX(targetSpecs, X)`, so an "X target …" group's Done waits for X members — `mayFinishGroup`) and builds the matching `Action` from click handlers. Each decision kind gets its own small UI (e.g. `commander-replacement` shows a move-to-command-zone prompt; `choose-modes` shows Yes/No, one-button-per-mode, or toggle+Confirm depending on shape, plus "Yes to all N" / "No to all N" when identical triggers wait under a trigger's "you may" (`sameForAll`, answered with `forAll`); `choose-x`/`choose-sacrifice` run before targeting and thread through it; an escape cast's exiled cards and then a delve cast's are picked before those, each in a `ZoneViewer` (`pendingEscape`, `pendingDelve` — delve between its offer's `minCards` and `maxCards`), carried on as `CastPicks`). `renderPlayerPanel`/`renderHandAndControls` are shared between the 2-player and quadrant-grid layouts. What a spell or ability on the stack targets is marked on the board (`Table`'s `aim`: the top of the stack's targets, or the hovered entry's via `Stack`'s `onFocusEntry` — and while a frame plays out over the board, whatever is resolving in it, an entry that has already resolved marking nothing: `aimedEntry` in `game/resolveAims.ts`, off the bus's `aims`, which `Table` subscribes to as `resolve`): a red frame and a reticle (`ui/TargetedMark.tsx`) on a permanent, a red frame and a "Targeted" chip on a player's panel, a red glow on a targeted spell's stack card — its own channel, since the border ring and the attack outline are both in use while a player responds. **`setState` updaters must stay pure** — dispatch happens after `setTargeting`, not inside its updater. State that must *not* reset per frame lives in `GameScreen` and comes in as props — the peekable hand tray's raised flag, which as `Table`-local state slammed the hand shut every time you played a card. For the same reason, anything measured off the layout that changes what's drawn is measured in a `useLayoutEffect` or a callback ref (as the boards' tile width is), never a plain `useEffect`: a freshly mounted `Table` would paint one frame at the default first. The hand's card spacing did exactly that, and the hand jittered through the mulligan each time a bot decided. The division step (`pendingDivision`) serves an ability as well as a cast: an `activate-ability` offer's or a `choose-targets` decision's `divide` is carried on the `Targeting`, and the answer goes out as that action's `division`. A `Targeting` also carries `facts` (`viewTargetFacts(view)` — who controls a target, its power, off the view), which `slotOptions` narrows "controlled by different players" and "total power N or less" by; the off-board group popup's Confirm waits on `groupPowerExceeded`. The escape-exile picker serves a graveyard permission's "exile N other cards" too (Kotis), worded by the cast's `via`. A modal cast's mode chooser (`choose-cast-modes`) draws each mode's text through `Symbols`, and for a spree spell (rule 702.172a) keeps to the offer's `castModal.modeSets`: a mode is open while some payable set holds it beside the picks, and Confirm waits for picks that are one of those sets. A gift spell's promised variant is its `kickerKeyword: "gift"` button; the opponent is asked afterwards, one at a time, as an optional `choose-modes` with `about`. `zoneChoiceTitle` says whose hand the cards go to when a `choose-from-zone` offer's `forPlayer` is someone else. `zoneChoiceTitle` has a line for an `"exile"` destination (Necropolis Fiend's cost). `GameScreen` works out the seats around the player (`opponents`) from the frame being *shown*, not `NetworkGame.opponents` (the newest frame's): a scenario builder can change the number of players between frames, and the table must only ask the board it's drawing about players on it. It lazy-loads `builder/BuilderPanel.tsx` behind `import.meta.env.DEV`, so a production build doesn't contain it. A `choose-enchant` offer with `players` (an "Enchant player" Aura entering without being cast, rule 303.4f) lights up those players' panels, and a click on one answers it. Space never passes while a `.zone-viewer-overlay` popup (History, a graveyard) is open, and those popups close on Escape (`ui/useEscape.ts`). A finished game gets `GameResultPanel` over the final board (who won and how, how many turns, a table of each player's game from `game/gameStats.ts` — result, life, damage dealt and taken, life gained, spells cast, cards drawn — "View the board" to put it aside — Escape or a click outside too — and "Main menu"; the old corner line stays, with a "Main menu" button); a rematch would need the server. The bots' speed is in the Settings panel (`MotionControl`'s `botSpeed`, host only, a table with bots), not the top strip, where its three buttons squeezed the phase track to a few steps at laptop widths; both speed rows read slowest to fastest (`ui/botSpeeds.ts`). The waiting room has `lobby/InviteLink.tsx` under the room code ("Copy invite link", `/?room=CODE`, shown as text to copy where the clipboard is unavailable).
- **`lobby/`** — the two screens before a game. **`LandingScreen`** (`landing.css`) is the front door: a hero, then "Start a game" and "Join a game" as two separated panels, then the library/deck-builder pages as footer cards. It is a real page, not `.overlay`/`.overlay-box` — reusing the same box the "Connecting…" dialog draws is why the app's first impression used to be a 368x277 modal on an empty scrim. It asks **no** player count: three "N players" buttons above the CTA left nothing tying the counts to the button under them (all four read as one menu), and the *selected count* was the only accent-coloured thing on the page, so a setting outranked the primary action. The count moved to `SeatBoard` — see below. The join field carries no `maxLength`: the browser applies that to pasted text, which would chop a pasted room *link* to five characters before `parseRoomCode` could read the code out of it; the cap lives in `normalizeCode` instead, and a complete five-character code submits itself. Behind it all, `client/public/menu-backdrop.webp` (a seamlessly-tiling 10x10 grid of the top 100 commanders) drifts diagonally: an outer element holds the angle and clips while an inner one, exactly one tile wider, slides exactly one tile — which lands on an identical repeat, so only a transform animates and no edge is ever dragged into view. Two things there are easy to get wrong and are commented in `landing.css`: the oversize has to add *half the opposite axis* rather than a flat percentage (a fixed 160% covers 16:9 and fails on a wide, short window), and the blur is baked into the image rather than applied as a CSS `filter` — blur strips exactly the high-frequency detail that costs bytes, which took the same 2048px export from 1278KB to 263KB. The shipped file is 1536x2128 at 152KB, from a 241MB 7680x10640 source: `magick src.png -background "#12171b" -alpha remove -alpha off -filter Lanczos -resize 1536x -gaussian-blur 0x3 -quality 72 menu-backdrop.webp`. **`SeatBoard`** (`lobby.css`) is the seat-picker/waiting room. Its table-shaping controls (seats, bots and their decks, Start Game) render only for the host; in a column to the right of the seats (under them, as one row, on a board narrower than ~1060px: a container query in `lobby.css`), **`RoomSettingsPanel`** shows the room's settings, above Start Game, (starting life as 20/30/40 presets plus a box that sends on Enter or blur, the first player as "Random (highroll)" or a seat, bot speed), editable by the host and plain text for everyone else (`NetworkGame.roomSettings`/`setRoomSettings`); everyone else sees a Host badge on the host's seat, and "Waiting for <host> to start". An open seat's "Add bot (random deck)" sends a deck with the `add-bot` (`randomBotDeck.ts`: a `BENCH_DECKS` deck at random, one no other seat plays while there is one), so the server's positional fallback deck is only for scripts and tests. It owns table size via "Add seat" and "Remove seat" tiles in a column on the end of the row (Remove drops the last seat nobody is sitting in, so the table shrinks from the end it grows at), plus a × on any such seat (2-4, enforced server-side by `PendingRoom`). A seat is the same width at every table size — the width it has when four share the row, with room for the controls column set aside — and a smaller table is a narrower, centred row of them: letting two seats take half the row each made the two-player lobby a different screen (450px deck art, Start Game below the fold at 768px). An empty seat's deck slot is laid out like a filled one (an art-shaped box, then the name and commander lines), so the row doesn't go ragged as decks are picked. Its grid gap and the dialog's own side padding share one `--seat-gap` token declared on `.seat-board-box`, because the grid runs the full width of that box and two different numbers there read as an uneven row. A seat's deck starts as the deck builder's active one (`getActiveDeck()`) and can be swapped per seat in `DeckPickerModal`; `claimSeat`/`addBot`/`setBotDeck` send it as a `WireDeck`. **A device takes a seat as it arrives** in a waiting room (`SeatBoard`'s effect → `takeSeat` → the server's `take-seat`, un-readied, named "Player N"; `room-joined` carries the `seat` it got and whether the room is `pending`), so two people who haven't readied no longer both draw themselves in the first open seat. A full table under four grows a seat for the arrival. The name field stays open until Ready, which sends a typed name with it. A rejoin to a waiting room goes through `take-seat` too (it reuses the stored token), since an un-readied seat is freed when its device drops. In a dev build only (`import.meta.env.DEV`), `LandingScreen` adds a dashed "Scenario builder" card under the two page links (`.landing-nav-dev`).
- **`builder/`** — the **scenario builder's drawer**, a dev build only (see `docs/plans/scenario-builder.md`). `BuilderPanel.tsx` (`builder.css`) sits over the table's right edge, above `--bottom-band`, and edits the scenario (`protocol`'s `ScenarioSpec`): seats (2–4, life, poison, bot, whose turn, "Sit" to act for a seat), the starting step and library fill, a search of the whole card pool (`loadCardPool`; cards by their front face, and tokens) to add cards to any seat's zone, and the selected card's owner, zone, commander flag, tapped, summoning sickness, counters, attachment and place in its zone. It never changes the board itself: each control makes a new spec with `spec.ts` (pure, unit-tested) and sends it, and the server's rebuilt board comes back. While building, a press on a card of the board selects it here, caught on `pointerdown` in the capture phase — a tile's hover popover can be under the pointer by the time a click arrives. Scenarios save to `localStorage`, copy or download as JSON, and paste back in. While playing: "Back to start" and "Edit from here". Its **Manual checks** list (`ManualChecksSection.tsx`) goes through `docs/manual-checks.md` entry by entry: the text read from the doc itself (`manualChecksDoc.ts`, a Vite `?raw` import, parsed by heading), and a Load button for each board `manualChecks.ts` gives that heading (written with its `board()` shorthand; `server/src/test/manual-check-presets.test.ts` builds every one and fails on a heading without one). Your place and the entries ticked off are kept in `localStorage`.
- **`deck-builder/`** — `DeckBuilderPage` (`/deck-builder`, no room server needed to browse/build): search the pool (`cardPool().cards` filtered by `isDeckableCard` — no tokens, no back faces; the result list pages at `POOL_PAGE_SIZE` 100, larger than the library's because a row here is text rather than an image), build a 100-card deck with a commander or a Partner pair (`SavedDeck.commanders` — a deck saved with the older single `commander` is migrated on read; starring a card pairs it with a commander it can partner with, and otherwise replaces them), and see live `validateCommanderDeck` legality — run in-browser from `engine` over `cardPool().registry`, no round-trip. **Right-clicking a card row** opens `CardContextMenu` (portalled to `<body>` and placed from JS, like the hover preview, since the lists are scroll boxes); its one unique item is "Change printing…", which opens `PrintingPicker` over Scryfall's `unique=prints` search (`printings.ts`, a direct browser call — one search for one card, unlike the import's hundred-name batch that needs the server). The choice is stored on `SavedDeck.printings` (card name → Scryfall card id) and travels `WireDeck.printings` → `DeckList.printings` → `viewFor`'s `art`. The server only accepts a bare card id there (`assertPrintingsAreSafe`): the value ends up as an `<img src>` in *every* seat's browser, and `resolveArtUrl` would otherwise take any absolute URL verbatim. Also hosts the **decklist import** panel, which POSTs pasted text to `/import-deck`, streams that endpoint's NDJSON progress lines into a live per-card progress bar, substitutes each unimplemented card's first suggested stand-in, and then opens `ReplacementReview` — a popup that walks the substitutions one at a time as real card faces (the original from Scryfall by name on the left, the up-to-three stand-ins on the right with a match-strength badge and the oracle tags each shares), where clicking a face (or 1-3, with ←/→ between cards) swaps it into the saved deck on the spot; a card the deck already holds is blocked. The report banner above the editor summarises the swaps and reopens the popup, and carries each kept card's `printingId` into the new deck's `printings` — so an imported list keeps the art it was exported with, without anyone opening the picker. `decks.ts` is per-browser persistence in `localStorage` (not `sessionStorage` — a deck should outlive the tab): a named `SavedDeck` list plus an `ActiveRef` pointing at either a saved deck or one of `engine`'s `SAMPLE_DECKS` directly, so a starter deck is playable without duplicating it first. Server-side deck save/share doesn't exist yet. Delete asks first ("Delete this deck? It can't be undone.", Cancel focused): a deck lives only in this browser. With a commander, the pool keeps to its colour identity by default (`DeckEditor`'s "Only cards in the commander's colours", `colorIdentityOf`/`withinIdentity`, each card's identity cached once). The starter list names each deck's commander.
- **`library/`** — `LibraryPage` (`/library`): the public, read-only card gallery, shaped like a Scryfall search result — a sticky search/filter bar (text — name, flavor names, type line and rules text, type, colour, sort and its direction — unranked cards stay last either way —, a "Tokens" toggle) over a **paginated** responsive grid of whole printed card faces (`PAGE_SIZE` 60, rounded to a whole number of rows of the grid's current column count — `pageSizeFor`, measured by `useGridColumns` — so only the last page ends in a short row; `loading="lazy"` keeps images off the wire but does nothing about node count, which is what costs layout time as the pool grows into the thousands). Its rows are built once from `cardPool()`, the first time the page renders. One sort is **`Popularity`**, off `engine`'s generated `EDHREC_RANK` (which ships in the library's own chunk), with unranked cards (basics) last (`CardImage`, not `CardTile` — nothing here is a game object, so there's no live state to overlay), and a card's own page as an overlay rather than a side pane, so the grid keeps its scroll and filters. One entry per *card*, not per registered definition: a DFC's back face appears as its front's flip side (`isCardFront`), and tokens are excluded unless asked for. `?card=Name` deep links. An omen card (`omen`) is shown like an adventure: one printed image, its Omen beneath an "Omen" divider, never flippable. The pager's page number is a box to type a page into (`PageJump`, taken on Enter or blur).
- **`ui/`** — `CardTile` (a card face *reassembled* out of DOM — title/cost, Scryfall art crop via `ui/art.ts`, type line, text box, P/T or loyalty badge; props for `highlight`/`selected`/`activatable`/`badge`/`order`/`stackCount`/`compact` — because it has to overlay live game state on it). `CardImage` is the other half of that pair: the whole printed face as one image, for anywhere there's no game state to show (the library gallery). It owns `ui/card-image.css` — one of the two stylesheets a component imports rather than a page, with `Symbols`' `ui/symbols.css` — and skips the art lookup entirely for a token with no pinned printing, since a token's name isn't one Scryfall has ever known. `ui/Symbols.tsx`+`symbols.ts`+`mana.ts` render `{…}` mana tokens as pips (art sliced from a spritesheet, CSS fallback for exotic symbols) — every cost on screen goes through them, a button's too (Cycle, Suspend, a cast's kicker or cost option, a zone viewer's ways to cast, a "you may pay" prompt). `CostSymbols` draws a cost as it is now (`effectiveManaCost`) against the printed one, its generic number tinted a muted green when it has come down, red when it has gone up. A planeswalker loyalty cost opening a line (`[+1]:`, `[-4]:`, `[0]:`, or the bare `+1:` Oracle form) becomes the printed loyalty badge instead: the Mana font's up/down/zero shape with the number laid over it, nudged per shape into the shape's body. That covers every card text and the ability menu at once. A permanent's loyalty is `LoyaltyCounter`, the starting-loyalty shield, in place of a gold box. `ZoneViewer` (takes `ids` + a `resolve(id)` lookup so an unresolvable id renders face-down; optional `castable` prop for graveyard flashback/play-from-graveyard buttons; in `selection` mode — a forced choose-from-zone/scry/surveil decision, whose optional `fits` (an offer's `together`, via `fitsTogether`) holds Confirm until the picks obey a set rule — a "View board" button hides it via `collapsed`/`onCollapse`, still mounted so picks survive, and `Table`'s `decisionCollapsed` puts a "Show choices" button in the decision strip as the way back; `CreatureTypePicker` shares the same state). `MiniTile` (a battlefield permanent as art + a stat badge; `held` is what it holds in exile — the engine's `VisibleObject.holding` resolved against the shown view, `null` for a face-down card — drawn beside the hover card under "Exiled with it", smaller as there are more, with an `Ex N` chip from `CardFlags` on the tile) **portals its hover popover to `document.body` and places it from JS** — below the tile, flipped above when near the bottom of the screen, clamped inside the viewport; it can't be a CSS-revealed absolutely-positioned child, since `.quadrant-body` is a scroll box (clips it) *and* a size container (so `position: fixed` wouldn't escape either). Its width is **per board**: `Table`'s `recomputeBoardMiniW` binary-searches the widest `--mini-w-fit` at which that board's rows still fit its quadrant's height, and the `.board` rule caps it at `--card-w-max`, so a sparse board's tiles grow into the room they have and a crowded one's shrink, to a 40px floor past which the board scrolls. It measures the rows' extent, never the board's own box — the board is stretched to the command/library rail's height, which is what used to pin every tile at the floor. `.quadrant-body` reserves its scrollbar's room (`scrollbar-gutter: stable`): without it the search could loop forever, a width that fits with no scrollbar wrapping a tile onto a new row once the scrollbar a probe left behind narrows the box, so the tiles jumped between rows every frame. A tile's keywords are drawn as the Mana font's Arena ability icons (`ui/abilityIcons.ts`, a `Record` over the engine's `Keyword` union so a new keyword without an icon fails the build). Only the font's woff2 is bundled, registered through `FontFace`, never the package's stylesheet, which drags in every font format. `mana-font` is pinned to an exact version because the glyphs are private-use code points copied from its CSS. On a tile (and in the keyword tooltips) each icon is drawn by **`KeywordIcon`** as an inline SVG of its outline, not as text: `ui/keywordIconPaths.ts`, generated by `npm run keyword-icons -w client` (`scripts/keyword-icons.mjs`) from `mana-font`'s `mana.svg`, holds each outline and the centre of its painted ink (measured on a canvas, not `getBBox`), and the viewBox is one em square around that centre, so the icon is centred in its circle at any size. As a font glyph it sat up to a pixel high in a 13px circle, because small text's baseline is rounded to the pixel. Re-run the script when `KEYWORD_GLYPH` changes or `mana-font` is upgraded. Its hover card (and a `CommanderTile`'s, and a hand card grown under the pointer) carries **`KeywordTips`** beside the card, after Hearthstone's keyword tooltips: a box per term with its name (and icon, for an engine keyword) and reminder text — the card's own keywords (`ui/keywordReminders.ts`, another `Record` over `Keyword`), then each term its rules text uses from `ui/textKeywords.ts` (ward, protection, prowess, toxic, kicker, flashback, scry, surveil, mill, Treasure… and engine keywords a card grants, "gains flying"). They fade in only after the pointer rests on a card (`--kt-delay`, 0.6s), so sweeping the board or the hand doesn't flash them. - **`ui/art.ts`** — `resolveArtUrl(art, name, version?, opts?)`: a `CardDefinition.art` link (a bare card id, a Scryfall page/API link, or a direct `cards.scryfall.io` file, whose first path segment is the size and so gets re-pointed at the one asked for) or a by-name Scryfall fallback. `opts.backFace` appends `face=back`, which is the only way to address a DFC's second image when the reference is a card id — pass `VisibleObject.faceIsBack` for it. Names without a pinned printing resolve through a batched `/cards/collection` lookup (`queueArtLookup`), and that name → image-URL cache is **persisted to `localStorage`** (`mtg-engine:art-cache:v1`, 14-day expiry, capped at 4,000 entries) — so a repeat visit to the library renders the faces it has shown before from the browser's HTTP cache without re-asking Scryfall for every URL first. Blocked or full storage just means a cold start. **Every emitted URL is host-checked against `ALLOWED_ART_HOSTS`**, and anything else falls back to the by-name lookup: `art` is also where another player's chosen printing lands after crossing the wire, and this function is what turns a value into an `<img src>`, so an arbitrary host here would be a request from every viewer's browser to whoever picked it. `cssUrl(url)` wraps one for a `background-image` — **always use it there**: an unquoted `url()` token may not contain a quote character and `encodeURIComponent` leaves an apostrophe alone, so every card whose name has one ("Atraxa, Praetors' Voice") silently lost its art. `prefetchArt(manifest)`, from the first frame's `artManifest`, loads every card's art crop quietly: 1.5 s after that frame, names through the batched lookup, a pinned printing's API redirect paced under Scryfall's rate limit, four images at a time at low priority, nothing under the browser's data saver.
- **`game/board.ts`** — `computeBoardEntries(view, pid)`: pure layout logic turning one player's battlefield into `BoardEntry[]` (bucketed by type, Auras/Equipment nested as `attachments`, matching untapped/tapped land stacks collapsed).
- **`game/boardOrder.ts`** — the order you've dragged your own permanents into, a client-only layout preference (where a permanent sits has no rules meaning): a list of object ids. `applyBoardOrder` sorts `computeBoardEntries`' tiles by it — a tile ranks by the earliest of its ids, so a token joining a stack keeps the stack's place, and tiles with no id in the list (anything that arrived since the last drag) follow in the board's own order. `moveInRow` gives the list after one drop. Only your own board is reordered; opponents' boards are as laid out.
- **`game/useBoardDrag.ts`** — the drag itself, used by `GameScreen` (not `Table`, which remounts every frame: a bot's move mid-drag would drop the tile) and handed to `Table` as `boardDrag`. Pointer events on `window`, not HTML5 drag-and-drop; a press becomes a drag after 6px, so a click on a tile still acts, and the click a real drag ends with is swallowed. It reads the board from the DOM each time — own rows carry `data-drag-row` (`lands` / `permanents`), tiles `data-obj-ids` — so whichever `Table` is mounted, the drop lands on what's drawn. The dragged tile follows the pointer (`.board-entry.dragging`, a `translate`), the tile nearest the pointer in its row shows a bar on the side it would drop (`.drop-before` / `.drop-after`), Escape cancels, and `body.board-dragging` hides hover cards. Rows never mix. The order is kept per room in `sessionStorage`, so a reload keeps it. The tile art's native image drag is off (`-webkit-user-drag` plus `onDragStart`): it fired `dragstart` and cancelled the pointer stream.

Pure; `waitingLabel.test.ts`.

- **`ui/SeatMenu.tsx`** — the top strip's "Seat" button: a panel (the animations panel's box) with *Let a bot play for me* / *Take back control* (`bot-takeover`; the button turns amber while a bot has the seat, and `GameScreen` empties the action list then), *Concede…* with an in-panel confirm (`concede`; hidden before the game begins and once you've left it), and *Leave the room*.
- **`game/blockGroups.ts`** — the block bar's model where one tile is several creatures, pure. A click on a folded tile takes a fitting member rather than the first: one of your blockers not yet blocking (`freeBlocker`), or the attacker with the fewest blockers so far (`leastBlocked`) — a stack of attacking tokens is woken into one attacker per token and folds right back into one tile, and before this every blocker landed on the same token. `blockPairs` gives the bar a count row per (your folded tile → the attacker tile it blocks), drawn with `ui/CountStepper.tsx` (− / a number field / + / "of N"), and `setPairCount` adds or frees blockers to hit a count, keeping blocks spread. A click on a tile whose members are all spoken for takes the whole tile back out. The answer is still one attacker per blocker id, checked by the engine's `blockingViolations`. A tile of several attacking tokens carries a shield and how many of them are blocked beside its `×N` pill (`MiniTile`'s `blockedCount`): picked in the bar while choosing, and afterwards the view's `blocked`, which every seat sees and which stays true once the blockers are gone (rule 509.1h). `board.ts`'s `tileKey` leaves `blocked` out, so the stack stays one tile rather than splitting in two. An engine-compacted stack takes part through **`game/stackMembers.ts`**: while a declaration is built, the offer is expanded so each stack is one member id per token (`<id>#<k>`, capped at the engine's 100 — `expandAttackOffer`/`expandBlockOffer`), everything above works on members, the engine's own `blockingViolations`/`attackingViolations` run on the expanded offer, and Confirm folds them back into counted entries (`collapseAttacks`/`collapseBlocks` — a stack that all goes one way is sent without a count, as a whole stack, which a must-attack stack needs). `game.nameOf` resolves a member id to its stack. The **`enter-attacking`** decision (what creatures put onto the battlefield attacking attack — rule 508.4) is answered with the same attack bar: `Table` reshapes its offer into a `declare-attackers` one where every creature must be sent somewhere (`mustAttack`), the banner reads "<card>: choose what each attacks — n of m" with Confirm, and `confirmAttackers` sends the `enter-attacking` action instead. A creature still waiting for its answer is attacking a placeholder in the view, so its tile shows no target until one is picked. A `choose-modes` offer with `about` (myriad's "you may", once per opponent) names that player after the prompt. **`game/attackGroups.ts`** is the attack bar's twin of this: a click on a tile takes a member not yet attacking (`freeAttacker`), and a count row per (your tile → a defender) (`attackPairs`, `setAttackPairCount`).
- **`game/damageAssignment.ts`** — the `assign-combat-damage` bar's model, pure. `groupBlockers` folds the offer's blockers into rows of interchangeable ones (the same in everything the view shows bar summoning sickness, the same lethal, nothing attached), because a token stack blocks as one creature per token and one input each made a twenty-Goblin block taller than the quadrant under it. The rows scroll past a few, and the board takes clicks for the same choice (`clickMembers`: one more to lethal, else spare), each blocker badged with its damage. A click or a row's `+` that needs more than is free takes it from other blockers wherever that kills least: damage past lethal, then damage too little to kill, then the cheapest kills. The answer is still one amount per blocker in offer order, checked by the engine's `damageAssignmentViolations`. Indestructible blockers take lethal (trample needs it) but aren't drawn as dying.
- **`game/usePlayback.ts` + `game/animationBus.ts` + `game/animationSchedule.ts` + `game/resolveAims.ts`** — the animation pipeline, Hearthstone-style: **one thing at a time, and nothing may act until it finishes**. `usePlayback(frame, bus, onShown)` queues the server's frames and plays them one at a time — each frame's animations run against the board *before* it (the previous frame's, still on screen), and only when they finish does the new board replace it. It reports `{view, actions, revision, busy}`; `busy` empties `Table`'s action list, and `onShown` (wired to `ackFrame`) is what lets the server hold its bots to the same rule. `scheduleEvents` gives each animate-worthy event its slot (`CARD_STEP_MS` 1800 / `HIT_STEP_MS` 720 / `DEATH_STEP_MS` 420 / `DRAW_STEP_MS` 520 / `TURN_STEP_MS` 1300 / `PHASE_STEP_MS` 700 / `TAP_STEP_MS` 260 — the same numbers `AnimationLayer`'s overlay timeouts and App.css's `animation-duration`s are written to, so nothing outlives its slot), with `MAX_FRAME_MS` (6s) as a backstop: the first paced slot that won't fit ends the frame, and it and everything after it are shown without animating rather than clustered past the ceiling. **A frame has two halves.** `before` plays over the old board (everything above); `after` plays over the new one once it's shown — a tile tilting to tapped or back upright (`permanent-tapped`/`permanent-untapped`, each kind one shared beat) — and the frame isn't acked, nor `busy` cleared, until it finishes. `usePlayback` publishes the `after` cues from a layout effect, once the new board is in the DOM and before it's painted, and `AnimationLayer` starts them in that same task with the wait handed to `.animate({ delay, fill: 'backwards' })`, so the new pose never paints first; a timer there would flash it. **The viewer's settings** (`game/motionPrefs.ts`, set from `ui/MotionControl.tsx`, the "Settings" button in the top strip, per device in `localStorage`): `animScale` (0.5–2) multiplies every slot, every overlay timeout and — as `--anim-scale` on `:root` — every overlay's CSS duration; reduced motion (the setting *or* `prefers-reduced-motion`) sets `:root[data-reduce-motion]`, which every reduced-motion rule in App.css keys on instead of the media query, drops the pure-movement slots (draws, taps), and turns the rest into fades and flashes (a hit flashes the target without the lunge, a played card fades in place). Both halves together are capped at `FRAME_CEILING_MS` (11s) however slow the viewer, under the server's 12s `FRAME_ACK_TIMEOUT_MS`. A hidden tab (`document.visibilityState`) animates nothing and acks each frame at once, so a backgrounded player never holds the bots up. **Only the animations in `PACED` (a card play, a combat hit, a permanent leaving, a tap) hold the game up**; a turn or phase banner is a caption that plays over whatever the board has moved on to, costing nothing — otherwise a land the bot played hangs in the air for the length of an "End Phase" banner before reaching the table. Banners a frame merely passed *through* are dropped too (only the phase it lands in is announced), and `MAX_QUEUED_BANNERS` (3) keeps the banner queue from narrating a turn that finished several turns ago. `AnimationBus` carries cues sideways to `AnimationLayer` (a sibling, since `Table` remounts per frame), and **each cue carries the view it belongs to** — that's what makes a played land draw as it looked when played, rather than as it looks after the bot tapped it. A played card flies out of its owner's `.quadrant-cell` and shrinks back toward it (`flyOrigin` measures the cell off the live DOM and hands the offset to the CSS as `--fly-x`/`--fly-y`), so which side of the table a play came from is readable at a glance. A permanent leaving the board is shown where it stands (`runDeath`, on `permanent-left-battlefield`), by where it went: to a graveyard it drains of colour and sinks, to exile it flares white-blue and dissolves upward, anywhere else it fades; a run of them in one frame goes together on one beat. One returned to hand (`toZone: 'hand'`) flies to its *owner's* hand edge (`runBounce`), the owner read off the old board — every cue carries `prev`, the board the frame started from, for what only it knows. Cards leaving a library from the top (`cards-milled`, `cards-put-into-exile` from a library — each arrival names its `owner`, so a face-down card or one already back in the library still finds its pile) peel off the pile's card (`libraryCardOf`: its cardback, or the revealed top card — never the `data-library-of` box, which stretches to the rail's height) as cardbacks turning over (`runMill`: one after another, `MILL_STAGGER_MS` 150 apart, up to `MAX_PEELED` 8, each a `MILL_STEP_MS` 560 peel; the pile's count, the panel's `data-library-count-of` and the `data-graveyard-count-of` / `data-exile-count-of` it lands in tick in step on the old board, and "−N exiled" / "−N milled" floats off the top of the card): darkening as they drop for a mill, flaring white-blue for an exile. All the cards shown sit on the pile from the start, each put in *under* the one before it so the card peeling is always on top of the ones still waiting (appended in order, a later one covered each peel), and each carries the number the pile's cardback shows while it's the top card, so the count on the pile itself runs down rather than hiding under the peels and jumping. Each peel's keyframe filters are one list of functions: lists that differ animate discretely, and Chromium painted the mill's last filter (`grayscale brightness(0.4)`) from the start, so its waiting cards came out black. **A run of them is one sequence**: the mill slots sharing a beat are merged per library (`libraryPeels` — "each player mills" or Pako's every-library exile peel side by side, one library's cards one after another), the beat lasting the whole run (`peelDurationMs`, laid out by `beatDuration`), and `AnimationLayer` gathers the run's cues by their shared delay into one `runMill`. That's what makes a cascade, a discover or an "exile cards until …" — which the engine announces one card per move — read as one library losing N cards like a mill of N, rather than N cards peeling at once under N "−1"s with the count dropping by one. A discard (`runDiscard`) lifts your own cards out of the fan and greys them away. **Moves** — a change of control, an Aura or Equipment moving to a new host, the monarch's crown — need both boards: the frame's first half takes a hidden snapshot of the old spot the moment it starts (`captureMove`, a zero-cost `capture` slot), and the second half flies it onto the new spot with the real one held hidden until it lands (`runMove`/`runCrown`, `MOVE_STEP_MS` 560 / `CROWN_STEP_MS` 640); without a snapshot (an Aura just cast) it simply arrives. The cast caption names the zone a spell came from when it isn't the hand ("casts from their graveyard"). It goes through `flyGhost`, the one "a card moves from here to there" helper: a copy of the tile in its own `.ghost-flight` box on `<body>`, outside React (the board it came from is about to remount), sized from the tile's layout width rather than its tilted on-screen box, flown with `.animate()` and removed when it lands, while the real tile is hidden. An attacking creature is tapped, so its tile is drawn tilted — the lunge travels on the outer `data-obj-id` box and the tilted face inside just goes along (straightening it up on impact read as the card spinning), clamped to stay inside its quadrant's scroll box, since a tile translated past a scroll box's edge counts toward its scrollable overflow and flashes a scrollbar. Something leaving the stack (`spell-resolved`, `ability-resolved`, `spell-countered`, `spell-fizzled`) gets a paced `before` slot (`STACK_EXIT_MS` 520): a resolving permanent spell is **put down on its tile**: the schedule pairs a `spell-resolved` with the same object's `permanent-entered-battlefield` later in the frame (the engine keeps the id across zones) and gives the arrival a `putDown` slot (first in `AFTER_ORDER`, one beat each so several land in turn) instead of `enter` (`findLandings`, which also pairs a `land-played` with its arrival and a `spell-cast` nothing later in the frame takes off the stack with itself — see the cast spotlight below), marking both ends `putDown` only when both kept their slot under the ceiling (`scheduleEvents` lays the frame out again without any that didn't, since a held card's shorter first slot moves what follows) — never under reduced motion, which keeps the fade out and fade in. The exit lifts the card (`liftOffStack`: the entry's copy without its caption and target line, in a size-less `.ghost-flight` box on its centre, scaling up with a shadow over the exit beat, held across the board swap by object id), and `putDownOnTile` flies it onto the permanent's tile (`boardTileOf`, so a folded `data-obj-ids` member too) on the new board: the box translates, the card shrinks uniformly to the tile's width while a copy of the tile's layout box (so a tapped tile lands tilted; its size tokens pinned by `pinTileTokens`) grows from the card's, cross-fading between 30% and 80% of the flight; the real tile is held at opacity 0 for exactly the flight, ending in the frame the flight's finish event removes the copy (`HIDE_UNTIL_LANDED`: showing it early put it beside a copy still short of it once flights grew with distance), and one joining a tile already there glows "+1" instead. No card held (the entry wasn't drawn) grows the permanent in as `runEnter`; no tile in view (`inView`: the window and every clipping box round it) fades the card where it hovers and grows the tile in; a new frame's first half drops any card still held (`dropAllLifted`). Without `putDown` (a ceiling cut its pair) `runStackExit` flies the entry to its controller's side as before; everything else ends where it is, since no graveyard or exile is drawn on the table to send it to (the user's call, 2026-09-30): an instant or sorcery flares and lifts away, an ability dissolves, and a countered or fizzled one breaks (a shudder, drained of colour, then it drops and fades) so it can't read as resolved. As an entry leaves, the rest of its pile moves up into the gap there and then (`ui/stackDepth.ts`'s `closeStackGap`, with the depth styling `Stack` uses, `stackDepthVars`): a deep stack resolved in one frame used to stand still until every entry had gone (a bug report, 2026-10-04). **What resolves points at what it hits** (`scheduleEvents`' `aims`, a `ResolveAim` per `spell-resolved`/`ability-resolved` with a slot — never a countered or fizzled one, which doesn't resolve): from the first animated event of its resolution — the engine logs a spell's effects before it logs the spell leaving the stack, so a creature it destroys fades out before its exit beat — to the end of that beat; a resolution begins after the last `priority-passed` (rule 117.4) or resolution before it, or with the frame if it began in an earlier one. `usePlayback` plays them on the bus's `aims` (`ResolveAims`, `game/resolveAims.ts`: an observable `{resolving, gone}` with its own timers, played as the first half starts and cleared as the board is shown — state rather than a cue, since `Table`, which reads it, remounts per frame and can mount a moment after a queued frame's first half starts). A trigger going on the stack (`ability-triggered`) lights its source's tile in the `after` half (`TRIGGER_STEP_MS` 480, one shared beat, `runPulse`), and in the same beat a copy of its entry flies out of that tile into its place in the pile (`flyTriggerIn`, found by the event's `object`: it starts the tile's size and upright and grows and turns into the entry's depth, the real entry held hidden until it lands; `holdEntriesAbove` leaves such an entry alone); a source that's already gone — a dies trigger's — has no tile to light or fly from, and its entry arrives in place, as every trigger's does under reduced motion. The `after` half also carries the board's own changes, **grouped by kind** (`AFTER_ORDER`: untap, tap, enter, flip, counter, buff, hurt, pulse — not log order), each run of one kind on one shared beat: a permanent arriving grows into place, and a token also shimmers cyan (`runEnter`, `ENTER_STEP_MS` 420, reading `VisibleObject.isToken`; `runEnters` plays one arrival per tile, so permanents the board folds into one tile — each `.board-entry` lists its members in `data-obj-ids` — grow in once with "×N" floating off, and ones joining a tile already there glow with "+N"); counters glow green (purple-red for −1/−1) and a one-shot pump or granted keyword glows blue, each with its change floating off the tile (`runMark`, `MARK_STEP_MS` 520); a transformed card swings in edge-on (`runFlip`); `life-changed` flashes the player's panel green or red and floats the amount off the life total, and damage to a creature floats "−N" off its tile, with a red flash when it wasn't combat (the strike already showed that) (`runHurt`, `HURT_STEP_MS` 700). Combat damage to a creature is the one event with a slot in each half. The floating words are `floatText`: a `.float-text` element on `<body>`, outside React, gone when it's done. A static buff (a lord, an anthem) changes P/T with no event, so it has no animation. The cast spotlight carries a "Bob casts" / "Bob plays" caption in the caster's seat colour, and by default **rises** from one spot for everyone, just left of the stack pile (`--spot-x`, measured off `.stack-overlay`'s inset and card width) so its flight into the stack is short (`:root[data-cast-entrance]`, the Animations panel's "Card entrance": rise, the older flight in from the caster's side, or a fade). **A card that goes somewhere flies there**: a spell still on the stack when the frame ends and a played land hold their spotlight (`CARD_HOLD_MS` 1296, the full beat's entrance and hold without its exit; `.played-card-fly.holds`, keyframes ending on the hold pose) and then, first thing in the second half, fly on — `liftSpotlight` takes the card and its caption out of React into a `.ghost-flight` box, and a land goes through `putDownOnTile` like a resolved permanent, while a spell goes through `slotIntoStack` into exactly the place its entry takes in the pile (`stackSpotOf`: the entry's card centre, and its depth's rotation and scale from its computed transform, so one buried under later arrivals lands tilted and shrunk where it lies; its `is-new` arrival is cancelled), turning and shrinking as it cross-fades into a copy of the entry, the real entry hidden for the flight. Entries new on this board above a landing spell (its cast trigger, a copy of it) are held hidden until it's down and then fade in (`holdEntriesAbove`), and its target arrows wait too (`ResolveState.arriving`, set by `usePlayback` as the board is shown and cleared by `landed` as the card lands). A spell resolved, countered, fizzled or exiled within the frame keeps the full spotlight; with no entry or tile in view the held card fades where it hovers; reduced motion has no flights at all. **A flight's time is its distance** (`flightMs`: 220 ms plus 1100 ms per viewport diagonal, between `FLIGHT_MIN_MS` 420 and `FLIGHT_MAX_MS` 1100, times `animScale`), so a card crossing a four-player table doesn't whip across it. The schedule can't know the distance (the new board doesn't exist yet), so a flight's slot reserves `FLIGHT_MAX_MS`, which keeps the ceiling honest; once the new board is mounted, `usePlayback`'s layout effect asks `AnimationLayer` (`bus.setFlightMeasure`, `measureFlight`) how long each flight takes from where its card is held to its target, `retimeFlights` pulls everything after each flight forward by what it saved, and the frame's backstop timer (started at the reserved length when the board is shown) is replaced by the measured one, so nothing idles after a short flight and the 12 s ack wait is never at risk. Each flight's box carries `data-object`, `data-to` (`stack`/`tile`) and `data-flight-ms` for `e2e/put-down.spec.ts`. A `card-drawn` sends a small cardback out of that player's library pile (`libraryCardOf`) and into their hand — the bottom edge of their cell for you, the top edge for a seat across the table (`drawFlight`) — staggered when several land at once and capped per frame, and unpaced like the banners. `MAX_QUEUED_FRAMES` (4) is the catch-up valve for a backgrounded tab whose timers have been throttled. **Replay** (`usePlayback`'s `replay`, the ↺ button in the top strip): the last frame that had events is kept with the board it started from; replaying shows that board, then plays the frame through the same `runFrame` the live queue uses, without acking (the server already has its ack); a frame arriving meanwhile waits its turn. **Sound** (`game/sound.ts`, off unless the Animations panel's "Sound effects" is on): a few short cues synthesised with Web Audio — nothing to license or download — played from the same cues as the animations (`AnimationLayer`'s `soundFor`), each kind at most once per beat. **Arrows** (`ui/ArrowLayer.tsx`, rendered inside `Table`): a full-screen SVG drawn from the board's state rather than from events — the aimed stack entry's targets (the same entry `aim` marks: the top one, or the hovered one), each attacker to what it attacks (a player by their life total), each blocker to what it blocks — measured off the mounted board, again on resize and scroll; one that wasn't on the previous board draws itself in, so the arrows already standing don't redraw every frame. A target is pointed at only where the viewer's own board shows it — a permanent, a stack entry, a player at the table (`shownTargets`). While something resolves over the board (`resolve.resolving`), its dashed waiting arrows give way to `resolve` ones (`arrowSources`): solid, heavier, glowing in its controller's colour, shooting out from its entry along their length with the head (a sliver path of its own, so it waits for the line) and a flaring ring (`.arrow-impact`) landing on each target — well inside a card (`STRIKE_REACH`), at the edge of a life total as a waiting arrow does, so the number stays readable — a fade and a static head under reduced motion — and once it has resolved (`resolve.gone`) nothing points from it, though the old board still lists it; a frame resolving several things points from each in turn. The layer sits at z-index 21, above a board tile's 20 (`.board-entry > .mini-tile-wrap`, which lifts a host over its attachments: at 19, every tile a line crossed hid that stretch of it) and under the stack pile's 22. Where a line runs is `ui/arrowGeometry.ts` (pure, unit-tested): from edge to edge with a gentle bow (`between`), except from one stack entry to another — a Counterspell at the spell it counters, which lies beneath it in the pile, showing only as a strip — which leaves the entry's left edge, swings out round the left of the pile and lands on that strip (`stackLoop`), drawn in a second layer over the pile (`.arrow-layer.over-pile`, z-index 23): under it, the cards around both ends hid the whole line. A card peeling off a library (`runMill` → `peelCards`) shows its face when it was public knowledge at that event — `publicNameAt` over the frame's `publicStints`, so a milled card, a face-up exile or a cascade's miss since put back under the library all show, and a face-down exile never does. The face is the frame's own object when it's still that card, else one built from the card's definition (`peekCard`/`loadCard` + `defToVisible`), rendered as a `CardTile` into the peel with its own React root. It turns over as it lifts off, is held fanned out towards the screen's middle at a readable size (170px wide at least), then drops away darkening (milled) or flares off (exiled); `MILL_STEP_MS` is 1100 for it. Peels sit at z-index 10002, over the rest of the animation layer (a resolving spell's preview) and under the floating numbers (10003).

**Standing UI rules** (settled during the board redesign — see `client/BOARD_REDESIGN_PLAN.md`):

- **No fixed px.** Sizing is `clamp()`/`vw`/`vh`, derived from the shared `--card-w` token for anything card-sized — never a new hardcoded number.
- **`--card-w` is viewport-*width*-derived; cap it against height where height is the real constraint.** A card-shaped box inside a container whose height is a viewport fraction (the quadrants are roughly half of it) needs a height cap too, or it fits on a tall monitor and overflows a short one — the two scale independently, and `--card-w` sits at its 150px ceiling all the way down to a 1667px-wide viewport. `--card-w-max` is the ceiling and `--card-w` is what everything reads, so a height-constrained subtree narrows `--card-w` for itself against that ceiling (the command/library rail does exactly this: `.quadrant-body` is a `container-type: size` container and the rail caps at `32cqh`). That cap is set against the **commander slot alone**, because the library pile below it squashes to whatever is left rather than demanding a full card's height — stacking two full slots plus their labels needs about twice a card's height, which at 768px tall didn't fit at all (a 286px rail in a 269px quadrant, the library count clipped off every cell, and that overflow was what made the boards scroll). The rail also stretches to the quadrant's full height, so its seat-coloured divider runs down the whole board. Note that making `.quadrant-body` a size container also makes it the containing block for `position: fixed` descendants (`contain: layout`), which is why the board's hover popover has to leave the subtree entirely rather than just going fixed.
- **What a decision picks from the board is picked on the board**, never from a row of name buttons (two Forests, or two copies of one creature, are two identical buttons): the eligible permanents are highlighted and clicked, players by their panel (`PlayerPanel`'s `targetable`/`selected`). A `choose-from-zone` popup is titled by where the cards go (`zoneChoiceTitle` — `exile` for a graveyard-exile cost), and a choice that puts cards on the top or bottom of a library numbers its picks (`ZoneViewer`'s `selection.ordered`), the order picked being the order they go — an offer's `order` (library ordering: a scry's kept cards, "the rest on the bottom in any order") is titled as an order, the last pick lowest on the bottom; a discard with `orOneOf` takes one land card as an answer. A cast whose offer carries `divide` (Magma Opus) gets a division step once its targets are in (`pendingDivision`, mode `choose-division`): a `CountStepper` per target, at least 1 each, Cast enabled once they total the amount; `finishTargets` is a named function so the step's `resume` can call back into it with the split. Buttons are for what isn't on the board — "Copy nothing", "All mine", Confirm, and "Keep …" when choosing new targets for a copy of a spell (the `choose-targets` action's `current`: the slot's target now, which may no longer be on the board to click; the prompt reads "Choose new targets for the copy of …"). And **every decision but the mulligan asks in the bottom-right `.decision-banner`**; one that picks from the hand (discard, put-on-bottom, a reveal land's reveal) holds the hand tray open under it rather than docking beside the hand, which pulled the strip out of its tray and squashed the board.
- **Mana symbols always go through `<Symbols text={…} />`**, which renders `{…}` tokens as sliced-artwork pips with a CSS fallback. Never hand-roll a coloured circle.
- **Columns that must be equal need `minmax(0, 1fr)`, not `1fr`.** A bare `1fr` is `minmax(auto, 1fr)`, so a track whose content has a wide minimum (a row of input-plus-button, a long unbreakable word, an image) takes more than its share and its neighbour takes less. On the landing page that silently gave the join panel 414px against the start panel's 387 while the footer nav below, having no such pressure, split evenly and lined up with neither. The same footgun is why the seat grid and the board rows are written with `minmax(0, 1fr)` too.
- **A child that names its own width inside a padded box will escape that padding.** `.seat-board` at `min(1180px, 90vw)` inside a `.seat-board-box` at `min(1180px, 94vw)` overran the box's content area on a wide screen and pushed the outer seat panels out through its side padding. Let the box own the width and the child fill it (`width: 100%`).
- **The client's automated tests are a few vitest unit tests for pure logic** (`src/**/*.test.ts`, `npm test -w client`, part of the root `npm test`: the animation scheduler, board order, event wording, the card pool's load progress, `game/resolveAims.ts` and `ui/arrowGeometry.ts`) **and a Playwright smoke suite** (`client/e2e/`, `npm run test:e2e -w client`): the landing page, a 2- and a 4-player dev room at 1366x768, walking into combat, the library's and deck builder's card-loading bar (`pool-progress.spec.ts`), and exiling from the top of a library (`exile-from-library.spec.ts`: an impulse draw, a cascade and Ulamog's and Pako's exiles played in the EXILE / EXIL4 rooms, with the peels, floating totals and library counts sampled every animation frame, and the order and numbers of Ulamog's eight peels as they wait on bob's pile); `token-stack-counters.spec.ts` casts a token maker under Tribute to the World Tree in `TREES`/`TREE4` and checks the Warriors split off the stack end up one tile with their counters (it reads the engine through the `objects` command, and with `E2E_SHOTS_DIR` set saves screenshots at 1366x768, 1920x1080 and 2560x1440 and a frame sequence); and `resolve-arrows.spec.ts` (resolving arrows in the `ARRWS`/`ARRW4` dev rooms: landing on the right tiles and life totals and clear of the stack pile at three sizes, two targets, a Counterspell looping round the pile to the spell beneath it, an ability, two resolving in one frame, a bot's spell, reduced motion; `RESOLVE_ARROW_SHOTS=<dir>` films each resolution there), `e2e/put-down.spec.ts` (a resolving permanent spell put down on its tile in the `PUTDN`/`PUTD4` rooms at three sizes, sampled every animation frame: it starts at the stack, ends exactly on the tile — a tapped one too — the real tile isn't seen before the copy is on it, and the copy is gone straight after; `PUT_DOWN_SHOTS=<dir>` films each landing). It catches a page that no longer loads or a flow that no longer reaches its decision, not a layout that got worse, so verify any UI change live in the browser, in *both* a 2-player and a 3-4 player room, since the layouts diverge — **and at a short viewport (~768px tall), not just whatever monitor you're on.** Several severe layout bugs (every battlefield tile crushed to its 40px floor, the command/library rail overflowing its quadrant, the hand fan hanging off the bottom of the screen) were invisible at 1440p and obvious at 768p.

## Client commands, in full

- `npm run dev -w client` — Vite dev server with HMR (build `engine`/`server` first); needs a room server reachable at `ws://<host>:4000` (override with `VITE_SERVER_URL`)
- `npm run build -w client` / `lint -w client` / `preview -w client`
- `npm run test:e2e -w client` — the Playwright smoke suite (`client/e2e/`, config `client/playwright.config.ts`, CI `.github/workflows/e2e.yml`). It starts `dev-rooms` and the Vite dev server itself, or reuses them if they're already up, and resets each dev room it uses through the command port. `E2E_WEB_PORT`, `E2E_SERVER_PORT` and `E2E_CONTROL_PORT` move it off 5173/4000/4099 — set any of them and it never reuses a running server (which could be another checkout's), so parallel worktrees each run their own: `E2E_WEB_PORT=5273 E2E_SERVER_PORT=4100 E2E_CONTROL_PORT=4199 npx playwright test`. Build `engine`, `protocol` and `server` first. It runs one test at a time on purpose: a dev-rooms `reset` drops every open connection, not just that room's. `@playwright/test` is pinned to the version whose Chromium the cloud sessions' image ships; elsewhere run `npx playwright install chromium` once.
- To watch it run by hand: start a room server, then `npm run dev -w client` and open two tabs/devices to the same room code.
