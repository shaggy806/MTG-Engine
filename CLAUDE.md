# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

MTG-Engine is a Magic: The Gathering rules engine (`engine/`) with an authoritative multiplayer
room server (`server/`) and a React web client (`client/`) — a real networked 2-4 player game
(Commander-capable), not a local hot-seat demo. The repo is an **npm workspaces monorepo**
(`workspaces: ["engine", "server", "client"]` in the root `package.json`, in that order so
`engine` builds first, then `server`).

**Where the docs live.** This file is a map of *current architecture* — not a changelog. The
others, and what each is for:

- **`ROADMAP.md`** — the engine's build history, condensed. Its 11 phases and the follow-on
  "needed-cards" P0–P20 passes are **all done**; ~180 source comments cite "ROADMAP Phase N", so
  the phase index stays. **Read its *Architecture constraints* section before touching the
  engine.** Per-phase narrative detail is in `git log`, not here.
- **`engine/src/cards/neededCards-features.md`** — the plan of record for *new* engine work: an
  EDH-popularity-driven backlog (from `top-commander-cards.txt`/`top-commander-cards-flagged.txt`,
  the top 2000 Commander cards by EDHREC rank cross-referenced against the pool) ranking features
  by how many real cards each would unblock, plus a compact P0–P20 index. The pool is 280+ cards.
- **`engine/src/cards/AUTHORING.md`** — the hand-authoring guide for adding a card. Read before
  authoring.
- **`DEPLOYMENT.md`** — the tobyens.com production hosting/update runbook.
- **`docs/plans/*.md`** — design records for four shipped client/server features (bots,
  card-library page, deck builder, card replacer). Each says *why* its architecture is shaped the
  way it is; all four are marked implemented and are not living documentation. A fifth feature
  from that program — server-side deck save/share — is still unscoped.
- **`client/BOARD_REDESIGN_PLAN.md`** — the board-overhaul record: the mockup URL, the settled
  design rules, and the two known gaps. All 18 phases shipped.

- `engine/` — a TypeScript library package, ESM (`"type": "module"`), NodeNext resolution. Emits to `dist/` with declarations; `package.json` `exports`/`main`/`types` point there. No I/O, no UI — a pure state machine driven entirely through `dispatch`.
- `server/` — a Node + `ws` package: the authoritative multiplayer room host. Owns the one real `Game` instance per room, keyed by a room code; every connected device gets its own redacted `viewFor(seat)` pushed after each dispatch. Imports `engine` the same way `client` does.
- `client/` — a Vite + React 19 + TypeScript app: a **networked** client — each device is one seat, connected over WebSocket to a `server` room, never running a local `Game` or a controller loop itself. Imports `engine` (`"engine": "*"`, the workspace symlink) and consumes only its public seam — `Game`, `viewFor`, `legalActions`, `dispatch`, the `Action`/`LegalAction` types — indirectly, via the wire protocol `server` speaks. Needs `engine/dist/` built (`npm run build` does engine, then server, then client).

## Engine architecture (`engine/src/`)

### What's implemented

Full turn/step loop, casting + targeting + fizzle, a LIFO stack, SBAs, full combat (first
strike/double strike/trample/deathtouch/lifelink/menace, multi-blocker damage assignment as a
player choice, a first-strike priority window, must-be-blocked), activated/triggered abilities
(intervening-ifs, `{X}` costs, loyalty abilities), the full continuous-effects layer pipeline
(1 copy, 2 control, 3 text, 4 type-change, 5 colour, 6 keywords/ability-loss, 7 P/T incl. a CDA
layer), tokens (with a `stackCount` compaction scheme so a self-replicating generator can't blow
up object count — see "Token stacking" below), Auras & Equipment, Commander (command-zone casting
with tax, 903.9a replacement as an owner's choice, commander damage, Partner, the legend rule),
an opt-in simultaneous-mulligan phase, 2-4 player tables (APNAP ordering, per-defender blocker
declarations), a full replacement-effects pipeline (`replacements.ts`), modal/"you may"/targeted-
modal spells, mass effects (wraths, edicts) and tutors/scry/surveil, a rich effect vocabulary
(bounce/exile/mill/discard, fight, counter, control-change, clone, animate, text-change,
count-scaled and trigger-supplied amounts, token-for-target and token-copy effects, conditional
effects, sacrifice costs incl. filtered ones, additional costs & kicker), planeswalkers, alternate
casting zones (flashback, suspend, foretell, escape, disturb, adventure, MDFCs, transforming DFCs
+ Day/Night, Channel from hand, Overload, a conditional free-cast permission, Convoke), extra
turns/combats, cascade/storm/spell-copying, Sagas, the Monarch/Energy/Emblems, damage-prevention
shields, and a color-identity-aware Commander deck validator (`identity.ts`, `deck-validation.ts`).

**Every player decision is a dispatched action**, never a synchronous controller callback —
`declare-attackers` / `declare-blockers` / `order-blockers` / `assign-combat-damage` / `discard` /
`choose-from-zone` / `mulligan` / `put-on-bottom` / `commander-replacement` /
`pay-life-for-untapped` / `choose-copy` / `choose-text` / `choose-modes` / `choose-targets` /
`sacrifice` / `scry` alongside the priority actions. `legalActions(player)` enumerates what's
playable right now with per-slot target options; `viewFor(player)` produces a redacted,
self-contained snapshot for one seat.

**Not modeled** (see ROADMAP for the full deferred list): Battles, phasing, dungeons/Initiative/
Ring, banding, Backgrounds/Companion, multi-replacement ordering (`choose-replacement-order`),
damage redirection to a third object, dependency ordering between static effects, a player choice
on which same-named legendary permanent the legend rule keeps (deterministic — oldest survives),
full text-change beyond a single creature-type word, snow *sources* (snow mana is generic today).

**Token stacking** (an engine resource-safety mechanism, not a rule — added after the fuzzer hung
on a self-replicating-token card): `GameObject.stackCount` lets one object stand in for many
fully interchangeable, still-pristine token copies instead of minting one object per copy.
`Game.mintTokenBatch` folds new batches into a matching existing stack; a fresh batch only
originates a stack past `STACK_ORIGIN_THRESHOLD` (8), so ordinary "create two tokens" cards are
untouched. Only tokens with no activated ability and only count-scalable, non-targeted triggered
abilities are ever stacked (`Game.isStackableTokenName`). `Game.splitOneFromStack` peels one off
into an ordinary object the instant anything singles it out (targeted effects, a chosen
sacrifice); `Game.materializeStack` expands a whole stack into real objects for combat (capped at
`MAX_MATERIALIZED` = 100 — attacking/blocking are optional, so declaring a legal subset is
allowed); `recompactTokens` (end of cleanup) folds untouched tokens back into stacks. See
`token-stacking.test.ts` and `random-demo.mjs` for the original repro.

### File map

Tests live in `engine/src/test/*.test.ts` (one directory level deeper than the source they cover,
so relative imports need an extra `../`), except `cards/pool.test.ts`, which stays colocated with
the `cards/pool/`/`cards/tokens/` layout it guards. `server/src/test/*.test.ts` mirrors this. No
`vitest.config` — default glob discovery finds them wherever they are; `tsconfig`'s
`src/**/*.test.ts` exclude already covers the subdirectory.

- **`state.ts`** — `GameState` is one plain, `structuredClone`-able tree (no class instances, `Map`/`Set`, or functions inside it). Holds `rules` (`startingLife`, `openingHandSize`, `maxHandSize`, `maxLandsPerTurn`, `skipFirstDraw`), players, `objects` (card/ability instances — `GameObject.kind` `"card"`|`"ability"`, `abilityKind` `"activated"`|`"triggered"`|`"chapter"`, `counters`, `modifiers`, combat fields — all cleared by `moveObject` on any zone change), `zones` (`perPlayer` library/hand/graveyard + `shared` battlefield/stack/exile/command as ordered `ObjectId[]`; stack top = last), `turn`, `priority`, `result`, `awaiting` (a discriminated `AwaitingDecision` union — one variant per decision kind listed above, each carrying whatever context that decision needs, e.g. `assign-combat-damage {attacker, blockers, power, lethal, trample}`, `mulligan {player, hands}` where every player still deciding may act at once, `commander-replacement {commander, intendedZone}` raised *before* the move), plus a grab-bag of pending-decision queues (`pendingBlockerOrders`, `pendingBlockerDeclarations`, `pendingTriggers`, `pendingTargetedTrigger`, `pendingTargetedCast`, `pendingSuspendedCasts`, `deferredCommanderMove`, `pendingDestruction`, `pendingSacrifices`/`pendingSacrificeVictims`) that let a mass effect or multi-step decision resume correctly after a player answers something mid-resolution, turn-scoped state (`preventAllCombatDamage`, `preventionShields`, `combatDamage`, `extraTurns`, `extraCombats`, `spellsCastThisTurn`, `dayNight`, `monarch`, `emblems`), and `eventLog`. `PlayerState` carries `energy`, `commanderCastCounts` (per-commander tax, Partner-aware), `commanderDamageTaken`, `spellsCastThisTurn`. `GameObject` carries the full set of per-permanent flags the layer/effect system needs: `markedByDeathtouch`, `summoningSick`, `loyaltyActivatedThisTurn`, `attacking` (`PlayerId | ObjectId`), `isToken`, `attachedTo`, `isCommander`, `controlEndsAtCleanup`, `copyOf`, `faces`/`face` (multi-face cards — `faceName(object) = faces[face]`, `printedCardName(object) = copyOf ?? faceName(object)` is what every characteristic/ability read goes through), `modifiers` (a `PtModifier[]` spanning layers 3–7d), `xValue`, `chosenModes`, `kicked`, `castVia` + the alt-zone markers (`grantedFlashback`, `suspended`+`counters.time`, `hastyUntilItLeaves`, `foretold`+`foretoldOnTurn`), `isCopy`, `stormCount`, `onAdventure` — all cleared by `moveObject` on any zone change unless noted otherwise. Also exports pure selectors.
- **`game.ts`** — `Game` owns the single mutable `GameState` and is the **only** writer. `dispatch(action)` handles every `Action` variant (see `actions.ts`). Multi-blocked attackers queue in `pendingBlockerOrders`; a 3-4 player table queues attacked defenders in `pendingBlockerDeclarations`, drained one `declare-blockers`/`order-blockers` at a time. `legalDefenders(attacker)` returns every non-eliminated opponent plus their planeswalkers. `advance()`/`advanceUntil(pred)` run `tick()`. `emit()` appends an event and runs `detectTriggers` (matches against every battlefield permanent's `triggered` list, honouring intervening-ifs via `interveningIfMet`). `prepareForPriority(player)` is the pre-priority fixpoint loop: run SBAs, drain pending mass-effect/sacrifice queues, place pending triggers (APNAP order) — repeat until stable, then hand off priority (to `awaiting.player` if a decision got raised mid-loop). Mana is **auto-paid**: `manaSources` reports each permanent's `{T}: Add` abilities as `ManaOption` alternatives → `Game.payMana` = `resolveHybridCost` (hybrid/twobrid/Phyrexian → concrete cost + life) → `planManaPayment` (a greedy solver) → `executePayment` (taps/sacrifices sources, spends the pool, pays life); `castingCostOf` folds in commander tax and `costModification` statics. `payMana`'s last two arguments are the difference between a preference and a rule: `avoid` puts a source last (don't casually tap a permanent for its own ability's mana cost), while `exclude` removes it outright — an ability whose cost includes `{T}` taps its source to pay that, so it can't be tapped for mana as well (rule 602.2a). Without the latter, Mind Stone's `{1}, {T}, Sacrifice` funded its own `{1}` off an otherwise empty board. Ability objects are minted onto the stack by `mintAbilityObject` and deleted from `state.objects` on resolution. All P/T reads go through `characteristicsOf`. Combat damage runs through `combatDamageStep` → `runCombatDamageSubPass` (first-strike sub-pass, then regular, each followed by SBAs + a priority window when relevant) → `dealCombatDamage`, which takes a player-chosen `assign-combat-damage` split when one exists, else auto-assigns lethal down `blockedBy`; `dealDamage` runs deathtouch/lifelink, prevention shields, and Fog uniformly (for combat and burn alike) and returns the amount actually dealt. `createTokens`/`addCounter`/`entersBattlefieldReplacement` all honour replacement multipliers (Doubling Season). `moveObject` is the single zone-transition function: it applies enters-battlefield replacements, defers a commander's leave-the-battlefield move behind a `commander-replacement` decision (903.9a), redirects a graveyard-bound card to exile when a replacement or `castVia` says to, resets face/copy/modifier state on any move to a hidden zone, and emits `permanent-left-battlefield`/`permanent-destroyed` as appropriate. `runStateBasedActions` recomputes control (layer 2), sweeps fallen-off Auras, deletes dead tokens, enforces the legend rule and commander-damage loss, and sacrifices 0-loyalty planeswalkers / completed Sagas. `castSpell`/`activateAbility`/`whyCannot*` thread through `via` (alt cast zone), `face` (multi-face cards), `xValue`, `kicked`, `sacrifice` (additional/ability costs), and evaluate `costModification`/`ward`/protection/`StaticAbility.condition` gates. `castCardWithoutPaying` is the shared free-cast core for suspend/cascade. A triggered ability or suspended spell needing a real target choice parks in `pendingTargetedTrigger`/`pendingTargetedCast` and raises a `choose-targets` decision rather than picking synchronously.
- **`actions.ts`** — the `Action` union: the priority actions, plus `declare-attackers`/`declare-blockers`/`order-blockers`/`assign-combat-damage`/`discard`/`choose-from-zone`/`mulligan`/`put-on-bottom`/`commander-replacement`/`choose-copy`/`choose-text`/`choose-modes`/`choose-targets`/`sacrifice`/`scry`/`suspend`/`foretell`/`cycle`. `cast-spell` carries optional `xValue`, `via?: CastVia` (`"flashback"|"escape"|"foretell"|"disturb"|"adventure"|"suspend"|"cascade"`), `face?`, `modes?`, `kicked?`, `overload?`, `free?` (a `CardDefinition.freeCastIf` permission), `convoke?: ConvokePayment[]`, `sacrifice?` (an additional cost); `activate-ability` carries optional `sacrifice`, `xValue`. `LegalAction` mirrors this — a castable/activatable option carries whatever context the client needs to build the action (`xCost: {maxX}`, `sacrifice: {choices}`, `castModal {...}`, `mustBlock`, etc.), and a card playable multiple ways (kicked/unkicked, multiple faces, via different alt-zones) is enumerated once per variant. Kept out of `game.ts` to avoid a cycle with `controller.ts`.
- **`view.ts`** — `viewFor(state, registry, viewer, opts)` / `game.viewFor(player)` → a `PlayerView`: your hand in full, other hands as counts, libraries as counts (except what a pending `choose-from-zone`/`scry` reveals to that player), battlefield/stack/graveyards public with **computed** characteristics baked in (power/toughness/keywords/types/subtypes/colors/restrictions/loyalty/`isToken`/`attachedTo`/`isCommander`/`xValue`/`copyOf`/`suspended`/`foretold`/`faceName`+`faces`/`stackCount`/`art`), so a client needs neither the registry nor the layer system. A foretold card in exile is redacted for everyone but its owner. `PlayerView` also carries `startingPlayer`, `dayNight`, `monarch`, `emblems`; `PublicPlayerInfo` carries `energy`, `commanderDamageTaken`, `commanderCastCounts`. `{ revealAll: true }` for a spectator/debug view. `art` is where a deck's **chosen printing** surfaces: `DeckList.printings` (card name → Scryfall card id) is stored at setup on `PlayerState.printings` and substituted here for the card's *owner*'s objects, so every device at the table draws the card its owner brought. Player-level, not per-`GameObject`, because it's a fact about the physical cards someone owns rather than any game state — so it survives zone changes and control changes for free. Skipped for a turned-over back face (`isCardFront`): a card id addresses the whole card and serves its front image, so honouring it there would show the wrong face.
- **`turn.ts`** — `Phase`/`Step` string-literal unions (no `enum`), `TURN_SEQUENCE`, `nextStep`, `stepUsesPriority` (false only for untap/cleanup), `isMainPhase`.
- **`events.ts`** — a discriminated `GameEvent` union (the audit log) covering every state change the engine makes — zone moves, damage, triggers, decisions, alt-cast events, combat, replacements, etc. Both log formatters (`scripts/format.mjs`, `client/src/format.ts`) render them; check there when you need the exact shape of a specific event.
- **`cards.ts`** — a thin re-export barrel; the real content lives in `cards/`: `cards/define.ts` (`CardDefinition`/`CardDraft` + `defineCard`/`hasKeyword`), `cards/helpers.ts` (`basicLand`, `manaTapAbility`, `addManaAbility`, land-toolkit builders — `entersTappedStatic`, `checkLandStatic`, `painLand`, `fetchLand`, `trikeland`, `shockLand` — `landProduces`), `cards/registry.ts` (`CardRegistry`, `createDefaultRegistry`), one file per card under `cards/pool/` (real cards + basics) and `cards/tokens/`. `CardDefinition` is **declarative** (`effect`, `keywords`, `activated`, `triggered`, `static: StaticAbility[]`, `supertypes`, `loyalty`, `chapters` for a Saga, `faces` for a multi-face card, `transform`/`disturb`/`adventure`/`suspend`/`foretell`/`flashback`/`escape`/`cycling`/`castModal`/`kicker`/`overload`/`freeCastIf`/`convoke`/`selfCostReduction`/`additionalCost`/`cantBeCountered`/`art`) with an imperative `resolve(ctx)` hatch. `cards/generated.ts` is the codegen'd barrel (`npm run gen:cards -w engine`, also a `prebuild`/`pretypecheck` step, checked in) — **to add a card, drop a new file in `cards/pool/` and run `gen:cards`**. It emits `POOL_CARDS` and `TOKEN_CARDS` as well as the combined `BUILTIN_CARDS`, because the directory is the only record that a definition is a *token* — nothing on `CardDefinition` says so. `cards/classify.ts` reads them back as `isTokenCard` (rule 111.1 — a token isn't a card), `isCardFront` (rule 712.3 — a DFC is one card, deck-listed under its front face) and `isDeckableCard` for the two together; `deck-validation.ts`, `card-replacer.ts`, the library page and the deck builder's pool all filter on these rather than guessing from the name. `cards/pool.test.ts` fails if a card isn't wired into `generated.ts`, or if the pool/tokens split drifts. **`cards/AUTHORING.md` is the hand-authoring guide** — every field, the effect/target/ability/static vocab, worked examples, current limitations; read it before authoring a new card. `engine/src/sandbox.ts` — `createSandbox(cardName)` builds a solo `Game` with the card in hand/battlefield, lands, and target fodder for the card lab; `Game.debugSpawn(name, player, zone)` is the sanctioned white-box "put a card straight into a zone" helper, going through the real `moveObject`.
- **`identity.ts`** — `colorIdentityOf(def)` (rule 903.4 — a lexical `{…}`-symbol scan of the mana cost + all rules/ability text) + `withinIdentity`/`identityString`. Consumed by `deck-validation.ts`.
- **`deck-validation.ts`** — `validateCommanderDeck({commanders, cards, size}, registry)` → `{legal, violations, identity}`: singleton (basics exempt), colour identity, deck size, legendary commander(s), Partner-for-two-commanders, and "is actually a card" (`cards/classify.ts` — a token or a DFC back face is a registered definition and would otherwise pass every other check). Only checks *implemented* cards. Lives in the engine (it originated in `server/`) because it's pure synchronous logic over `CardRegistry` data — the client's deck builder needs the same rules with no network round-trip.
- **`sample-decks.ts`** — `SAMPLE_DECKS`: four hand-curated, differently-themed 60-card decks showing off a broad slice of the pool. Deliberately *not* format-legal (colour identity ignored, 60 cards not 100). One source of truth for two consumers: `server/src/decks.ts`'s `SEATS` (a seat's fallback deck) and the client deck builder's "starter decks".
- **`card-replacer.ts`** — `suggestReplacement({manaCost, typeLine})` → the closest implemented `BUILTIN_CARDS` name, for the decklist-import flow. Pure and synchronous; scores against the *unimplemented* card's Scryfall type line + mana cost (all that's available without a `CardDefinition`). Hard-filters on a shared primary type, then scores mana-value distance, type-shape and colour mismatch, with a shared subtype as tiebreaker. Deliberately a similarity proxy, not a rules computation — an off-identity suggestion still surfaces normally in `validateCommanderDeck`. Also exports `parseTypeLine`.
- **`filter.ts`** — `CardFilter` + `matchesFilter(state, registry, id, filter, { you })`: a pure predicate over an object + its *computed* characteristics (`type`/`types`/`notTypes`/`subtype`/`subtypes`/`supertype`/`name`/`colors`/`notColors`/`colorless`/`manaValue`/`power`/`toughness`/`controlledBy`/`ownedBy`/`keyword`/`tapped`/`token`, ANDed). Off the battlefield it degrades to printed values. The shared "which objects" vocabulary for mass effects, tutors, and filtered triggers — `ZoneChoiceFilter` is an alias. Answers type/subtype/colour clauses lazily via the self-contained `effectiveTypes`/`effectiveSubtypes`/`effectiveColors`; only a `power`/`toughness`/`keyword` clause needs the full characteristics fold (kept cheap deliberately — a `StaticAbility.condition` re-runs `matchesFilter` over the whole battlefield on every read).
- **`replacements.ts`** — `ReplacementSpec` (rule 614/616), a discriminated union on `StaticAbility.replacement`: `enters-battlefield { tapped?, tappedUnless?, counters?, transformed? }`, `would-create-token { multiplier }`, `would-add-counter { multiplier, counterKind? }`, `would-be-put-into-graveyard { instead: "exile", filter? }`, `would-draw { who: "opponent", instead: "you-draw" }`. Not modeled: multi-replacement ordering, damage redirection to a third object.
- **`abilities.ts`** — `ActivatedAbility` (`cost: {mana, tap, sacrifice?, payLife?, removeCounter?, payEnergy?}`, `sacrifice: "self" | "creature-you-control" | {filter: CardFilter}`, optional `sorcerySpeed`, optional `loyaltyCost`, optional `zone: "hand"` (Channel — activatable only from hand, discarding the source as an implicit cost) and `costReduction` (a live-count discount printed on the ability itself, mirroring `selfCostReduction`); `mana` may contain `{X}`). `TriggeredAbility` (`trigger: TriggerSpec` — `enters-battlefield`/`dies` (with `filter?`/`otherOnly?`), `leaves-battlefield`, `gains-life`, `loses-life {who}`, `attacks`, `sacrifice {who}`, `deals-combat-damage-to-player`, `step-begins {step}`, `cast-spell {who, noncreatureOnly?, firstEachTurn?}`, `this-cast`, `transforms {who, intoFront?, filter?}`, a `predicate` escape hatch; optional `condition?: StaticCondition` — an intervening-if, rule 603.4). `StaticAbility` also carries `restrictions: CombatRestriction[]`, `ward {mana?, payLife?}`, `costModification {applies, reduceGeneric?, increaseGeneric?}`, `protection {colors?, types?}`, `grantsActivated: ActivatedAbility[]`, `condition?: StaticCondition` (`controls {filter, atLeast}` / `opponent-controls {filter, atLeast}` / `your-turn` / `threshold` / `metalcraft`). `isManaAbility` permits a `sacrifice: "self"` or `payLife` cost, excludes `removeCounter`/loyalty/a non-self sacrifice.
- **`effects.ts`** — the `EffectSpec` vocabulary: `sequence`, `damage`/`draw`/`modify-pt`/`modify-pt-all`/`create-token`/`create-token-copy` `count` fields accept an `EffectAmount = number | "x" | {countOf: CardFilter} | {triggerValue: true}`; `add-mana` (`+ painToController?`), `gain-life`/`lose-life`, `tap`/`untap`/`untap-all`, `destroy`/`destroy-all`, `damage-all`, `fight {a, b, oneSided?}`, `counter {target}`, `gain-control {target, untilEndOfTurn}`, `return-to-hand`/`return-to-hand-all`/`exile`/`exile-graveyard`/`mill`/`return-from-graveyard`/`discard`, `grant-keyword`/`grant-keyword-all`, `add-counter`/`proliferate`, `double-counters-all`/`double-pt-all` (a one-shot doubling effect reading each matching permanent's own current count/P-T, distinct from Doubling Season's replacement-based multiplier), `animate {target, power, toughness, addTypes, addSubtypes, setSubtypes?, setColors?, loseAbilities?, keywords?, duration}`, `change-text`, `grant-flashback`, `take-extra-turn`/`additional-combat`, `storm`/`cascade`/`copy-spell`, `create-token {token, count, who?: "you"|"target-controller"}`, `create-token-copy {of: "source"|"trigger-object"|slot, count, gainsHaste?, exileAtEndStep?, notLegendary?, basePt?}`, `conditional {condition, then, else?}`, `attach`, `transform`/`day-night`, `become-monarch`/`get-energy`/`create-emblem`, `prevent-all-combat-damage`/`prevent-damage`, `modal {minModes, maxModes, modes}`/`may {effect, prompt}` (non-targeted only — a targeted modal spell uses `CardDefinition.castModal` instead), `sacrifice {who, filter, count, exceptSource?}`, `sacrifice-source {then?}`, `search-library`, `scry`/`surveil`, `look-and-choose`. `EffectApi`/`ResolutionContext` (`ctx.x`, `amountValue`), `applyEffectSpec`.
- **`characteristics.ts`** — `computeCharacteristics(state, registry, id)` folds printed → layer 3 (text substitution) → layer 4 (type/subtype changes) → layer 5 (colour) → layer 6 (keyword grants/ability loss) → layer 7b (a `setBasePtFromCount` CDA, then `animate`'s `setPt`) → layer 7c (counters) → layer 7d (P/T grants/modifiers), timestamp-ordered. `Characteristics.restrictions`/`.protectionFrom` collect `StaticAbility.restrictions`/`.protection`. `staticAffects` resolves an `AffectSpec` scope (`"self"`/`"creatures-you-control"`/`"lands-you-control"`/`"attached"`, lord `subtype` clauses). Layer 1 (copy) is handled upstream via `printedCardName`. `staticConditionMet(state, registry, source, condition, opts?)` evaluates a `StaticAbility.condition` gate, checked *after* `staticAffects` confirms reachability, with a re-entrancy guard for mutually-conditional permanents. Dependency ordering between static effects is not implemented.
- **`target.ts`/`targeting.ts`** — `TargetRef` (player or object) and `TargetSpec` (`"any-target"`/`"creature"`/`"nonblack-creature"`/`"creature-you-control"`/`"creature-an-opponent-controls"`/`"player"`/`"opponent"`/`"creature-or-player"`/`"permanent"`/`"nonland-permanent"`/`"nonland-permanent-an-opponent-controls"`/`"land"`/`"artifact"`/`"artifact-an-opponent-controls"`/`"artifact-or-enchantment"`/`"artifact-enchantment-or-nonbasic-land-an-opponent-controls"`/`"creature-or-enchantment"`/`"attacking-or-blocking-creature"`/`"spell"`/`"creature-spell"`/`"noncreature-spell"`/`"instant-or-sorcery-in-your-graveyard"`/`"instant-or-sorcery-spell"`). `isLegalTarget`/`legalTargets` take a `forPlayer` and an optional `TargetSource` (`{colors, types}`), and enforce protection (`protectionBlocks`, also used by `dealDamage`/`whyCannotBlock`/`attachPermanent`). Checked on cast and again at resolution (all-illegal ⇒ fizzle).
- **`mana.ts`** — `Color`/`ManaType`/`ManaPool`, `parseManaCost` (generic, `{X}`, `{C}` colorless, hybrid `{W/U}`, twobrid `{2/W}`, Phyrexian `{W/P}`, snow `{S}` folded into generic), `manaValue`, `poolTotal`.
- **`controller.ts`** — `PlayerController.act(view)` is the single entry point: when `view.state.awaiting` is set it must return that declaration, otherwise any legal priority action. `AutomaticController` always passes/keeps its hand. `ScriptedController` plays a queue plus assignable `*Fn` callbacks (what tests use). `RandomController` picks uniformly from `legalActions()` — the engine's fuzzer (see `random-demo.mjs`). `HeuristicBotController` extends `AutomaticController` with a v1 "plays a sensible game, not a good one" policy (land first, else the highest-mana-value affordable spell, else a **non-mana** ability, else pass; attack with every eligible creature at the lowest-life defender; block favourable trades and chump-block lethal), owning its own `CardRegistry` so it can read mana values and computed P/T. Mana abilities are never activated on their own (`isManaOnlyAbility`): casting auto-pays, so floating mana gains nothing, strands the source, and — once bot moves are paced out one at a time — shows up as a land flipping sideways for no reason between a spell being cast and that spell resolving. It's what fills a bot seat in a live room — see `server/src/room.ts`. `engine/src/test/heuristic-bot.test.ts` runs bot-vs-bot games to completion as a second fuzz target.
- **`primitives.ts`** — branded `PlayerId`/`ObjectId`, seeded `Rng` (mulberry32), `shuffle`.
- **`auto-settle.ts`** — `isSettled(state)` / `autoSettle(game)`: cascades past every "dead" priority window in one go. `Room` uses `isSettled` as its per-hop predicate but deliberately never `autoSettle` — it has to stop at every bot action to publish a frame, and per-seat auto-pass/skip-mana-only are one-shot-per-call, neither of which survives a cascade. `autoSettle` itself is now only used by tests/scripts that want a game settled in one call.

Snapshot/restore: `game.snapshot()` → `structuredClone(state)`; `Game.fromSnapshot(snap, env)` rebuilds (re-supply `registry`/`controllers` via `env`). Determinism: same seed + same controllers ⇒ identical replay.

## Server architecture (`server/src/`)

The authoritative multiplayer host. One process can run many rooms; each room owns exactly one
real `Game` and pushes every connected seat its own `viewFor` after each settle. Transport-agnostic
at the `Room` level (a `Connection` is just "something we can push a `ServerMessage` to"), so it's
unit-testable without a real WebSocket — `ws-server.ts` is the only place that touches `ws` itself.

A room has **two lifecycle stages**, because a seat's deck isn't known until whoever claims it
connects (the deck builder sends it with `claim-seat`) and `Game.create` shuffles and deals
immediately for every seat: a `PendingRoom` (a code, seat claims, no `Game`) is **promoted** into a
real `Room` the moment every seat is claimed or bot-filled.

- **`room.ts`** — `Room` wraps one `Game` plus a `Seat` per `turnOrder` entry (`clientToken`, `connection`, `autoPassUntil`, `skipManaOnly`, `displayName`, `ackedSeq`/`acksFrames`). `claimSeat(player, clientToken, connection, displayName?)` binds a connection to a seat — a token mismatch is rejected even while offline, the same token reclaims it. `addBot(player)` fills an open seat with a `HeuristicBotController` (rejecting a seat already claimed or botted); `seatStatuses()` reports `isBot`. `dispatch(connection, action)` forwards to `Game.dispatch` then calls `settle()`, which auto-passes dead priority windows / mana-only windows / whole turns per-seat, one stopping point at a time (built on `isSettled`, deliberately not `autoSettle` — see `auto-settle.ts`). **Bots live in `settle()`**, not in `Game`'s `config.controllers` (`nextBotDecider` is seat-by-seat across `awaiting.hands` for the parallel mulligan, otherwise the single `awaiting.player`), so a mixed bot/human table composes for free.
  **Frames and the animation gate.** Every push is a numbered **frame** (`publish()` bumps `seq` and calls `onUpdate`; the transport fans it out, and `seq` travels on the `state` message). A bot used to take its whole turn inside one `settle()` call, so clients only ever saw the board *after* all of it and played the arrival animations over an outcome already on screen — a land shown flying in was already tapped for the spell after it. Now `settle()` stops at each bot action: it publishes a frame, parks the move behind `holdForClients`, and releases it once every *acking* seat reports finishing that frame (`ack(connection, seq)`) and `BOT_MIN_THINK_MS` (350ms) has passed, with `FRAME_ACK_TIMEOUT_MS` (6s) as a backstop for a seat that has gone quiet. A seat that has never acked never gates anything, so no client can deadlock a room; a disconnect re-checks the gate. A bot move nobody could watch is dispatched without a frame — a plain `pass-priority`, or any window where `isDeadForMana` says passing and tapping for mana are the only options. That isn't just tidiness: a beat spent on one of those lands *between* a spell being cast and that spell resolving, which is what made a creature seem to arrive long after its own play animation had finished. Whatever the move lets through is paced in the next frame. `RoomOptions.pacing: "immediate"` opts out of all of it (bots run to completion, one push at the end) and is what tests and scripts use; `RoomOptions.timers` swaps in a fake clock. `dispose()` drops a parked move's timers.
- **`pending-room.ts`** — `PendingRoom`: the same seat-claiming bookkeeping as `Room` (claim/reclaim semantics, `addBot`, `connectedSeats`, idle tracking) with no `Game`, no dispatch, no settle. `claimSeat(..., deck?)` stores the seat's deck, falling back to its positional starter deck from `decks.ts` so a bare room-code link still works. `isReady()` = every seat claimed or bot-filled; `toGameConfig()` assembles the `DeckList[]` and rolls the starting player (the "highroll") *at promotion time*, since turn order isn't settled before then. Deliberately a separate class, not a nullable-`game` variant of `Room`. **The table is also sized here, not at creation**: `addSeat()`/`removeSeat(player)` grow and shrink it between 2 and `SEATS.length`, which is what the seat board's add/remove controls drive. `addSeat` takes the first unused `SEATS` entry and re-sorts, so the seat array stays in printed seating order however the table was assembled — turn order comes straight off that array, and must not depend on the order seats were added. `removeSeat` refuses a seat a human has claimed (leaving is that player's own call) but allows an open or bot-filled one, on the same "anyone in the room" reasoning as `addBot`.
- **`room-manager.ts`** — `RoomManager.createPending(players, config)` mints a room code and a `PendingRoom`; `promote(id)` builds the real `Game`/`Room` for a ready one (wiring its `onUpdate` to the manager's own `onRoomUpdate`), replays its connected claims and bot fills onto it, then `room.start()` settles it to the first real decision and publishes the opening frame. `get(id)` returns a `Room | PendingRoom`. `reapIdle(maxIdleMs)` disposes and drops abandoned rooms. No player-count assumption.
- **`ws-server.ts`** — `attachRoomServer(wss, manager)` wires a `WebSocketServer` to a `RoomManager`: parses messages as `ClientMessage`s, dispatches to the matching `Room`/`PendingRoom`/`RoomManager` call, pushes `ServerMessage`s back. **`broadcast` is never called from a message handler** — a room publishes its own frames on its own clock now (one per bot action), so it's wired up as `manager.onRoomUpdate` and as `room.onUpdate` on any room `requireRoom` is handed, and anything wanting a push calls `room.publish()`. That second binding is what keeps the hand-built-`Room` `scratch.mjs` pattern working without a real `RoomManager`. `create-room` clamps `players` (2-4, default 2) — the client always takes the default now and sizes the table from the seat board instead, so that parameter is for scripts and tests. `add-bot` mirrors `claim-seat`'s error shape and also sends a direct `room-joined` refresh, since the caller may not hold a seat yet and so isn't in `connectedSeats()`; `add-seat`/`remove-seat` need the same follow-up for the same reason, and are pending-room-only (`requirePendingRoom`) because a promoted room's turn order is already dealt. `ack` is exempt from the per-IP rate limit (it's automatic traffic, one per frame shown, with no effect beyond releasing a bot).
- **`protocol.ts`** — the wire protocol, duplicated (not imported) in `client/src/net/protocol.ts` — keep the two in sync by hand. `ClientMessage`: `create-room {seed?, players?}`, `join-room`, `claim-seat {seat, clientToken, displayName?, deck?}`, `add-bot {seat}`, `set-bot-deck {seat, deck}`, `add-seat`, `remove-seat {seat}`, `set-ready {ready}`, `start-game`, `dispatch {action}`, `pass-turn`, `auto-pass`, `toggle-mana-skip`, `ack {seq}`. `ServerMessage`: `room-created`, `room-joined {seats}`, `state {seq, seat, view, actions, seats, autoPassing, skipManaOnly}`, `error`. A `WireDeck` carries `cards`/`commander`/`name`/`printings`. `SeatStatus` carries `claimed`/`online`/`displayName`/`isBot`, and its `deck` carries `commanderPrinting` — just the one card, since the seat board only draws the commander; the whole map rides with the deck itself. Doesn't cover `/import-deck` (a plain HTTP route, not a WS message).
- **`decks.ts`** — `SEATS: SeatDeck[]`, up to four named seats (`ALICE`/`BOB`/`CAROL`/`DAVE`) in seating order, sliced by `create-room`'s `players` count — a seat's fallback deck when nobody brought their own. The deck contents come from `engine`'s `SAMPLE_DECKS`.
- **`import-deck.ts`** — the decklist-import backend, unrelated to any room: `parseDecklistText(text)` parses a pasted Moxfield-style export, honouring a `Commander` section header; `evaluateDecklist(entries, registry)` cross-references each name against the local `CardRegistry` (implemented cards reported from their `CardDefinition`), falls back to Scryfall for anything else (throttled, 429-aware retry), and fills `suggestedReplacement` for an unimplemented card via `engine`'s `suggestReplacement`. `formatCheck(...)` runs `validateCommanderDeck` over the result. Scryfall lookups go through `lookupScryfallMany`, which **batches**: `POST /cards/collection` takes 75 names at a time, so a 100-card list costs two round-trips rather than a hundred throttled ones (~1s instead of ~35s). Responses carry no echo of which identifier produced which card, so they're matched back by name — each returned card is indexed under its own name, its `"Front // Back"` name rewritten in the single-slash form decklists use, and each face name. A name that misses is retried once per alternate spelling (`scryfallNameVariants`), one extra batched round each. Results (misses included) are cached process-wide for the life of the process. Wired up as `POST /import-deck` in `index.ts`, which answers with **newline-delimited JSON, not one object**: `{type:"progress", done, total, name}` lines as `evaluateDecklist`'s `onProgress` fires (implemented cards land at once, then a line per lookup batch), then exactly one terminal `{type:"result", cards, format}` or `{type:"error"}` line. Streamed so the deck builder's import panel can render a progress bar off those lines rather than sit silent. Live-fetching a Moxfield URL server-side was tried and abandoned (403s) — pasted export text only.

`server/scripts/smoke.mjs` (`npm run smoke -w server`) is the server's own eyeball check.

## Client architecture (`client/src/`)

A **networked** client: each device is one seat, connected over WebSocket to a `server` room. It
never owns a `Game` or runs a controller loop itself. 2-player rooms render a classic vertical
layout; 3-4 player rooms render a 2x2 quadrant grid, with you always bottom-left.

**Three pages, branched by path in `main.tsx`** before `<App/>` is chosen, so `useNetworkGame`'s
eager WebSocket never opens for the two network-free ones: `/library` → `LibraryPage`,
`/deck-builder` → `DeckBuilderPage`, everything else → `App` (the game itself).

- **`net/useNetworkGame.ts`** — owns the WebSocket connection and the current seat's latest `frame` (`{seq, view, actions}` — one server push, whole), with `view`/`actions` derived from it for bookkeeping that has to be current. Reconnects with exponential backoff; a previously-claimed seat (`clientToken` in `sessionStorage`, per-tab) is reclaimed automatically. `ConnectionStatus` is `connecting` → `no-room`/`room-not-found` → `choosing-seat` → `waiting-for-players` (my seat is claimed but the room is still a `PendingRoom` — other seats are open) → `playing`/`disconnected`. `opponents: readonly PlayerId[]` is every other seat in turn order starting right after your own, wrapping around. `createRoom(seed?, players?)`, `claimSeat(seat, displayName?, deck?)`, `addBot(seat)`, `addSeat()`/`removeSeat(seat)`, `dispatch(action)`, `passTurn()`/`autoPass()`/`toggleManaSkip()`, `ackFrame(seq)`, `nameOf(id)`. `everConnected` distinguishes a first visit to a server that isn't up from a connection actually lost mid-game — both land on `disconnected` (a failed initial socket fires `onerror` then `onclose` without ever reaching `no-room`), and only the wording differs.
- **`net/protocol.ts`** — mirrors `server/src/protocol.ts` by hand. Also `ImportedCardReport`/`DeckFormatReport`, mirroring `server/src/import-deck.ts`'s response shape.
- **`App.tsx`** — `App` picks a screen off `NetworkGame.status`: `LandingScreen` → `SeatPickerScreen` → `GameScreen`. `GameScreen` renders the topbar/history popup, seat banner, highroll banner, `<Table>`, plus the floating `<Stack>` overlay and `<AnimationLayer>` as siblings. **Everything it draws comes from `usePlayback`'s `shown` view, never `game.view`** — the two differ for as long as an animation is running, and mixing them is what put a card's arrival animation over a board that already had the card on it. `Table` (keyed on `shown.revision`, i.e. one remount per frame actually shown) classifies `actions` into a `mode` (mulligan → commander-replacement → pay-life-for-untapped → choose-copy → choose-text → choose-modes → sacrifice → scry → assign-combat-damage → put-on-bottom → discard → order-blockers → attackers → blockers → choose-from-zone → choose-x → choose-sacrifice → targeting → priority) and builds the matching `Action` from click handlers. Each decision kind gets its own small UI (e.g. `commander-replacement` shows a move-to-command-zone prompt; `choose-modes` shows Yes/No, one-button-per-mode, or toggle+Confirm depending on shape; `choose-x`/`choose-sacrifice` run before targeting and thread through it). `renderPlayerPanel`/`renderHandAndControls` are shared between the 2-player and quadrant-grid layouts. **`setState` updaters must stay pure** — dispatch happens after `setTargeting`, not inside its updater. State that must *not* reset per frame lives in `GameScreen` and comes in as props — the peekable hand tray's raised flag, which as `Table`-local state slammed the hand shut every time you played a card.
- **`lobby/`** — the two screens before a game. **`LandingScreen`** (`landing.css`) is the front door: a hero, then "Start a game" and "Join a game" as two separated panels, then the library/deck-builder pages as footer cards. It is a real page, not `.overlay`/`.overlay-box` — reusing the same box the "Connecting…" dialog draws is why the app's first impression used to be a 368x277 modal on an empty scrim. It asks **no** player count: three "N players" buttons above the CTA left nothing tying the counts to the button under them (all four read as one menu), and the *selected count* was the only accent-coloured thing on the page, so a setting outranked the primary action. The count moved to `SeatBoard` — see below. The join field carries no `maxLength`: the browser applies that to pasted text, which would chop a pasted room *link* to five characters before `parseRoomCode` could read the code out of it; the cap lives in `normalizeCode` instead, and a complete five-character code submits itself. Behind it all, `client/public/menu-backdrop.webp` (a seamlessly-tiling 10x10 grid of the top 100 commanders) drifts diagonally: an outer element holds the angle and clips while an inner one, exactly one tile wider, slides exactly one tile — which lands on an identical repeat, so only a transform animates and no edge is ever dragged into view. Two things there are easy to get wrong and are commented in `landing.css`: the oversize has to add *half the opposite axis* rather than a flat percentage (a fixed 160% covers 16:9 and fails on a wide, short window), and the blur is baked into the image rather than applied as a CSS `filter` — blur strips exactly the high-frequency detail that costs bytes, which took the same 2048px export from 1278KB to 263KB. The shipped file is 1536x2128 at 152KB, from a 241MB 7680x10640 source: `magick src.png -background "#12171b" -alpha remove -alpha off -filter Lanczos -resize 1536x -gaussian-blur 0x3 -quality 72 menu-backdrop.webp`. **`SeatBoard`** (`lobby.css`) is the seat-picker/waiting room, and owns table size via an "Add seat" tile on the end of the row plus a × on any seat nobody is sitting in (2-4, enforced server-side by `PendingRoom`). Its grid gap and the dialog's own side padding share one `--seat-gap` token declared on `.seat-board-box`, because the grid runs the full width of that box and two different numbers there read as an uneven row. `claimSeat` sends along whatever deck `deck-builder/decks.ts`'s `getActivePayload()` reports as active.
- **`deck-builder/`** — `DeckBuilderPage` (`/deck-builder`, no room server needed to browse/build): search the pool (`BUILTIN_CARDS` filtered by `isDeckableCard` — no tokens, no back faces), build a 100-card deck with a commander, and see live `validateCommanderDeck` legality — run in-browser from `engine`, no round-trip. **Right-clicking a card row** opens `CardContextMenu` (portalled to `<body>` and placed from JS, like the hover preview, since the lists are scroll boxes); its one unique item is "Change printing…", which opens `PrintingPicker` over Scryfall's `unique=prints` search (`printings.ts`, a direct browser call — one search for one card, unlike the import's hundred-name batch that needs the server). The choice is stored on `SavedDeck.printings` (card name → Scryfall card id) and travels `WireDeck.printings` → `DeckList.printings` → `viewFor`'s `art`. The server only accepts a bare card id there (`assertPrintingsAreSafe`): the value ends up as an `<img src>` in *every* seat's browser, and `resolveArtUrl` would otherwise take any absolute URL verbatim. Also hosts the **decklist import** panel, which POSTs pasted text to `/import-deck`, streams that endpoint's NDJSON progress lines into a live per-card progress bar, and offers `suggestedReplacement` substitutions for unimplemented cards, turning the result into a real saved deck. `decks.ts` is per-browser persistence in `localStorage` (not `sessionStorage` — a deck should outlive the tab): a named `SavedDeck` list plus an `ActiveRef` pointing at either a saved deck or one of `engine`'s `SAMPLE_DECKS` directly, so a starter deck is playable without duplicating it first. Server-side deck save/share doesn't exist yet.
- **`library/`** — `LibraryPage` (`/library`): the public, read-only card gallery, shaped like a Scryfall search result — a sticky search/filter bar (text, type, colour, sort, a "Tokens" toggle) over a responsive grid of whole printed card faces (`CardImage`, not `CardTile` — nothing here is a game object, so there's no live state to overlay), and a card's own page as an overlay rather than a side pane, so the grid keeps its scroll and filters. One entry per *card*, not per registered definition: a DFC's back face appears as its front's flip side (`isCardFront`), and tokens are excluded unless asked for. `?card=Name` deep links (the same convention the card lab uses). Distinct from `lab/`, which is a dev tool excluded from the production build and deliberately still shows everything.
- **`ui/`** — `CardTile` (a card face *reassembled* out of DOM — title/cost, Scryfall art crop via `ui/art.ts`, type line, text box, P/T or loyalty badge; props for `highlight`/`selected`/`activatable`/`badge`/`order`/`stackCount`/`compact` — because it has to overlay live game state on it). `CardImage` is the other half of that pair: the whole printed face as one image, for anywhere there's no game state to show (the library gallery). It owns `ui/card-image.css` — the one stylesheet a component imports rather than a page — and skips the art lookup entirely for a token with no pinned printing, since a token's name isn't one Scryfall has ever known. `ui/Symbols.tsx`+`symbols.ts`+`mana.ts` render `{…}` mana tokens as pips (art sliced from a spritesheet, CSS fallback for exotic symbols). `ZoneViewer` (takes `ids` + a `resolve(id)` lookup so an unresolvable id renders face-down; optional `castable` prop for graveyard flashback/play-from-graveyard buttons). `MiniTile` (a battlefield permanent as art + a stat badge) **portals its hover popover to `document.body` and places it from JS** — below the tile, flipped above when near the bottom of the screen, clamped inside the viewport; it can't be a CSS-revealed absolutely-positioned child, since `.quadrant-body` is a scroll box (clips it) *and* a size container (so `position: fixed` wouldn't escape either). `PhaseTrack`, `TurnBanner`, `PlayerPanel`, `Stack`, `EventLog`. `AnimationLayer` draws the purely cosmetic overlays (a card zooming up when cast or played, an attacker lunging at what it damages, turn/phase banners) off the cues `usePlayback` publishes — nothing here ever touches game state, and a missed or double-played animation is harmless.
- **`lab/`** — the **card lab** (`npm run lab -w client` → port 5174, no room server needed): a searchable gallery of `BUILTIN_CARDS` + a detail pane (`Tile`, `Structure` = feature chips + pretty-printed def, `Sandbox` = a local solo game via `engine`'s `createSandbox`). `vite.lab.config.ts` aliases `engine` to source so card-file edits hot-reload (a *new* file still needs `gen:cards`).
- **`ui/art.ts`** — `resolveArtUrl(art, name, version?)`: a `CardDefinition.art` link or a by-name Scryfall fallback. `cssUrl(url)` wraps one for a `background-image` — **always use it there**: an unquoted `url()` token may not contain a quote character and `encodeURIComponent` leaves an apostrophe alone, so every card whose name has one ("Atraxa, Praetors' Voice") silently lost its art.
- **`game/board.ts`** — `computeBoardEntries(view, pid)`: pure layout logic turning one player's battlefield into `BoardEntry[]` (bucketed by type, Auras/Equipment nested as `attachments`, matching untapped/tapped land stacks collapsed).
- **`game/usePlayback.ts` + `game/animationBus.ts` + `game/animationSchedule.ts`** — the animation pipeline, Hearthstone-style: **one thing at a time, and nothing may act until it finishes**. `usePlayback(frame, bus, onShown)` queues the server's frames and plays them one at a time — each frame's animations run against the board *before* it (the previous frame's, still on screen), and only when they finish does the new board replace it. It reports `{view, actions, revision, busy}`; `busy` empties `Table`'s action list, and `onShown` (wired to `ackFrame`) is what lets the server hold its bots to the same rule. `scheduleEvents` gives each animate-worthy event its slot (`CARD_STEP_MS` 1800 / `HIT_STEP_MS` 720 / `DEATH_STEP_MS` 420 / `DRAW_STEP_MS` 520 / `TURN_STEP_MS` 1300 / `PHASE_STEP_MS` 700 — the same numbers `AnimationLayer`'s overlay timeouts and App.css's `animation-duration`s are written to, so nothing outlives its slot), with `MAX_FRAME_MS` (6s) as a backstop that *drops* animations rather than clustering them past the ceiling. **Only the animations in `PACED` (a card play, a combat hit, a permanent leaving) hold the game up**; a turn or phase banner is a caption that plays over whatever the board has moved on to, costing nothing — otherwise a land the bot played hangs in the air for the length of an "End Phase" banner before reaching the table. Banners a frame merely passed *through* are dropped too (only the phase it lands in is announced), and `MAX_QUEUED_BANNERS` (3) keeps the banner queue from narrating a turn that finished several turns ago. `AnimationBus` carries cues sideways to `AnimationLayer` (a sibling, since `Table` remounts per frame), and **each cue carries the view it belongs to** — that's what makes a played land draw as it looked when played, rather than as it looks after the bot tapped it. A played card flies out of its owner's `.quadrant-cell` and shrinks back toward it (`flyOrigin` measures the cell off the live DOM and hands the offset to the CSS as `--fly-x`/`--fly-y`), so which side of the table a play came from is readable at a glance. A permanent leaving the board fades out first (`runDeath`, on `permanent-left-battlefield`, whatever the destination) rather than blinking out of existence; a run of them in one frame goes together on one beat. An attacking creature is tapped, so its tile is drawn tilted — the lunge travels on the outer `data-obj-id` box while the inner face straightens up to full size at the moment of impact, instead of sliding across the board at 20 degrees. A `card-drawn` sends a small cardback out of that player's `data-library-of` pile and into their hand — the bottom edge of their cell for you, the top edge for a seat across the table (`drawFlight`) — staggered when several land at once and capped per frame, and unpaced like the banners. `MAX_QUEUED_FRAMES` (4) is the catch-up valve for a backgrounded tab whose timers have been throttled.
- **`format.ts`** — `describeEvent`/`describeTarget` (event log text), `playerLabel` (prefers a chosen display name, falls back to a capitalized seat id), `seatClassOf` (stable per-seat colour by turn-order position, not table position), `isDetailOnlyEvent` (the bookkeeping the history hides by default — priority going round, step boundaries, mana entering a pool and the lands tapping to fill it; it's roughly three quarters of the log by volume, so `EventLog` opens concise and offers "Detailed" as a toggle).
- A rejected `dispatch` surfaces as `NetworkGame.error` → a dismissable red banner.
- Styling is `App.css` for the game table (plus a small `.css` beside each standalone page: `lobby/` — two files, `landing.css` and `lobby.css` — `deck-builder/`, `library/`, `lab/`) — legible dark table, no UI library. `index.css` holds the palette tokens and the element-level baseline for `button` and for text `input`s; that input rule is written as `input:where(…)` so it weighs the same as a bare element selector and every per-page class rule still wins. Card art is the only network dependency. Out of scope: undo.

**Standing UI rules** (settled during the board redesign — see `client/BOARD_REDESIGN_PLAN.md`):

- **No fixed px.** Sizing is `clamp()`/`vw`/`vh`, derived from the shared `--card-w` token for anything card-sized — never a new hardcoded number.
- **`--card-w` is viewport-*width*-derived; cap it against height where height is the real constraint.** A card-shaped box inside a container whose height is a viewport fraction (the quadrants are roughly half of it) needs a height cap too, or it fits on a tall monitor and overflows a short one — the two scale independently, and `--card-w` sits at its 150px ceiling all the way down to a 1667px-wide viewport. `--card-w-max` is the ceiling and `--card-w` is what everything reads, so a height-constrained subtree narrows `--card-w` for itself against that ceiling (the command/library rail does exactly this: `.quadrant-body` is a `container-type: size` container and the rail caps at `32cqh`). That cap is set against the **commander slot alone**, because the library pile below it squashes to whatever is left rather than demanding a full card's height — stacking two full slots plus their labels needs about twice a card's height, which at 768px tall didn't fit at all (a 286px rail in a 269px quadrant, the library count clipped off every cell, and that overflow was what made the boards scroll). The rail also stretches to the quadrant's full height, so its seat-coloured divider runs down the whole board. Note that making `.quadrant-body` a size container also makes it the containing block for `position: fixed` descendants (`contain: layout`), which is why the board's hover popover has to leave the subtree entirely rather than just going fixed.
- **Mana symbols always go through `<Symbols text={…} />`**, which renders `{…}` tokens as sliced-artwork pips with a CSS fallback. Never hand-roll a coloured circle.
- **Columns that must be equal need `minmax(0, 1fr)`, not `1fr`.** A bare `1fr` is `minmax(auto, 1fr)`, so a track whose content has a wide minimum (a row of input-plus-button, a long unbreakable word, an image) takes more than its share and its neighbour takes less. On the landing page that silently gave the join panel 414px against the start panel's 387 while the footer nav below, having no such pressure, split evenly and lined up with neither. The same footgun is why the seat grid and the board rows are written with `minmax(0, 1fr)` too.
- **A child that names its own width inside a padded box will escape that padding.** `.seat-board` at `min(1180px, 90vw)` inside a `.seat-board-box` at `min(1180px, 94vw)` overran the box's content area on a wide screen and pushed the outer seat panels out through its side padding. Let the box own the width and the child fill it (`width: 100%`).
- **The client has no automated tests.** Verify any UI change live in the browser, in *both* a 2-player and a 3-4 player room, since the layouts diverge — **and at a short viewport (~768px tall), not just whatever monitor you're on.** Several severe layout bugs (every battlefield tile crushed to its 40px floor, the command/library rail overflowing its quadrant, the hand fan hanging off the bottom of the screen) were invisible at 1440p and obvious at 768p.

## Commands

Run from the repo root unless noted. Workspace scripts: `npm run <script> -w engine` / `-w server` / `-w client`.

**Whole repo** (root scripts fan out with `--workspaces --if-present`):
- `npm run build` — builds `engine` (tsc), then `server` (tsc), then `client` (`tsc -b && vite build`)
- `npm test` — runs `engine` and `server` vitest, each once (`client` has no tests)
- `npm run lint` — oxlint on `client`
- `npm run typecheck` — `tsc --noEmit` on `engine`, `tsc --noEmit` on `server`, `tsc -b` on `client`

**Engine** (`engine/`):
- `npm run card:lookup -w engine -- "Card Name"` — fetches the card's authoritative mana cost/type line/Oracle text/rulings from the Scryfall API (`engine/scripts/scryfall-lookup.mjs`). Run this before authoring a new card — see `cards/AUTHORING.md` §1.
- `npm run card:verify -w engine` — diffs every `cards/pool/` card's mana cost/colors/types/subtypes/P-T/loyalty against real Scryfall data, batched (`engine/scripts/verify-cards.mjs`). Structural fields only, not ability text. See `cards/AUTHORING.md` §16. **Every card in `pool/` is a real Magic card** — the pool's 27 invented placeholders were replaced with real printings of the same mechanic (see `neededCards-features.md` "E2"), so a `NOT FOUND` from this script now means a made-up or misspelled card, not a known exception. `tokens/` is exempt (token names aren't unique on Scryfall).
- `npm run test -w engine` — vitest, single pass (CI mode); `-- path/to/file.test.ts` for one file, `-- -t "name"` for a name match
- `npm run test:watch -w engine` — vitest watch mode
- `npm run build -w engine` / `npm run typecheck -w engine`
- `npm run play -w engine` — builds, then runs `engine/scripts/play.mjs`: a full two-player game with default controllers, prints the event log (`-- --seed 7`, `-- --turns 3`). The engine has no UI, so this and the tests are how you watch it run.
- `npm run play:<demo> -w engine` — small narrated demo scripts for specific mechanics: `cast`, `combat`, `abilities`, `triggers`, `static`, `keywords`, `tokens`, `attachments`. See `engine/scripts/*-demo.mjs`.
- `npm run play:random -w engine` — `engine/scripts/random-demo.mjs`: N random-vs-random games (`-- --games 300`, `-- --log`, `-- --players 3|4`, `-- --progress` to announce each seed on stderr before playing it). This is the engine fuzzer — if `legalActions` ever offers something `dispatch` refuses, or an unbounded loop/object-count blowup happens, this crashes or hangs. Decks A/B/C exercise most of the card pool (deck D reuses deck B); every needed-cards/EDH-backlog card is added to one as it ships.
- Each major feature has its own dedicated engine test file rather than a standalone demo script (commander, mulligans, legend rule, multiplayer, bounce, X-spells, sacrifice, hand disruption, fight/keywords, counterspell, flash/prowess, proliferate, combat-damage triggers, control-change, base-P/T CDA, clone, animate, text/color, replacements, modal, filters/scopes, tutors, static restrictions, ability costs, ward, cost modification, protection, and one file per "needed-cards" pass — dual-lands, graveyard-recursion, landfall-payloads, count-scaled, trigger-value, token-for-target, token-copy, sacrifice-cost, intervening-if, additional-costs, token-stacking, mdfc, transform, phase10-misc). Read the relevant one for a runnable example of how a mechanic works.

A git-ignored `scratch.mjs` at the repo root is a scratch pad for ad-hoc exploration (`node scratch.mjs` after building `engine`/`server`) — build a `Game` (often spawning objects directly onto the battlefield), wrap it in a `Room`, serve it over a raw `ws` `WebSocketServer` on port 4000 for a browser (or `claude-in-chrome`) to connect to at the client dev server's URL with `?room=<CODE>`.

**Server** (`server/`):
- `npm run test -w server` / `test:watch` / `build` / `typecheck`
- `npm run start -w server` — runs the built `dist/index.js`: a real room server on `ws://localhost:4000` (or `$PORT`)
- `npm run dev -w server` — `tsc --watch` + `node --watch dist/index.js` together
- `npm run smoke -w server` — an in-process two-client round-trip sanity check

**Client** (`client/`):
- `npm run dev -w client` — Vite dev server with HMR (build `engine`/`server` first); needs a room server reachable at `ws://<host>:4000` (override with `VITE_SERVER_URL`)
- `npm run lab -w client` — the card lab, no room server needed (build `engine` once first for types)
- `npm run build -w client` / `lint -w client` / `preview -w client`
- No client tests yet. To watch it run: start a room server, then `npm run dev -w client` and open two tabs/devices to the same room code.

## Git workflow

- **Standing authorization to commit and push**: once a feature is working (build/lint/typecheck/tests clean, and — for anything UI-visible — checked live in the browser), commit it and push to `origin/main` without asking first each time. Split unrelated work into separate, logically-scoped commits the way the existing history does (see `git log`), rather than one giant commit. This still doesn't cover force-push, history rewrites, or pushing something you haven't actually verified — those still warrant asking.

## Toolchain notes

- **Module systems differ**: `engine`/`server` are ESM + NodeNext, so their own relative imports need explicit `.js` extensions (e.g. `import { x } from "./foo.js"` even though the file is `foo.ts`). `client` is ESM + bundler mode.
- **Engine/server TS config is `erasableSyntaxOnly`** (same as the client): **no `enum`, no `namespace`, no constructor parameter properties**. Use string-literal unions + `as const satisfies` tables instead. Also `verbatimModuleSyntax` → split `import type { … }` from value imports. `strict` + `noUnusedLocals`/`noUnusedParameters`.
- **Client TS config** (`client/tsconfig.app.json`) is strict bundler-mode: `verbatimModuleSyntax`, `erasableSyntaxOnly`, `noUnusedLocals`/`noUnusedParameters`, `allowImportingTsExtensions` (relative imports include the `.tsx`/`.ts` extension). `noEmit` — Vite does the transform.
- **Engine/server tsconfig excludes `src/**/*.test.ts`** from the build; vitest type-checks tests itself.
- **Shared dev deps are hoisted to the root** `package.json` (`typescript`, `@types/node`). Don't re-add them to a workspace unless a version needs to diverge.
- **Lint** is oxlint, not ESLint. Config in `client/.oxlintrc.json` (`react`, `typescript`, `oxc` plugins; `react/rules-of-hooks` errors).
- Assets in `client/public/` are referenced by absolute path (e.g. `/favicon.svg`); assets imported from `src/` go through Vite.
- **Windows CRLF/LF drift**: editing an existing pure-LF source file on Windows can leave it with *mixed* line endings (untouched lines stay LF, lines the tool rewrites come out CRLF) — distinct from a file that's already consistently CRLF (harmless). Before committing, if `git diff --stat` on an edited file looks disproportionate to the actual edits, check directly (`git cat-file -p HEAD:<path> | grep -c $'\r'` vs total line count) rather than trusting the diff size. Fix with `sed -i 's/\r$//' <path>`, rebuild/retest, then fold the fix into the same commit via `git commit --amend` if nothing's been pushed yet.
