# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

MTG-Engine is a Magic: The Gathering rules engine (`engine/`) with an authoritative multiplayer
room server (`server/`) and a React web client (`client/`) — a real networked 2-4 player game
(Commander-capable), not a local hot-seat demo. The repo is an **npm workspaces monorepo**
(`workspaces: ["engine", "protocol", "server", "client"]` in the root `package.json`, in
that order so `engine` builds first, then `protocol`, then `server`).

**Where the docs live.** This file is a map of *current architecture* — not a changelog. The
others, and what each is for:

- **`BACKLOG.md`** — **the plan of record for open work**: one line per thing still to do
  (commander gap, card backlog, engine rules gaps, bots, client/UI, tooling), each pointing at
  where its detail lives. Delete a line when it lands; add one when you find something. Nothing
  else lists open work, so check it before starting and update it in the same commit.
- **`ROADMAP.md`** — the engine's build history, condensed. Its 11 phases and the follow-on
  "needed-cards" P0–P20 passes are **all done**; ~180 source comments cite "ROADMAP Phase N", so
  the phase index stays. **Read its *Architecture constraints* section before touching the
  engine.** Per-phase narrative detail is in `git log`, not here.
- **`engine/src/cards/neededCards-features.md`** — the detail behind `BACKLOG.md`'s engine items:
  engine features ranked by how many real cards each would unblock, over two measured
  populations, plus a compact index of finished passes (P0–P20, Tier 1, E1–E3) that source
  comments cite. **The commander gap comes first**: `top-commanders.txt` (`npm run cmdrs:top` /
  `cmdrs:mark -w engine`) is the top 500 commanders by decks run *as commander* — ranking them by
  card popularity misses 53 of the top 100, because a commander is a singleton played almost
  nowhere but its own deck — and `top-commanders-gaps.json` maps every unimplemented one to the
  engine features it needs (a per-card triage over one ~245-feature vocabulary), which
  `npm run cmdrs:gaps -w engine` ranks by commanders blocked and as a greedy engine-only build
  order. Add a feature's key to the JSON's `built` array when it lands. The card backlog is
  `top-commander-cards.txt` (the top 2000 Commander cards by
  EDHREC rank against the pool), re-marked in place by `npm run cards:mark -w engine`. The pool is
  ~5,400 real cards (`npm run card:verify -w engine` prints the current count of definitions,
  which is a little higher: each face of a double-faced card is its own).
- **`engine/src/cards/AUTHORING.md`** — the hand-authoring guide for adding a card. Read before
  authoring.
- **`DEPLOYMENT.md`** — the tobyens.com production hosting/update runbook.
- **`docs/plans/*.md`** — design records, each saying *why* its piece is shaped the way it is; a
  `Status:` line at the top of each says where it stands, and none is living documentation.
  Shipped: `basic-bots` (v1 bot), `card-library-page`, `deck-builder`, `card-replacer` (reworked
  onto Scryfall Tagger oracle tags), `precon-decks` (the five starter decks and their stand-ins), `resolve-all-stack` (the one-shot "resolve the whole stack" button),
  `auto-pass-interruptions` (the shared "something real happened" scan that
  stops both it and auto-pass).
  `engine-gaps` records the engine work that unblocked most of the precons, paused with the rest
  substituted. `smarter-bots` (v2, one-ply search, what live rooms seat) has its search architecture superseded by `bot-v3-search` (rollout search over sampled worlds — **built, benched, and deliberately not seated**: it loses to v2 by six points at four players, and the evaluation re-fit is outstanding; read it before changing how the bot picks actions). `token-stack-choices` (**in progress**) designs picking some members of a token stack, the last stack gap after the counting and whole-stack fixes: sacrifice N, tap costs and convoke are built; splitting a stack across attackers or blockers, and choosing which of a stack proliferate touches, are not. `commander-replacement` records how rule 903.9 is asked (never skipped: queued when it can't be asked yet, re-asked when overwritten), the older bugs found alongside it, all since fixed, and the move from the pre-2020 replacement to the current rule, where a commander dies first and a state-based action then offers the command zone. `damage-assignment-order` (**implemented**) records that Foundations removed damage assignment order, so a blocked creature's damage is divided freely among its blockers (trample still needs lethal on each first), and how the engine dropped its `order-blockers` decision and lethal-in-order validator for it. Server-side deck save/share
  is still unscoped.
- **`client/BOARD_REDESIGN_PLAN.md`** — the board-overhaul record: the mockup URL, the settled
  design rules, and the known gaps. All 18 phases shipped.

- `engine/` — a TypeScript library package, ESM (`"type": "module"`), NodeNext resolution. Emits to `dist/` with declarations; `package.json` `exports`/`main`/`types` point there. No I/O, no UI — a pure state machine driven entirely through `dispatch`.
- `protocol/` — a types-only package: the wire contract between `server` and `client`, imported by both rather than restated on each. Emits no runtime code (`export {}` and comments), which is why it can sit between a Node process and a browser bundle for free. Depends on `engine` for the types that cross the wire (`Action`, `LegalAction`, `PlayerView`).
- `server/` — a Node + `ws` package: the authoritative multiplayer room host. Owns the one real `Game` instance per room, keyed by a room code; every connected device gets its own redacted `viewFor(seat)` pushed after each dispatch. Imports `engine` the same way `client` does.
- `client/` — a Vite + React 19 + TypeScript app: a **networked** client — each device is one seat, connected over WebSocket to a `server` room, never running a local `Game` or a controller loop itself. Imports the engine (`"engine": "*"`, the workspace symlink) as **`engine/client`** — `engine/src/client.ts`, a second package entry with every type but only the values a page uses, none of which reaches a card definition (`test/client-entry.test.ts` walks its imports to keep it so). The main `engine` barrel exports `BUILTIN_CARDS`, which imports every card file, and Vite's dev server doesn't tree-shake, so a page importing the barrel fetched all ~5,500 card modules on every load (16 s warm). No page imports `engine` itself. Consumes the engine's public seam — the `Action`/`LegalAction`/`PlayerView` types, plus pure helpers such as the combat validators — indirectly, via the wire protocol `server` speaks. Needs `engine/dist/` and `protocol/dist/` built (`npm run build` does engine, protocol, server, then client).

## Engine architecture (`engine/src/`)

### What's implemented

Full turn/step loop, casting + targeting + fizzle, a LIFO stack, SBAs, full combat (first
strike/double strike/trample/deathtouch/lifelink/menace, multi-blocker damage assignment as a
player choice, a first-strike priority window, must-be-blocked), activated/triggered abilities
(intervening-ifs, `{X}` costs, loyalty abilities), the full continuous-effects layer pipeline
(1 copy, 2 control, 3 text, 4 type-change, 5 colour, 6 keywords/ability-loss, 7 P/T incl. a CDA
layer), tokens (with a `stackCount` compaction scheme so a self-replicating generator can't blow
up object count — see "Token stacking" below), Auras & Equipment (an Aura put onto the battlefield without being cast chooses what it enchants, rule 303.4f), Commander (command-zone casting
with tax, the command zone as its owner's choice — a state-based action once it's in a graveyard or exile (903.9a), a replacement for a hand or library (903.9b) — commander damage, Partner and every variant of
it — Partner with, Partner—[text]/Friends forever, Choose a Background, Doctor's companion — as a
declarative `CardDefinition.pairing`, the legend rule),
an opt-in simultaneous-mulligan phase, 2-4 player tables (APNAP ordering, per-defender blocker
declarations), a full replacement-effects pipeline (`replacements.ts`), modal/"you may"/targeted-
modal spells, mass effects (wraths, edicts) and tutors/scry/surveil, a rich effect vocabulary
(bounce/exile/mill/discard, fight, counter, control-change, clone, animate, text-change,
count-scaled and trigger-supplied amounts, token-for-target and token-copy effects, conditional
effects, sacrifice costs incl. filtered ones, additional costs & kicker), planeswalkers, alternate
casting zones (flashback, suspend, foretell, escape, disturb, adventure, MDFCs, transforming DFCs
+ Day/Night, Channel from hand, Overload, a conditional free-cast permission, Convoke), extra
turns/combats, cascade/storm/spell-copying, Sagas, station cards (Spacecraft — rule 702.184, 721), the Monarch/Energy/Emblems, damage-prevention
shields, and a color-identity-aware Commander deck validator (`identity.ts`, `deck-validation.ts`).

**Every player decision is a dispatched action**, never a synchronous controller callback. Each of the 18 kinds is a module under `decisions/` owning its whole *answer* half — offer, validator, controller arm, bot candidates — registered in a total table, so adding one fails the build at that table rather than several hundred lines away. Applying stays on `Game`. See `docs/plans/decision-registry.md`. The kinds:
`declare-attackers` / `declare-blockers` / `assign-combat-damage` / `discard` /
`choose-from-zone` / `mulligan` (answered by `mulligan`, then `put-on-bottom`) / `commander-replacement` /
`pay-life-for-untapped` / `choose-copy` / `choose-enchant` / `legend-rule` / `choose-text` / `choose-creature-type` / `choose-modes` / `choose-targets` /
`sacrifice` / `scry` / `proliferate` alongside the priority actions. `legalActions(player)` enumerates what's
playable right now with per-slot target options; `viewFor(player)` produces a redacted,
self-contained snapshot for one seat.

**Not modeled**, and every other known rules gap, is listed under "Engine rules gaps" in
`BACKLOG.md` — Battles, phasing, dungeons/Initiative/Ring, banding, Companion, replacement
ordering, static dependency ordering and snow sources among them.

**Token stacking** (an engine resource-safety mechanism, not a rule — added after the fuzzer hung
on a self-replicating-token card): `GameObject.stackCount` lets one object stand in for many
fully interchangeable, still-pristine token copies instead of minting one object per copy.
`Game.mintTokenBatch` folds new batches into a matching existing stack; a fresh batch only
originates a stack past `STACK_ORIGIN_THRESHOLD` (8), so ordinary "create two tokens" cards are
untouched. Only tokens with no activated ability and only count-scalable, non-targeted triggered
abilities are ever stacked (`Game.isStackableTokenName`). `Game.splitOneFromStack` peels one off
into an ordinary object the instant anything singles it out (a chosen sacrifice; a target is split
*once, as it's chosen* — `Game.lockInTargets` at cast, activation and trigger placement, after
costs are paid — so every step of a multi-step effect, and any copy of the spell, reaches the same
token); `Game.materializeStack` expands a whole stack into real objects for combat (capped at
`MAX_MATERIALIZED` = 100 — attacking/blocking are optional, so declaring a legal subset is
allowed); `recompactTokens` (end of cleanup) folds tokens back into stacks once nothing tells them apart (`tokenFoldKey`, shared with `findMergeableStack`) and nothing else names them by id (`pinnedTokenIds` — an attachment's host, a delayed trigger's target, a prevention shield's). **Anything that counts permanents counts a stack as every token in it** — `permanentCount` (`state.ts`), behind `countOf`, cost reductions, "controls N or more" conditions, count-scaled P/T and the died-this-turn count; counting objects instead had Krenko, Mob Boss making two Goblins forever. An "each **other** …" count bonus (`grantPtPerCount.excludeSelf`) beside a stacked source still counts the rest of that stack (`othersInOwnStack`), since each token in it is "other" to the rest. Because that makes counts of a million reachable, loops that mint one real thing per unit (individually made tokens, mana units, unscalable trigger copies) stop at `Game.MAX_EFFECT_INSTANCES` (1000), and a draw loop stops at the first empty-library draw. The same holds on the stack: a triggered ability that chooses no targets and isn't count-scalable, fired once per token of a stack (Authority of the Consuls seeing twenty Goblins enter), is queued once with `PendingTrigger.copies` and goes on the stack as one ability object with that `stackCount` — each copy still its own resolution, one at a time with priority between (`removeOneAbilityCopy`), a counter taking one. See
`token-stacking.test.ts`, `token-stack-counts.test.ts`, `token-stack-targets.test.ts` and `random-demo.mjs` for the original repro.

### File map

Tests live in `engine/src/test/*.test.ts` (one directory level deeper than the source they cover,
so relative imports need an extra `../`), except `cards/pool.test.ts`, which stays colocated with
the `cards/pool/`/`cards/tokens/` layout it guards. `server/src/test/*.test.ts` mirrors this. Discovery is
vitest's default glob, which finds them wherever they are; `tsconfig`'s `src/**/*.test.ts`
exclude already covers the subdirectory. `engine/vitest.config.ts` sets two things and
deliberately leaves discovery alone. It raises `testTimeout` to 30s: these are CPU-bound
simulations rather than the async I/O vitest's 5s default is sized for, and several sat close
enough to that limit to pass alone and fail on a busy machine. The two real long-runners
(`bot-plan.test.ts`, `eval-bot.test.ts`) keep their own larger per-file overrides. And it turns
off `isolate`, so each worker imports the card barrel once rather than once per test file,
which took the suite from 4m30s to under a minute. That is safe only while no engine test
mocks, spies, stubs a global or fakes timers. **While authoring, run just the files you touched**
(`npx vitest run cmdr-sokka pool.test` from `engine/`, ~15s), and the whole suite once per batch
before committing. `server` has no config — nothing there runs long, since its pacing tests
drive a fake clock.

- **`state.ts`** — `GameState` is one plain, `structuredClone`-able tree (no class instances, `Map`/`Set`, or functions inside it). Holds `rules` (`startingLife`, `openingHandSize`, `maxHandSize`, `maxLandsPerTurn`, `skipFirstDraw`), players, `objects` (card/ability instances — `GameObject.kind` `"card"`|`"ability"`, `abilityKind` `"activated"`|`"triggered"`|`"chapter"`, `counters`, `modifiers`, combat fields — all cleared by `moveObject` on any zone change, bar a `countersPersistAcrossZones` card's counters on any move but to a hand or library — Skullbriar), `zones` (`perPlayer` library/hand/graveyard + `shared` battlefield/stack/exile/command as ordered `ObjectId[]`; stack top = last), `turn`, `priority`, `result`, `awaiting` (a discriminated `AwaitingDecision` union — one variant per decision kind listed above, each carrying whatever context that decision needs, e.g. `assign-combat-damage {attacker, blockers, power, lethal, trample}`, `mulligan {player, hands}` where every player still deciding may act at once, `commander-replacement {commander, intendedZone}`, raised once a commander is in a graveyard or exile, or *before* a move to a hand or library), plus a grab-bag of pending-decision queues (`pendingBlockerDeclarations`, `pendingTriggers`, `pendingTargetedTrigger`, `pendingTargetedCast`, `pendingSuspendedCasts`, `commanderArrivals` (commanders put into a graveyard or exile since the last state-based check, each with the `zoneChangeCount` it arrived with — the next check queues its owner's 903.9a offer, `offerArrivedCommanders`, APNAP) and `deferredCommanderMove` + `pendingCommanderMoves` (a commander's 903.9 choice is never skipped: a 903.9a offer waits in its graveyard or exile, and a 903.9b move that can't be asked yet waits on the battlefield in the queue — or, for a return to hand from the stack, a graveyard or exile, in that zone — and a question another decision overwrote is re-asked — `raiseNextCommanderChoice`, run at the top of `prepareForPriority` and after each state-based check), `pendingPayLifeForUntapped` (a shock land that entered while another decision was being answered — a fetch land's own search — sits there tapped until `raiseNextPayLifeOffer` offers the life, one land at a time), `pendingDestruction`, `pendingDiscards` (a scoped "each opponent discards" asks one player at a time; the rest wait here), `pendingSacrifices`/`pendingSacrificeVictims`), `suspendedResolutions` (a resolution that stopped partway to ask someone something: a `sequence` step that raised a decision parks the steps after it here, and a resolution ending with a decision still open parks an empty remainder; `prepareForPriority` resumes the newest once nothing is awaited or queued, and while any is parked no SBAs are performed and no triggers placed — rule 608.2c, 704.3), `resolutionSince` (the `eventSeq` the resolution under way began at, across its parked steps: "this way" — the `thisWay` amount and `this-way` condition — is read off the discard/draw/mill/sacrifice events since) and `resolvingSource` (beside it while an *ability* resolves: its source and that source's timestamp, stamped as `entry.by` on whatever it puts onto the battlefield), `revealedThisTurn` (cards shown to every player — rule 701.16; a reveal is momentary but a client only ever sees whole *frames*, so the identity has to outlive the instant or the event names a card nobody can render. Turn-scoped, so it doesn't become a permanent window into a hand), `delayedTriggers` (delayed triggered abilities — rule 603.7; they belong to no permanent, so `detectTriggers`' battlefield scan can't see them: `enterStep` fires the step-keyed ones directly, and a `permanent-left-battlefield` event fires the ones keyed to that permanent leaving (`DelayedLeaveWatch` — earthbend's "when it dies or is exiled, return it", "when that creature dies this turn"; used up by its first departure, stint-keyed so a round trip isn't watched), minting a stack object that carries the whole `DelayedTrigger` record because there is no card ability to look up by index) that let a mass effect or multi-step decision resume correctly after a player answers something mid-resolution, `decisionSource` (what raised `awaiting`; whether a decision *names* a source is `decisions/registry.ts`'s `decisionHasSource`, read off each module rather than a switch here — set around every resolution by `withDecisionSource`, carried across the sacrifice queue's deferral, cleared when `prepareForPriority` hands priority off with nothing pending; a decision the rules raise rather than a card does, like declaring blockers, is filtered out by the `decisionHasSource` selector rather than by clearing this), turn-scoped state (`preventAllCombatDamage`, `preventionShields`, `combatDamage`, `extraTurns`, `extraCombats`, `spellsCastThisTurn`, `turnRestrictions` (a `restrict` effect's turn-wide rule, read by `restrictionsOf`), `attackRequirements` (an `attack-requirement` effect's goad-like rule of the game — Kardur, Doomscourge — lapsing as its controller's next turn begins; not a goad, rule 611.2c), `turnProhibitions` (a `prohibit` effect's "can't cast / activate this turn"), `playerEffects` (a `player-effect`'s cost reduction, free-from-hand permission or damage multiplier, gone at cleanup or as its owner's next turn begins), `dayNight`, `monarch`, `emblems`), and `eventLog`. `PlayerState` carries `energy`, `turnHistory` (what this turn has held for that player — permanents that entered under their control, creatures that died under it, permanents they sacrificed, permanent cards put into their graveyard, damage and combat damage taken, whether they attacked, and the damage sources they controlled dealt, each with its source's colours as it dealt it; recorded off the events in `emit` by `recordTurnHistory` and reset as each turn begins; read by the `turn-history` and `damage-dealt-this-turn` conditions, the `turnHistory` and `damageDealtThisTurn` amounts and the turn stats), `counters` (every other kind a player has — poison, where ten lose the game as an SBA, and experience; given by `add-player-counters`, read by the `playerCounters` amount/count/cost reduction and the `player-counters` condition, grown by proliferate), `commanderCastCounts` (per-commander tax, Partner-aware), `commanderDamageTaken` (keyed by the **commander's object id**, not its controller — rule 903.10a counts each commander separately, so two Partners at 11 apiece isn't a loss, and a stolen commander's damage still counts toward that commander; a commander keeps its id through every zone change), `spellsCastThisTurn`. `GameObject` carries the full set of per-permanent flags the layer/effect system needs: `markedByDeathtouch`, `summoningSick`, `loyaltyActivatedThisTurn`, `attacking` (`PlayerId | ObjectId`), `isToken`, `attachedTo`, `isCommander`, `controlEffects` (timestamped layer-2 control effects from resolved spells/abilities — `recomputeControl` weighs them against attached control Auras, latest wins, rule 613.7) + `controlEndsAtCleanup`, `copyOf`, `faces`/`face` (multi-face cards — `faceName(object) = faces[face]`, `printedCardName(object) = copyOf ?? faceName(object)` is what every characteristic/ability read goes through), `modifiers` (a `PtModifier[]` spanning layers 3–7d), `xValue`, `chosenModes`, `kicked`, `castVia` + the alt-zone markers (`grantedFlashback`, `suspended`+`counters.time`, `hastyUntilItLeaves`, `foretold`+`foretoldOnTurn`), `isCopy`, `stormCount`, `onAdventure`, `exiledBy`/`flickerLink` (what links an O-Ring's or a delayed flicker's return to its exile, rule 610.3), the designations `goadedBy`/`goadedForGameBy` (goads until the goader's next turn / for the rest of the game — read only through `goad.ts`) and `suspectedAt` (rule 701.60, the timestamp its menace and can't-block take in layer 6), `entry` (an `EntryRecord`: how it came onto the battlefield this stint — the zone it came from, whether it was cast and by whom from where (`castFrom`, set as it's cast), and whose ability put it there — read by the `cast`/`castBy`/`castFrom`/`enteredFrom`/`putThereBySource` filter clauses) — all cleared by `moveObject` on any zone change unless noted otherwise. The exception is `lastKnown`, a `LastKnownInfo`: the permanent as it last existed on the battlefield (rules 603.10a, 608.2h) — computed name, P/T and base P/T, types, subtypes, supertypes, colours, keywords, whether it had a mana ability or any ability, counters, controller, mana value, token/commander, tapped/attacking/blocking, attachments, lost abilities and granted triggered abilities — taken by the move off the battlefield and **kept** through later moves until the next departure replaces it, stamped with the `zoneChangeCount` it had there. A spell or ability object carries `lastKnownRefs` (`LastKnownRefs`: the battlefield stint — `zoneChangeCount` — of its source and triggering object when it triggered or was activated, the permanent it sacrificed, and the one it tapped for its cost (station's "the tapped creature"); for a trigger, also what its event was aimed at — `recipient`, the permanent (with its stint) or player dealt damage — and `player`, the player the event names: the one dealt damage or controlling the permanent dealt it, or an attack's defending player; and, for a trigger fired by its object *leaving* the battlefield, `triggerObjectAfterLeaving` — where that object went, which is as far as "return it" follows it: moved on again since, it is a new object (rule 400.7) and `ResolutionContext.triggerObjectLost` makes acting on it a no-op, while reading it stays last-known information), which is how a reader tells the departure it means from a later one; a target is known to have been a permanent from `targetZones`. Acting on an object needs it to still be the same one (rule 400.7): a stack object's `targetStints` and `sourceZoneChangeCount` record each target's and its source's `zoneChangeCount` as it went on the stack, and at resolution a target that has changed zones since is gone (`targetsStillMeant`) and a changed source is `sourceLost` — while reads of either still go through last-known information. A delayed trigger chose no targets, so only its source's identity is checked (`DelayedTrigger.sourceStint`). `GameState.ceasedTokens` keeps a deleted token's snapshot for the rest of the turn (rule 111.7). Also exports pure selectors.
- **`game.ts`** — `Game` owns the single mutable `GameState` and is the **only** writer. `dispatch(action)` handles every `Action` variant (see `actions.ts`). A 3-4 player table queues attacked defenders in `pendingBlockerDeclarations`, drained one `declare-blockers` at a time. There is no blocker-ordering step (Foundations removed damage assignment order): after blocks the active player simply gets priority. `legalDefenders(attacker)` returns every non-eliminated opponent plus their planeswalkers. `advance()`/`advanceUntil(pred)` run `tick()`. `emit()` appends an event and runs `detectTriggers` (matches against every battlefield permanent's `triggered` list, honouring intervening-ifs via `interveningIfMet`). `prepareForPriority(player)` is the pre-priority fixpoint loop: run SBAs (not while a resolution is suspended), drain pending mass-effect/sacrifice queues, resume a suspended resolution, place pending triggers (APNAP order) — repeat until stable, then hand off priority (to `awaiting.player` if a decision got raised mid-loop). Mana is **auto-paid**: `manaSources` reports each permanent's `{T}: Add` abilities (plus an untapped once-a-turn one — Vivi Ornitier's `{0}: Add`) as `ManaOption` alternatives, sizing a live `amount` (a power, a turn stat) against the board as it stands and compressing "X in any combination of" into one `anyColorOf` option rather than X+1 splits → `Game.payMana` hands a `ManaPlanningView` to `mana-payment.ts`'s `planPayment` (= `resolveHybridCost` → `planManaPayment`, both pure) → `executePayment` (taps/sacrifices sources, spends the pool, pays life); `castingCostOf` folds in commander tax and `costModification` statics (a `commanderTaxAsLife` card's tax is life instead, paid beside the mana and reserved out of the planning view's `life`). `payMana`'s last two arguments are the difference between a preference and a rule: `avoid` puts a source last (don't casually tap a permanent for its own ability's mana cost), while `exclude` removes it outright — an ability whose cost includes `{T}` taps its source to pay that, so it can't be tapped for mana as well (rule 602.2a). Without the latter, Mind Stone's `{1}, {T}, Sacrifice` funded its own `{1}` off an otherwise empty board. Ability objects are minted onto the stack by `mintAbilityObject` and deleted from `state.objects` on resolution. An ability that was *granted* (a `grantsActivated`/`grantsTriggered` static, or a modifier's `grantsTriggered`) carries a `GrantedAbilityRef` from the moment it's activated or triggers, and `stackAbilityOf` resolves from that rather than by index into its source's current abilities — the grant is often gone by then (an Aura that fell off with the creature it enchanted), and rule 113.7a says the ability doesn't care. All P/T reads go through `computeCharacteristics`. Combat damage runs through `combatDamageStep` → `runCombatDamageSubPass` (first-strike sub-pass, then regular, each followed by SBAs + a priority window when relevant; who deals damage in the regular one is fixed by who had first or double strike as the first began — `CombatDamageState.firstStepStrikers`, rule 510.4 — plus whoever has double strike by then) → `dealCombatDamage`, which takes a player-chosen `assign-combat-damage` split when one exists, else auto-assigns the standard split (`standardAssignment`); `dealDamage` runs deathtouch/lifelink, prevention shields, and Fog uniformly (for combat and burn alike) and returns the amount actually dealt. Damage dealt all at once (a combat damage sub-pass, `damage-all`, "each opponent") runs inside `withDamageBatch`, which settles it as one event: lifelink gains once per *source* (rule 119.9 — so "whenever you gain life" counts sources, not recipients), and a `dealt-damage` (enrage) trigger fires once per permanent for the total; a `deals-damage` trigger (the source's side) is not batched — it fires once per recipient, as rule 603.2 reads "deals damage to a permanent or player". `createTokens`/`addCounter`/`entersBattlefieldReplacement` all honour replacement multipliers (Doubling Season). `moveObject` is the single zone-transition function: it applies enters-battlefield replacements — the entering permanent's own, then every other permanent's `others-enter-battlefield` (Giada's counters, Thalia's "enter tapped", The Wandering Minstrel's "enter untapped", which beats every enters-tapped), with the moving effect's own "tapped" and "under your control" passed in as `EnterOptions` rather than applied after the move, so a replacement can see and override them (and the permanent is its entering controller's for the whole entry, so the triggers its counters set off see it as theirs; the control effect that keeps it there is still the caller's to create) — defers a commander's move to a hand or library behind a `commander-replacement` decision (903.9b), from the battlefield or, to a hand, from the stack, a graveyard or exile (a spell Remand counters into its owner's hand), and records one put into a graveyard or exile (from anywhere) for the next state-based check to offer the command zone (903.9a) — and **returns whether it moved** — `false` for that deferral, and for a card that can't enter the battlefield, which stays where it was (an instant or sorcery, rule 400.4a; an Aura with nothing to enchant, 303.4g); a caller that only announces a completed move reads that, never `awaiting`, which may be someone else's decision — redirects a graveyard-bound card to exile when a replacement or `castVia` says to, resets face/copy/modifier state on any move to a hidden zone, and emits `permanent-left-battlefield`/`permanent-destroyed` as appropriate. `runStateBasedActions` recomputes control (layer 2, every control effect in timestamp order), puts an Aura attached to nothing, or to something it can't enchant, into its owner's graveyard and unattaches an Equipment from anything it can't equip (704.5m–n), deletes dead tokens, removes +1/+1 and -1/-1 counters in pairs (704.5q — not from a permanent the same check kills, which leaves with both), enforces commander-damage loss and the legend rule — the player's choice of which to keep, asked (`legend-rule`, one group at a time, APNAP) before anything moves, the answers waiting in `legendRuleKeeps` so every move the check found still happens at once — offers a commander that's arrived in a graveyard or exile the command zone (903.9a — so it has died, and every "dies" trigger saw it, before its owner is asked), and sacrifices 0-loyalty planeswalkers / completed Sagas — every graveyard-bound SBA is collected first (`stateBasedGraveyardMoves`) and performed at once (rule 704.3), so a creature that dies only because its lord did waits for the next check. A player who loses **leaves the game at once** (`leaveGame`, rule 800.4a): control effects they held end and what they own leaves with them — it stays where it is to be seen but is out of the game (`inGame`, which state-based actions skip; `matchesFilter`, which finds nothing a departed player owns; `moveObject`, which won't move it) — their spells and abilities leave the stack, what they control but don't own is exiled (a spell cast from someone else's cards, a permanent put onto the battlefield under their control — `ControlEffect.entered`, default control rather than an effect), their pending and delayed triggers are dropped, and the monarch passes on (725.4). **Simultaneous leaves are one event** (rule 603.10a): the SBA sweep, a wrath (`drainPendingDestruction`), an edict's victims (every player chooses first, then all are sacrificed) and a return-all each run inside `withLeaveBatch`, and `detectTriggers` shows each leave event to the batch's already-moved permanents too (`lookBackSources`, leaves-the-battlefield triggers only) — so every one of them sees every other one leave, whatever order they moved in. A commander whose move to a hand or library the batch deferred for 903.9b carries the list as `leftWith` and completes its move inside the same batch. **Cards leaving graveyards are batched the same way** (rule 603.10a again): `moveObject` notes each card that leaves a graveyard, with a snapshot of it as it was there, and `withGraveyardLeaveBatch` — around a whole graveyard exiled, a return-all, the moves a `choose-from-zone` answer makes, an escape cost, a `simultaneous` sequence (`ctx.simultaneously`) — announces them as one `cards-left-graveyard` event once they have all moved; outside a batch each card is its own event. A batched `leaves-graveyard` trigger ("whenever one or more cards leave your graveyard") fires once per such event, matching its filter against those snapshots. **Simultaneous entries are one event too** (rule 614.12): a token batch, a return-all, a flicker's return, a tutor's finds and an O-Ring's exiles coming back each run inside `withEnterBatch`, whose members neither apply their `others-enter-battlefield` replacements to one another nor count as "already" on the battlefield for one another. **"As this enters" choices are asked before the move** (rule 614.12 — `askEnterChoice`: a Clone's copy, a chosen creature type or word): a permanent spell resolving (`enterPermanentSpell`), a land played, a reanimation, a blink or its delayed return, an O-Ring's return and a tutor to the battlefield each ask first and wait — a spell or land play (or a `choose-from-zone` answer) parks a `PendingEntry` in `suspendedResolutions`, an effect step parks itself and runs again — and `moveObject` applies the answer (`GameObject.enterChoice`) as the permanent enters, before its replacements and triggers look at it. **A permanent that left is read as it last existed there** (rules 603.10a, 608.2h): `moveObject` snapshots it (`takeLastKnown` → `GameObject.lastKnown`) before resetting it, and a batch's callers snapshot all of their victims up front (`snapshotLeaving`, kept on the batch and used by `moveObject` in place of its own), so the second victim of a wrath is read before its lord left; a commander whose 903.9b move was deferred keeps the snapshot of the moment it was asked. `detectTriggers` matches a departed subject or look-back source through it — `matchesWho`/`FilterContext.lastKnown` (controller, types, subtypes, counters, keywords, power), no triggered abilities if it had lost them, and the abilities it had then (`departedTriggeredEntries`: a copied card's printed ones plus its granted ones by `GrantedAbilityRef`), recording `LastKnownRefs` on the trigger. A resolving spell or ability reads a departed source, triggering object, sacrificed permanent (by stint — `lastKnownOfStint`) or target (by `targetZones` — `lastKnownOfTarget`) through the snapshot in `makeResolutionContext`: `powerOf`/`toughnessOf`/`manaValueOf`/`manaSpentOf`/`controllerOf`/`cardTypesOf`, the `target`/`trigger-object`/`sacrificed`/`source` conditions, "trigger-controller" scopes, and the damage a departed source deals (`dealDamage`'s `sourceLastKnown`: its colours for protection, lifelink, deathtouch and controller). `choose-modes` and `unless` continuations carry the refs and target zones along. `castSpell`/`activateAbility`/`whyCannot*` thread through `via` (alt cast zone), `face` (multi-face cards), `xValue`, `kicked`, `sacrifice` (additional/ability costs), and evaluate `costModification`/protection/`StaticAbility.condition` gates, and the prohibitions (`whyProhibitedFromCasting` — split second, a `prohibit` effect's `turnProhibitions`, a `prohibits` static, a card's own `castOnlyIf` — and `abilitiesProhibited`, which `manaSources` honours too, so a barred mana ability can't pay for anything). **Ward** (rule 702.21) is a real triggered ability (`cards/helpers.ts`'s `ward(cost)`: a `becomes-target` trigger with a `{ kind: "ward", cost: WardCost }` effect), so it goes on the stack above the targeting spell or ability. Every spell, activated ability, copy *and triggered ability* announces the objects it targets as it goes on the stack (`announceTargeted` → `object-targeted`, whose `stackObject` is the spell or ability object; a trigger announces from `mintTriggerAbility`, skipping event-filled `autoTargetSlots`), and a `becomes-target` trigger records that as `PendingTrigger`/`GameObject.targetedBy`. `beginWard` asks *that* player to pay the one compound cost as a `choose-modes` decision carrying `ward` (mana on the decision's `cost`, life/sacrifice/discard as the mode's effect, a `counter` of the targeting object as `onDecline`), offered only when all of it is affordable; `counterObject` removes a countered *ability* from the stack. `castCardWithoutPaying` is the shared free-cast core for suspend/cascade; it still pays any cost increase (Thalia, a Hinata per-target {1} — rule 601.2f) once targets are chosen, and a spell whose increase can't be paid isn't cast. A triggered ability or suspended spell needing a real target choice parks in `pendingTargetedTrigger`/`pendingTargetedCast` and raises a `choose-targets` decision rather than picking synchronously.
- **`actions.ts`** — the `Action` union: the priority actions, plus `declare-attackers`/`declare-blockers`/`assign-combat-damage`/`discard`/`choose-from-zone`/`mulligan`/`put-on-bottom`/`commander-replacement`/`choose-copy`/`choose-enchant`/`legend-rule`/`choose-text`/`choose-modes`/`choose-targets`/`sacrifice`/`scry`/`proliferate`/`suspend`/`foretell`/`cycle`. `cast-spell` carries optional `xValue`, `via?: CastVia` (`"flashback"|"escape"|"foretell"|"disturb"|"adventure"|"suspend"|"cascade"`), `face?`, `modes?`, `kicked?`, `overload?`, `free?` (a `CardDefinition.freeCastIf` permission), `convoke?: ConvokePayment[]` (the creatures that convoke, a token stack named once per token; what each `pays` is optional and worked out by the engine when omitted; convoke pays for `{X}` too, and `convokeProofFor(offer, x)` fits an offer's proved payment to the X a driver picked), `sacrifice?` (an additional cost), `tap?` (what an alternative cost's "tap N untapped …" taps — Sephara), `escapeExile?` (which other graveyard cards an escape cast exiles, from the offer's `escapeExile: {count, choices}`; omitted, the oldest); `cast-spell` and `play-land` carry `graveyardGrant?: {source, asType?}` — which graveyard permission a card played from a graveyard spends (a grantor permanent, or the card itself for a one-shot "you may cast that card this turn"; Muldrotha's per-type `asType`), one `LegalAction` variant per permission that applies; `activate-ability` carries optional `sacrifice`, `xValue`, `tap` (an `AbilityCost.tapOthers` choice). `LegalAction` mirrors this — a castable/activatable option carries whatever context the client needs to build the action (`xCost: {maxX}`, `targetCount: {min, max, copies?}` — the distinct-target counts (a token stack named in several slots counting once per slot, up to its size) a "for each target" cost (Hinata) is affordable at, which drivers fit their picks into with `fitTargetCount`/`fitCastTargets` —, `sacrifice: {choices}`, `tapCost: {count, choices, copies?}`, `castModal {...}`, `mustBlock`, etc.), and a card playable multiple ways (kicked/unkicked, multiple faces, via different alt-zones) is enumerated once per variant. Kept out of `game.ts` to avoid a cycle with `controller.ts`.
- **`view.ts`** — `viewFor(state, registry, viewer, opts)` / `game.viewFor(player)` → a `PlayerView`: your hand in full, other hands as counts, libraries as counts (except what a pending `choose-from-zone`/`scry` reveals to that player), battlefield/stack/graveyards public with **computed** characteristics baked in (power/toughness/keywords/types/subtypes/colors/restrictions/loyalty/`isToken`/`attachedTo`/`isCommander`/`xValue`/`copyOf`/`suspended`/`foretold`/`faceName`+`faces`/`stackCount`/`art`), so a client needs neither the registry nor the layer system. `subtypes` is the type line's: without `subtypes.ts`'s every-type markers. A foretold card in exile is redacted for everyone but its owner. **`state.revealedThisTurn` is the one path that puts a card in someone else's hidden zone into your view** — a reveal is to *all* players (rule 701.16), so those ids go into every seat's `objects`; a library is still never listed as a zone, so a revealed card's identity is public while its position stays hidden. `PlayerView` also carries `startingPlayer`, `dayNight`, `monarch`, `emblems`, and `decisionSource` (the `{object, cardName}` behind `awaiting`, or `null` — a decision variant's own `source` wins over `state.decisionSource`, and `cardName` stands alone because the object is often somewhere the deciding player can't see: an edict's sacrifice is asked *after* the edict resolved into a graveyard); `PublicPlayerInfo` carries `energy`, `counters`, `commanderCastCounts`, and `commanderDamageTaken` as a list of `CommanderDamage` (`commander` id, `name`, `owner`, `art`, `amount`) — named even when that commander isn't visible to the viewer. `COMMANDER_DAMAGE_LETHAL` (21) is exported alongside. `art` is where a deck's **chosen printing** surfaces: `DeckList.printings` (card name → Scryfall card id) is stored at setup on `PlayerState.printings` and substituted here for the card's *owner*'s objects, so every device at the table draws the card its owner brought. Player-level, not per-`GameObject`, because it's a fact about the physical cards someone owns rather than any game state — so it survives zone changes and control changes for free. Keyed by the card's **front face** (`def.faces[0]`), which is the name a decklist uses, so a transformed permanent keeps wearing it. `faceIsBack` rides alongside: a card id names the whole card and serves its front image, so a client has to ask Scryfall for `face=back`, and only the registry can tell a real second image from an adventure's spell half (same two-entry `faces` shape, one printing).
- **`turn.ts`** — `Phase`/`Step` string-literal unions (no `enum`), `TURN_SEQUENCE`, `nextStep`, `stepUsesPriority` (false only for untap/cleanup), `isMainPhase`.
- **`events.ts`** — a discriminated `GameEvent` union (the audit log) covering every state change the engine makes — zone moves, damage, triggers, decisions, alt-cast events, combat, replacements, etc. Both log formatters (`scripts/format.mjs`, `client/src/format.ts`) render them; check there when you need the exact shape of a specific event.
- **`cards.ts`** — a thin re-export barrel; the real content lives in `cards/`: `cards/define.ts` (`CardDefinition`/`CardDraft` + `defineCard`), `cards/helpers.ts` (`basicLand`, `manaTapAbility`, `addManaAbility`, land-toolkit builders — `entersTappedStatic`, `checkLandStatic`, `painLand`, `fetchLand`, `sacrificeFetchLand`, `shockLand`), `cards/registry.ts` (`CardRegistry`, `createDefaultRegistry`), one file per card under `cards/pool/` (real cards + basics) and `cards/tokens/`. `CardDefinition` is **declarative** (`effect`, `keywords`, `activated`, `triggered`, `static: StaticAbility[]`, `supertypes`, `loyalty`, `chapters` for a Saga, `faces` for a multi-face card, `transform`/`disturb`/`adventure`/`suspend`/`foretell`/`flashback`/`escape`/`cycling`/`castModal`/`kicker`/`overload`/`freeCastIf`/`convoke`/`selfCostReduction`/`additionalCost`/`cantBeCountered`/`art`) with an imperative `resolve(ctx)` hatch. `cards/generated.ts` is the codegen'd barrel (`npm run gen:cards -w engine`, also a `prebuild`/`pretypecheck` step, checked in) — **to add a card, drop a new file in `cards/pool/` and run `gen:cards`**. It emits `POOL_CARDS` and `TOKEN_CARDS` as well as the combined `BUILTIN_CARDS`, because the directory is the only record that a definition is a *token* — nothing on `CardDefinition` says so. `cards/classify.ts` reads them back as `isTokenCard` (rule 111.1 — a token isn't a card), `isCardFront` (rule 712.3 — a DFC is one card, deck-listed under its front face) and `isDeckableCard` for the two together; `deck-validation.ts`, `card-replacer.ts`, the library page and the deck builder's pool all filter on these rather than guessing from the name. `cards/pool.test.ts` fails if a card isn't wired into `generated.ts`, or if the pool/tokens split drifts. The same run writes the pool a second way, for the web client: 32 shard modules under `cards/shards/`, each card in the shard its name hashes to (`cards/card-shards.ts`: `cardShardOf`, and `loadCardShard`, whose literal `import()` per shard is what gives each shard its own file in a bundle), plus `cards/generated-index.ts`, what a page can know without loading any card: `TOKEN_NAMES` (what `isTokenCard` reads, so classifying a definition never imports every token) and `PINNED_ART` (a card's pinned printing, for drawing a commander from its name alone). The codegen reads each card's name and art from its source — `defineCard({ name, … })`, or a helper whose first argument is the name — and `pool.test.ts` checks both, and every card's shard, against the real definitions. The engine's `package.json` declares **`"sideEffects": false`**, which is what lets a bundler leave out every card module a page never reaches: each card file's `defineCard(…)` call would otherwise count as an import-time side effect, and the whole pool would ship with any page that touched the engine's barrel. It holds because no engine module does anything at import time but define things; keep it so. **`cards/AUTHORING.md` is the hand-authoring guide** — every field, the effect/target/ability/static vocab, worked examples, current limitations; read it before authoring a new card. `Game.debugSpawn(name, player, zone)` is the sanctioned white-box "put a card straight into a zone" helper, going through the real `moveObject`.
- **`cards/edhrec-rank.ts`** — `EDHREC_RANK` / `edhrecRankOf(name)`: how popular each pool card is in Commander (1 = most played). **Generated** by `npm run gen:edhrec-rank -w engine` from Scryfall's `edhrec_rank`, batched 75 names to a request, and checked in so nothing needs the network at runtime. A card absent from the table is *unranked* rather than unpopular — basics always are — and consumers sort those last. Two consumers: the library's `Popularity` sort, and the authoring backlog's ordering (`top-commander-cards.txt` is a frozen snapshot of the same data).
- **`identity.ts`** — `colorIdentityOf(def)` (rule 903.4 — a lexical `{…}`-symbol scan of the mana cost + all rules/ability text) + `withinIdentity`/`identityString`. Consumed by `deck-validation.ts`.
- **`deck-validation.ts`** — `validateCommanderDeck({commanders, cards, size}, registry)` → `{legal, violations, identity}`: singleton (basics exempt), colour identity, deck size, a commander that may command (`canCommandAlone`, rule 903.3: a legendary creature, Vehicle, or Spacecraft with P/T, or a card whose declarative `canBeCommander` says it can be your commander — a planeswalker without it can't), a legal pair for two commanders (`pairingProblem`/`canPairCommanders` over each card's declarative `pairing` — never its rules text — and also what the deck builder's commander toggle asks: two plain Partners, two "Partner with"s naming each other, two same-text "Partner—[text]"s, "Choose a Background" + a legendary Background enchantment, "Doctor's companion" + a lone Time Lord Doctor; a Background is a commander *only* as that second half, and `canCommandAlone`/`isBackground` are exported for callers that pick commanders), and "is actually a card" (`cards/classify.ts` — a token or a DFC back face is a registered definition and would otherwise pass every other check). Only checks *implemented* cards. Lives in the engine (it originated in `server/`) because it's pure synchronous logic over `CardRegistry` data — the client's deck builder needs the same rules with no network round-trip.
- **`sample-decks.ts`** — `SAMPLE_DECKS`: the five 2022 Starter Commander Decks, each a legal 100-card Commander deck. Each keeps its `printed` list verbatim plus a `substitutions` table (`{original, substitute, reason}`) swapping in hand-picked stand-ins for cards the engine doesn't implement yet; `cards` is the result. To revert a substitution once its card is authored, delete its entry — `test/sample-decks.test.ts` fails for any substitution whose original is now implemented, and checks legality. The record of every swap and why is `docs/plans/precon-decks.md`. One source of truth for two consumers: `server/src/decks.ts`'s `SEATS` (a seat's fallback deck — the first four, one per seat) and the client deck builder's "starter decks" (all five).
- **`card-replacer.ts`** — `suggestReplacements(target, context)` → up to three implemented `BUILTIN_CARDS` stand-ins for an unimplemented card, best first, each with a `confidence` (`high`/`medium`/`low`) and the `sharedTags` behind it. `assignReplacements` does it for a whole deck at once, and is what the import uses: the Hungarian algorithm over every missing card's candidates, so a stand-in two cards want goes to the one with the most to lose. Pure and synchronous. `target` is what Scryfall says about the missing card (name, mana cost, type line, power/toughness, keywords); `context` is the destination deck — `identity` (only cards inside it), `exclude` (never a card the deck already has, so singleton holds), `forCommander` (only legendary creatures/planeswalkers) — plus an optional `OracleTagIndex`. **Role matching runs on Scryfall Tagger oracle tags**: `createOracleTagIndex(data)` wraps the server's generated index, and similarity is an IDF-weighted cosine over the tags two cards share (a rare shared tag says more than a common one). A candidate must share a primary type with the target (instant/sorcery count as one) unless the tags say they do the same job; a land only replaces a land. Score = tags, then type, a steep mana-value closeness (so a finisher isn't replaced by a two-drop that shares a mechanic) and, for creatures, body (P/T and combat keywords). Without tags only the latter count and confidence is always `low`. The engine does no I/O; the index lives server-side. Design record and measured results: `docs/plans/card-replacer.md`. Also exports `parseTypeLine`.
- **`filter.ts`** — `CardFilter` + `matchesFilter(state, registry, id, filter, { you })`: a pure predicate over an object + its *computed* characteristics (`type`/`types`/`notTypes`/`subtype`/`subtypes`/`supertype`/`name`/`colors`/`notColors`/`colorless`/`manaValue`/`power`/`toughness`/`controlledBy`/`ownedBy`/`keyword`/`tapped`/`token`/`enteredThisTurn`/`attackedThisTurn`/`goaded`/`suspected`/`putIntoGraveyardFromLibraryThisTurn` — the last read off `GameObject.putIntoGraveyardFromLibraryOnTurn`, which `moveObject` sets on a library-to-graveyard move and clears on any other, ANDed). Off the battlefield it degrades to printed values — unless the caller asks for last-known information: `FilterContext.lastKnown` (a trigger filter matched as a permanent leaves — its `GameObject.lastKnown`, or `GameState.ceasedTokens` for a deleted token) or `FilterContext.snapshot` (a `LastKnownInfo` the caller picked out), and then every clause reads the snapshot through the same code path. `sharesCardTypeWith: "sacrificed"` is bound to a plain `typesAnyOf` by `bindDynamicCompares` and matches nothing unbound. Clauses about a card's own properties: `basePower`/`baseToughness` (after layer 7b — `Characteristics.basePower`), `hasManaAbility` and `hasAbilities` (`characteristics.ts`'s `hasManaAbility`/`hasAnyAbility`, granted abilities included), `xInManaCost`/`coloredManaSymbols` (the up face's own mana cost — a transformed back face has none), `cardTypeCount` and `nameDiffersFromEach` (an inner filter over the battlefield, rule 201.2c). Subtype clauses ask `subtypes.ts`'s `hasSubtype`, so a changeling matches every creature type, and `ofChosenType` reads the chosen creature type of the `FilterContext.source` (static scopes and trigger filters pass one). The shared "which objects" vocabulary for mass effects, tutors, and filtered triggers — `ZoneChoiceFilter` is an alias. A numeric clause's `n` may be a `DynamicOperand`: `{ own }` (the matched object's own power/toughness/mana value) or `{ amount: EffectAmount }`, answered by `FilterContext.amount` — `Game.filterAmounts` supplies it to target filters (via `TargetSource.amount`, rechecked on resolution) and trigger filters, and `applyEffectSpec` binds an effect's filters to plain numbers as that effect applies (`bindDynamicCompares`); with nothing to answer it, the comparison fails closed. Answers type/subtype/colour clauses lazily via `effectiveTypes`/`effectiveSubtypes` (layer 4 alone — `characteristics.ts`'s `layerFour`) and `effectiveColors`; only a `power`/`toughness`/`keyword` clause needs the full characteristics fold (kept cheap deliberately — a `StaticAbility.condition` re-runs `matchesFilter` over the whole battlefield on every read). `FilterContext.layered` is how a static's `filter` scope is matched from *inside* the fold computing its target: types/subtypes/keywords as folded so far, and a power/toughness clause fails closed. Also the shared **weighted** scan behind "other" and aggregates: `weightedMatches` weighs each permanent by its `stackCount` and drops one permanent per excluded id (so "other" beside a stacked source leaves the rest of the stack counted), and `AggregateSpec`/`aggregateOver` sum or max power/toughness/mana value over it — the `EffectAmount`, the `aggregate`/`source-greatest` `StaticCondition`s and the `CostReductionAmount` all read through it.
- **`goad.ts`** — `goadersOf`/`isGoaded`: every player who has goaded a creature (rule 701.15), whichever way — a one-shot goad (`GameObject.goadedBy`, until the goader's next turn), one for the rest of the game (`goadedForGameBy`), or a static one (`StaticAbility.goads` — Baeloth Barrityl, an Aura's "enchanted creature is goaded" — read live, its source's controller the goader). The attack checks, the `goaded` filter clause and last-known information (`LastKnownInfo.goaders`) all read through it, so a goad is never asked about half-way. Goaded is a designation, not an ability: nothing here is in the layer fold.
- **`subtypes.ts`** — subtype lists and their two markers, `EVERY_CREATURE_TYPE` (changeling, rule 702.73a) and `EVERY_LAND_TYPE`: one entry standing for every type of its kind, so a changeling's list is `["Shapeshifter", EVERY_CREATURE_TYPE]` rather than ~300 names in every snapshot, mana unit and type line. **Every subtype question goes through `hasSubtype(list, subtype)`, never `includes`** — filters, lords, amass, mana provenance. Asked *for* a marker it means "any type of that kind", which is how "shares a creature type with" a changeling works (Path of Ancestry). `withoutTypeMarkers` is what a type line shows (`viewFor` strips them; the changeling keyword icon says it instead). Changeling adds its marker as the first step of layer 4, in every zone (`characteristics.ts`'s `withChangeling`); an effect adds either marker as an ordinary `addSubtypes` entry.
- **`this-way.ts`** — `thisWayEntries(state, what, since?)`: what the resolution under way (`GameState.resolutionSince`) has discarded, drawn, milled, sacrificed, destroyed (a destroy effect, not a death), exiled, returned to a hand, put into a graveyard or put onto the battlefield from a zone, read off its own events — each object with whose it counts as, whether it left the battlefield doing so (so it's read as it last existed there) and how many tokens a stack that went whole stood for. - **`characteristics.ts`** — `computeCharacteristics(state, registry, id)` folds printed → layer 3 (text substitution) → layer 4 (type/subtype changes) → layer 5 (colour) → layer 6 (keyword grants/ability loss, and keyword counters — rule 122.1b, `KEYWORD_COUNTERS`) → layer 7b (a `setBasePtFromCount` CDA — a `CountSpec` counting a `CardFilter` over the battlefield or all graveyards, applied in every zone per rule 604.3 — then `animate`'s `setPt` and statics' `setBasePt`, by timestamp) → layer 7c (counters) → layer 7d (P/T grants/modifiers), timestamp-ordered. `Characteristics.restrictions`/`.protectionFrom` collect `StaticAbility.restrictions`/`.protection`. **Layer 4 is its own fold, `layerFour`**, because statics grant types to other permanents (`StaticAbility.addTypes`/`addSubtypes` — Kudo's Bears, Ragost's Foods, Bello's creatures): the object's own type-changing modifiers (ordered by `PtModifier.timestamp`) and every type-granting static on the battlefield, in timestamp order, each static's scope matched against the types folded so far plus everything the previous pass added, repeated until the set of statics that apply settles — dependency order (rule 613.8) for effects that only add types, so Kudo still reaches a land animated after it arrived; a dependency loop settles in timestamp order. `effectiveTypes`/`effectiveSubtypes` read it (so every filter, target check and scope sees granted types); with no type-granting static on the battlefield it is the old self-contained read of the object's own modifiers. A re-entrant fold for the same object (a grant's condition or attachment clause reading back into it) answers with its own types only (`layer4InProgress`, a third re-entrancy guard beside the condition and CDA ones), which is what keeps two grants whose scopes read each other's grants from looping. `LayerFour.applied` records which statics reached the object there, and **`staticReaches`** — what the fold and `Game`'s granted-ability lookups ask — sends a static with a layer-4 part to exactly those for its later layers (rule 613.6). `staticAffects` resolves an `AffectSpec` scope (`"self"`/`"creatures-you-control"`/`"all-creatures"`/`"lands-you-control"`/`"attached"`, lord `subtype` clauses, and `"filter"` — any `CardFilter`, from the source's controller's perspective), given a `TargetView` by callers partway through the fold. Changeling (rule 702.73a) is a CDA, so `withChangeling` adds `EVERY_CREATURE_TYPE` to a creature's subtypes before any other layer-4 step, in every zone, from its copiable values — kept through a loss of abilities (layer 6 comes later), replaced by a later `setSubtypes`. `Characteristics` also carries `basePower`/`baseToughness`, the P/T after layer 7b. `hasManaAbility` (rule 605.1 — activated by rule 605.1a's own test, `isManaAbilityByRule`, or triggered, `isTriggeredManaAbility`) and `hasAnyAbility` (rule 113 — `cards/define.ts`'s `printedHasAbility`, a table over every `CardDefinition` field, plus every kind of grant) read granted abilities through the memoized `abilityGrantSources`; a scope asking about the permanent it is granting to re-enters, which the `grantedAbilitiesInProgress` guard answers conservatively (printed abilities only), never cached. Dependency ordering between static effects is not implemented. **Also owns the scoped computed-value cache**: `withComputedCache(fn)` opens a region (one per `legalActions` call / SBA sweep / `detectTriggers` event / `viewFor` / bot feature scan) inside which characteristics, layer-4 results, the contributing- and type-granting-statics pre-scans and `Game.manaSources` memoize; `invalidateComputedCache()` must be called by any mutation reachable from inside a region (`emit` is the broad net; `moveObject` suspends the cache outright via `suspendComputedCache`), values computed during a condition evaluation, a CDA count or a layer-4 fold (each has a re-entrancy guard whose answers are conservative) are never cached, and `MTG_CACHE_CHECK=1` on the fuzzer turns every characteristics and layer-4 hit into a recompute-and-compare that throws on divergence. **Wrap new read-only hot paths in a region; never let a region span a mutation without an invalidate.**

- **`mana.ts`** — `Color`/`ManaType`/`ManaPool`/`ManaUnit`, `parseManaCost` (generic, `{X}`, `{C}` colorless, hybrid `{W/U}`, twobrid `{2/W}`, Phyrexian `{W/P}`, snow `{S}` folded into generic), `manaValue`, `poolTotal`, `poolCounts`. **A player's mana pool is a list of `ManaUnit`s, not a count per colour** (`poolCounts` rebuilds the count view for the player view and the payment planner): a unit carries where it came from — a `ManaRestriction` on what it may be spent on (rule 106.6b — Cavern of Souls), a `ManaSpendRider` that fires when it's spent (Path of Ancestry), `persists` for mana that survives the end of a step (Savage Ventmaw), `uncounterable` for "and that spell can't be countered", `from` for what made it (a `ManaOrigin` — the source's types, subtypes and supertypes as it made the mana, which a spell keeps as `GameObject.manaSpentFrom` and the `manaFrom` filter clause reads: "if mana from an artifact was spent to cast it") — and a count can carry none of it. The pool is empty almost all the time, since the engine auto-pays; it fills only when someone activates a mana ability by hand, which is exactly where an untagged pool would drop the restriction. The restriction is enforced twice on purpose: `planManaPayment` won't *tap* a source whose mana couldn't pay for the thing being paid for, and `spendFromPool` won't *spend* such a unit — and the latter spends restricted units first, because an unrestricted one can pay for anything later in the same cost.
- **`controller.ts`** — `PlayerController.act(view)` is the single entry point: when `view.state.awaiting` is set it must return that declaration, otherwise any legal priority action. `AutomaticController` always passes/keeps its hand. `ScriptedController` plays a queue plus assignable `*Fn` callbacks (what tests use). `RandomController` picks uniformly from `legalActions()` — the engine's fuzzer (see `random-demo.mjs`); it builds the six priority actions itself and gets every *decision* answer from that kind's `decisions/` module via `randomAnswerFor`, handing it a `RandomSource` (`random`/`pickIndex`/`pickTargets`). **The exact sequence of draws against that source is what makes a seed replay identically**, so changing the order or count of calls in one of those arms silently re-points every fuzzer seed. `HeuristicBotController` extends `AutomaticController` with a v1 "plays a sensible game, not a good one" policy (land first, else the highest-mana-value affordable spell, else a **non-mana** ability, else pass; attack with every eligible creature, each at the lowest-life defender *it* may legally attack that can't profitably block it (`defendersFor` — goad and "can't attack you" differ per creature — and `wouldDieAttacking`, a crude "can anyone there kill it" check; a creature every defender could eat stays home); block favourable trades and chump-block lethal), owning its own `CardRegistry` so it can read mana values and computed P/T. Mana abilities are never activated on their own (`isManaOnlyAbility`): casting auto-pays, so floating mana gains nothing, strands the source, and — once bot moves are paced out one at a time — shows up as a land flipping sideways for no reason between a spell being cast and that spell resolving. Already-attached Equipment is never re-equipped, and one ability of one permanent is activated at most `MAX_ACTIVATIONS_PER_TURN` (4) times a turn — without both, Lightning Greaves' Equip {0} kept a bot in one main phase forever. It's the base class of both searching bots (`bot/` below) and the fallback under them, so every decision their search doesn't improve on is still this — including, now, the opening hand: `mulligan`/`chooseBottomOfLibrary` are overridden here and delegate to `bot/mulligan.ts`. `engine/src/test/heuristic-bot.test.ts` runs bot-vs-bot games to completion as a second fuzz target.
- **`bot/`** — two searching bots. **v2** (`EvalBotController`) is what `Room.addBot` seats, design record `docs/plans/smarter-bots.md`; **v3** (`PlanBotController`) extends it and is built but *not* seated, having benched six points worse at four players. **v3** (`plan.ts`, `determinize.ts`) plans a whole *turn* rather than searching one priority window, scores a plan by sampling plausible completions of the hidden information (`determinize.ts` — v3 does **not** read opponents' hands, unlike v2) and rolling each forward several turns, and hill-climbs over plans by appending, swapping and dropping plays. Read `docs/plans/bot-v3-search.md` before changing how the bot picks actions; it records why one-ply had to go and which v2 decisions were measured wrong. One-ply search: enumerate the concrete actions available now (`candidates.ts`), play each against a throwaway `Game.fromSnapshot` copy (`simulate.ts`), score the result and take the best. `features.ts` computes one player's raw unweighted feature vector and `evaluate.ts` is `EvalWeights` plus a dot product over it — split apart so the weights can be **fitted** by logistic regression over harvested self-play positions rather than hand-picked. Combat is built one attacker/defender pair at a time and never enumerated (`combat-math.ts`, `eval-bot.ts`); `decisions.ts` searches the decisions the engine raises mid-resolution. `scenarios.ts` is the opponent-independent gate (hand-built positions with a known right answer, parameterised by a weight vector) and `champions/` holds the frozen gauntlet opponents, each spelling out its whole `EvalWeights` literally so it can't drift when the defaults change. `bot/mulligan.ts` is the opening-hand policy all three share (hooked onto v1, since a mulligan has no board to roll forward): a hand is scored on mana sources plus its cheapest few castable spells, ramp counting for both, and the bar it has to clear *falls* as the hand it would keep gets smaller — with a free Commander mulligan raising it instead, and a floor at four cards. `EvalBotOptions.timeBudgetMs` is a wall-clock ceiling on one decision, **off by default** because a clock breaks the engine's same-seed-replays-identically guarantee that tests, the fuzzer and the tuner all rely on; only `Room.addBot` turns it on. When it expires the search plays the best candidate found so far, and `pass` plus v1's own pick are scored first precisely so that an expired search degrades to v1-quality play rather than to whatever `legalActions` happened to enumerate first.
- **`mana-payment.ts`** — the mana solver, lifted out of `game.ts`: `planPayment` (the entry point `Game.payMana` wraps) = `resolveHybridCost` (hybrid/twobrid/Phyrexian pips → a concrete cost + the life they owe) → `planManaPayment` (a greedy solver: floating mana first, then coloured pips, then `{C}`, then generic, tapping a fresh source only when the already-tapped ones can't cover it). A generic cost reduction that outran the generic part rides on `ManaCost.twobridReduction` (`mana.ts`'s `reduceManaCost`, which `castingCostOf` applies) and comes off only the twobrid pips `resolveHybridCost` ends up paying generically — the Spectral Procession ruling. Also `ManaOption`/`ManaSource`/`ManaPlanStep`/`ManaPayment`/`ManaPurpose` and the `standaloneManaChoices`/`manaCombinations` enumerators `Game.manaSources` builds options with. **Everything here is pure** — it returns a *plan* and never applies one, so `Game` stays the only writer of `GameState` (`useManaSource`/`executePayment` are still methods). What the planner may read is declared by `ManaPlanningView` (pool, life, sources, and a `canPay` closure for rule 106.6b) rather than being whatever `this` exposed; `Game.manaPlanningView` builds it, which also resolves `manaSources` once per payment instead of once per hybrid-pip trial.
- **`decisions/`** — one module per `AwaitingDecision` kind (18), each owning that kind's *answer* half: its `LegalAction` projection, its `whyCannot` validator, its `ask` (one arm of `controller.ts`'s `answerAwaited`), its bot `candidates`, its `randomAnswer` (the fuzzer's arm, reached via `randomAnswerFor` — `RandomController` keeps only the six priority arms), and the per-kind predicates `hasSource`/`mayAct`/`autoAnswer`. `contract.ts` holds `DecisionModule`, `DecisionReadCtx` (what a module may read), `DecisionHost` (`Game.dispatch`'s decision arms transposed — every one was already a one-line delegate, so **no `apply*` body moved**) and the two total `as const satisfies` tables `DECISION_ACTIONS`/`DECISION_OFFERS`. `registry.ts` is the table plus `decisionFor`/`decisionForAction`/`decisionForOffer`/`mayActOn`/`decisionHasSource`/`autoAnswerFor`/`randomAnswerFor`; `define.ts` holds `defineDecision` **in its own file on purpose** — the registry imports every module, so a module importing the registry back is a value cycle whose symptom is `TypeError` at module init, not a build failure. `shared/` holds `picks.ts` (the four checks a validator keeps rewriting), `subsets.ts`, `target-combos.ts`, `mulligan-math.ts`. **Nothing under `decisions/` may import `game.js`, and `state.ts` may not import from `decisions/`** (`choose-creature-type.ts` imports `printedCardName` as a value, so the reverse closes a real ESM cycle). To add a kind: write the module (including a `randomAnswer` — optional on the contract, but the fuzzer stalls without one, so `registry.test.ts` requires it), register it, add it to both tables, add a fixture to `test/decisions/registry.test.ts` — the compiler names every step you skip, but not the raise, which is still hand-placed (`pay-life-for-untapped` has no `begin*` at all; its raise is inlined in `moveObject`).
- **`combat/`** — the combat predicates as free functions over `(state, registry, …)`, so decision modules and the client's public seam can ask without holding a `Game`. `eligibility.ts`: `whyCannotAttack`, `whyCannotBlock`, `legalDefenders`, `creatureDef`, `attackRequirementsForbid` (rule 508.1d — the most attack requirements obeyed, per creature: a goad's "a player other than [the goader]", which a planeswalker doesn't satisfy, encore's "that opponent", an `attack-requirement` rule's; `mustAttack` is whether any can be), and **`defendersForAttacker`** — which defenders *this* attacker may be sent at, not the union, a distinction goad (701.15b) and Vow of Duty make load-bearing. `damage.ts`: `standardAssignment` (the one copy of the default split — kill as many blockers as possible, the ones needing least first and indestructible ones last, then trample the rest over or leave it on a blocker — shared by `Game`, every controller and the client's damage bar), `lethalFor`, `liveBlockersOf`, `needsDamageAssignmentChoice`, `damageAssignmentViolations` (rule 510.1c). `blocking.ts`: `blockingViolations` — the set-level rules (menace, Lure, "must be blocked if able" via `ifAblePlan`) that can only be judged once a whole declaration is known, checked **against the offer** rather than the board so the engine's validator and the client's Confirm button cannot disagree; `obeyingLure` is the fix-up every bot policy finishes its blocks with. `attacking.ts` is its attack-side twin: `attackingViolations` — a creature that must attack if able ("attacks each combat if able", goad, encore — the offer's `mustAttack`) left out of the declaration, which the validator refuses (rule 508.1d) and the client won't confirm — and `withRequiredAttackers`, which sends a left-out one at its first defender for a driver that doesn't choose (a bot, a test's scripted player, via the decision's `ask`). A static's `cantBeBlockedBy`/`canBlockOnly`/`cantAttackController` are read in `whyCannotBlock`/`whyCannotAttack` rather than folded into characteristics, so their scopes may ask about power. `Game` keeps one-line delegates for its own callers.
- **`primitives.ts`** — branded `PlayerId`/`ObjectId`, seeded `Rng` (mulberry32), `shuffle`.
- **`auto-settle.ts`** — `isSettled(state)` / `autoSettle(game)`: cascades past every "dead" priority window in one go. `Room` uses `isSettled` as its per-hop predicate but deliberately never `autoSettle` — it has to stop at every bot action to publish a frame, and per-seat auto-pass/skip-mana-only are one-shot-per-call, neither of which survives a cascade. `autoSettle` itself is now only used by tests/scripts that want a game settled in one call.

Snapshot/restore: `game.snapshot()` → `cloneGameState(state)` (`state.ts` — a plain-tree deep copy, ~2× faster than `structuredClone`, which stays the reference in `test/clone-state.test.ts`; bot search clones a state per simulated candidate, so this is the "candidates per decision budget" path); `Game.fromSnapshot(snap, env)` rebuilds (re-supply `registry`/`controllers` via `env`). Determinism: same seed + same controllers ⇒ identical replay.

## Server architecture (`server/src/`)

The authoritative multiplayer host. One process can run many rooms; each room owns exactly one
real `Game` and pushes every connected seat its own `viewFor` after each settle. Transport-agnostic
at the `Room` level (a `Connection` is just "something we can push a `ServerMessage` to"), so it's
unit-testable without a real WebSocket — `ws-server.ts` is the only place that touches `ws` itself.

**Rooms have a host** (`host.ts`'s `HostRole`, shared by both stages and carried across promotion): whoever created the room. `create-room` carries a `hostToken` the creating tab keeps in `sessionStorage`, and a `join-room` presenting it binds that connection as host, seated or not. Only the host may `add-seat`/`remove-seat`/`add-bot`/`set-bot-deck`/`start-game`/`set-bot-speed` (`requireHost` in `ws-server.ts`); your own seat, deck and ready state stay yours. While the host is disconnected the role falls to the first connected human seat, and returns when they reconnect — computed on demand, so there's no hand-off state to go stale. With nobody eligible (no token, nobody seated — scripts and tests) no one is excluded. `room-joined`/`state` carry the recipient's `isHost` and the room's `botSpeed`, and `SeatStatus.isHost` marks the host's seat.

A room has **two lifecycle stages**, because a seat's deck isn't known until whoever claims it
connects (the deck builder sends it with `claim-seat`) and `Game.create` shuffles and deals
immediately for every seat: a `PendingRoom` (a code, seat claims, no `Game`) is **promoted** into a
real `Room` the moment every seat is claimed or bot-filled.

- **`room.ts`** — `Room` wraps one `Game` plus a `Seat` per `turnOrder` entry (`clientToken`, `connection`, `autoPassUntil`, `skipManaOnly`, `displayName`, `ackedSeq`/`acksFrames`). `claimSeat(player, clientToken, connection, displayName?)` binds a connection to a seat — a token mismatch is rejected even while offline, the same token reclaims it. `addBot(player)` fills an open seat with `RoomOptions.botController`, defaulting to `DEFAULT_BOT` — the v2 searching bot — under `BOT_DECISION_BUDGET_MS` (300ms) per priority window, set a shade under `BOT_MIN_THINK_MS` so the search finishes inside the pause the room is already taking for animations (rejecting a seat already claimed or botted). `BOT_PLAN_BUDGET_MS` is kept for whoever seats v3 next. `botController` exists so the pacing tests can pin v1 and stay about the frame machinery rather than about how well a bot plays; `seatStatuses()` reports `isBot`. `dispatch(connection, action)` forwards to `Game.dispatch` then calls `settle()`, which auto-passes dead priority windows / mana-only windows / whole turns per-seat, one stopping point at a time (built on `isSettled`, deliberately not `autoSettle` — see `auto-settle.ts`). **Bots live in `settle()`**, not in `Game`'s `config.controllers` (`nextBotDecider` is seat-by-seat across `awaiting.hands` for the parallel mulligan, otherwise the single `awaiting.player`), so a mixed bot/human table composes for free.
  **Frames and the animation gate.** Every push is a numbered **frame** (`publish()` bumps `seq` and calls `onUpdate`; the transport fans it out, and `seq` travels on the `state` message). A bot used to take its whole turn inside one `settle()` call, so clients only ever saw the board *after* all of it and played the arrival animations over an outcome already on screen — a land shown flying in was already tapped for the spell after it. Now `settle()` stops at each bot action: it publishes a frame, parks the move behind `holdForClients`, and releases it once every *acking* seat reports finishing that frame (`ack(connection, seq)`) and `BOT_MIN_THINK_MS` (350ms) has passed, with `FRAME_ACK_TIMEOUT_MS` (6s) as a backstop for a seat that has gone quiet — then pauses a further `BOT_LINGER_MS[botSpeed]` (the host's setting: fast 0 / normal 700ms / slow 1.6s) before the move, so a string of moves with little to animate still reads one at a time. Once that pause starts the ack timeout is cleared, so a slow client catching up late doesn't cut it short. A seat that has never acked never gates anything, so no client can deadlock a room; a disconnect re-checks the gate. A bot move nobody could watch is dispatched without a frame — a plain `pass-priority`, or any window where `isDeadForMana` says passing and tapping for mana are the only options. That isn't just tidiness: a beat spent on one of those lands *between* a spell being cast and that spell resolving, which is what made a creature seem to arrive long after its own play animation had finished. Whatever the move lets through is paced in the next frame. `RoomOptions.pacing: "immediate"` opts out of all of it (bots run to completion, one push at the end) and is what tests and scripts use; `RoomOptions.timers` swaps in a fake clock. `dispose()` drops a parked move's timers.
- **`pending-room.ts`** — `PendingRoom`: the same seat-claiming bookkeeping as `Room` (claim/reclaim semantics, `addBot`, `connectedSeats`, idle tracking) with no `Game`, no dispatch, no settle. `claimSeat(..., deck?)` stores the seat's deck, falling back to its positional starter deck from `decks.ts` so a bare room-code link still works. `isReady()` = every seat claimed or bot-filled; `toGameConfig()` assembles the `DeckList[]` and rolls the starting player (the "highroll") *at promotion time*, since turn order isn't settled before then. Deliberately a separate class, not a nullable-`game` variant of `Room`. **The table is also sized here, not at creation**: `addSeat()`/`removeSeat(player)` grow and shrink it between 2 and `SEATS.length`, which is what the seat board's add/remove controls drive. `addSeat` takes the first unused `SEATS` entry and re-sorts, so the seat array stays in printed seating order however the table was assembled — turn order comes straight off that array, and must not depend on the order seats were added. `removeSeat` refuses a seat a human has claimed (leaving is that player's own call) but lets the host remove an open or bot-filled one.
- **`room-manager.ts`** — `RoomManager.createPending(players, config)` mints a room code and a `PendingRoom`; `promote(id)` builds the real `Game`/`Room` for a ready one (wiring its `onUpdate` to the manager's own `onRoomUpdate`), replays its connected claims and bot fills onto it, then `room.start()` settles it to the first real decision and publishes the opening frame. `get(id)` returns a `Room | PendingRoom`. `reapIdle(maxIdleMs)` disposes and drops abandoned rooms. No player-count assumption.
- **`ws-server.ts`** — `attachRoomServer(wss, manager)` wires a `WebSocketServer` to a `RoomManager`: parses messages as `ClientMessage`s, dispatches to the matching `Room`/`PendingRoom`/`RoomManager` call, pushes `ServerMessage`s back. **`broadcast` is never called from a message handler** — a room publishes its own frames on its own clock now (one per bot action), so it's wired up as `manager.onRoomUpdate` and as `room.onUpdate` on any room `requireRoom` is handed, and anything wanting a push calls `room.publish()`. That second binding is what keeps the hand-built-`Room` `scratch.mjs` pattern working without a real `RoomManager`. `create-room` clamps `players` (2-4, default 2) — the client always takes the default now and sizes the table from the seat board instead, so that parameter is for scripts and tests. `add-bot` mirrors `claim-seat`'s error shape and also sends a direct `room-joined` refresh, since the caller may not hold a seat yet and so isn't in `connectedSeats()`; `add-seat`/`remove-seat` need the same follow-up for the same reason, and are pending-room-only (`requirePendingRoom`) because a promoted room's turn order is already dealt. `ack` is exempt from the per-IP rate limit (it's automatic traffic, one per frame shown, with no effect beyond releasing a bot).
- **the wire protocol** lives in the `protocol/` workspace, not here — `server` and `client` both `import type { … } from "protocol"`. It was two hand-synced copies (`server/src/protocol.ts` and `client/src/net/protocol.ts`) until it became clear the reason given for that — Node package vs browser bundle — never applied to a file that compiles to nothing. `protocol/src/room.ts` holds the room protocol; `protocol/src/import-deck.ts` holds the `POST /import-deck` shapes, a separate surface (stateless, no room) that was mirrored just as silently. `ClientMessage`: `create-room {seed?, players?, hostToken?}`, `join-room {roomId, hostToken?}`, `claim-seat {seat, clientToken, displayName?, deck?}`, `add-bot {seat}`, `set-bot-deck {seat, deck}`, `add-seat`, `remove-seat {seat}`, `set-ready {ready}`, `start-game`, `set-bot-speed {speed}`, `dispatch {action}`, `pass-turn`, `auto-pass`, `toggle-mana-skip`, `resolve-all` (a **one-shot**, unlike the three standing modes beside it: pass this seat's priority until the stack drains, stopping the moment anything real happens — a decision for this seat, an opponent casting or activating, or something this seat owns being targeted or leaving the battlefield), `ack {seq}`. `ServerMessage`: `room-created`, `room-joined {seats, isHost, botSpeed}`, `state {seq, seat, view, actions, seats, autoPassing, autoPassPaused, skipManaOnly, isHost, botSpeed}`, `error`. A `WireDeck` carries `cards`/`commanders`/`name`/`printings` — one commander or a Partner pair, with the lone `commander` a client from before pairs sends still read (`engine`'s `commandersOf`). `SeatStatus` carries `claimed`/`online`/`displayName`/`isBot`, and its `deck` carries `commanders` as `{name, printing}` — just those cards, since the seat board only draws the commanders (a pair splits the art box in two); the whole map rides with the deck itself. Doesn't cover `/import-deck` (a plain HTTP route, not a WS message).
- **`decks.ts`** — `SEATS: SeatDeck[]`, up to four named seats (`ALICE`/`BOB`/`CAROL`/`DAVE`) in seating order, sliced by `create-room`'s `players` count — a seat's fallback deck when nobody brought their own. The deck contents come from `engine`'s `SAMPLE_DECKS`.
- **`import-deck.ts`** — the decklist-import backend, unrelated to any room: `parseDecklistText(text)` parses a pasted Moxfield-style export, honouring a `Commander` section header and keeping each line's `(SET) collector-number` suffix as a `printing`; `evaluateDecklist(entries, registry, onProgress?, {commanders, tags})` cross-references each name against the local `CardRegistry` (implemented cards reported from their `CardDefinition`), falls back to Scryfall for anything else (throttled, 429-aware retry), and gives each unimplemented card `replacements` (up to three, via `engine`'s `assignReplacements`) plus `suggestedReplacement` (the first). Stand-ins are chosen *for this deck*: the commander first (a legendary for a legendary), inside the commander's colour identity — read from Scryfall's `color_identity` when the commander itself is unimplemented — and never a card the list already has or another card's first choice. `lookupPrintingIds` resolves those suffixes to Scryfall card ids (`printingId`) so an imported deck arrives wearing the art it was exported with — batched by `{set, collector_number}` identifiers, which match back exactly, and only for *implemented* cards, since a substituted one is a different card whose art the suffix says nothing about. A returned card whose name doesn't match the line's is discarded: a stale collector number resolves to some other card, and pinning its art here would be worse than no printing at all. `formatCheck(...)` runs `validateCommanderDeck` over the result, reporting the `commanders` it settled on — two when a `Commander` section names two, or when Moxfield's trailing block is a pair the registry can't rule out. Scryfall lookups go through `lookupScryfallMany`, which **batches**: `POST /cards/collection` takes 75 names at a time, so a 100-card list costs two round-trips rather than a hundred throttled ones (~1s instead of ~35s). Responses carry no echo of which identifier produced which card, so they're matched back by name — each returned card is indexed under its own name, its `"Front // Back"` name rewritten in the single-slash form decklists use, and each face name. A name that misses is retried once per alternate spelling (`scryfallNameVariants`), one extra batched round each. Results (misses included) are cached process-wide for the life of the process. Wired up as `POST /import-deck` in `index.ts`, which answers with **newline-delimited JSON, not one object**: `{type:"progress", done, total, name}` lines as `evaluateDecklist`'s `onProgress` fires (implemented cards land at once, then a line per lookup batch), then exactly one terminal `{type:"result", cards, format}` or `{type:"error"}` line. Streamed so the deck builder's import panel can render a progress bar off those lines rather than sit silent. Live-fetching a Moxfield URL server-side was tried and abandoned (403s) — pasted export text only.

- **`oracle-tags.ts`** — `loadOracleTagIndex()`: the card replacer's oracle-tag index, read once from `server/data/oracle-tags/index.json` (null if missing — imports then match on type, cost and body alone). That file is **generated** by `npm run gen:oracle-tags -w server` from `server/data/oracle-tags/allowlist.txt`, the curated list of ~260 tags describing what cards *do* (removal, sweeper, edict, tutor, ramp, draw engine, recursion, tokens, anthem, evasion, punisher, …) — trivia tags (card names, cycles, typal, errata) are left out on purpose, since they're rare and would dominate an IDF-weighted score. The generator uses only Scryfall's public API: one paged `oracletag:<slug> legal:commander` search per tag (a parent tag's search includes its children, so listing both broad and specific tags gives graded credit), after checking every slug against scryfall.com/docs/tagger-tags — search answers an unknown tag exactly like an empty one. A card's own tags aren't in Scryfall's API; Tagger's GraphQL has them, but it's undocumented and nothing here uses it. Slow (~2s per page, most of an hour), so it's a checked-in, occasionally-regenerated file.

- **`status.ts`** — the operator endpoint, for reading over SSH with `curl`: `GET /status` (an aligned text table of rooms, seats, turn, step and idle time), `/status.json`, `/healthz`. It runs as a **second HTTP server bound to 127.0.0.1** (`STATUS_PORT`, default 4010) rather than a route on the game port, and that is load-bearing rather than tidy: a room code is a join credential, port 4000 is published to the internet by the Cloudflare tunnel, and a loopback *check* on 4000 would be worthless anyway because `cloudflared` makes every public request arrive from 127.0.0.1. Don't add it to the tunnel's ingress list.

## Client architecture (`client/src/`)

A **networked** client: each device is one seat, connected over WebSocket to a `server` room. It
never owns a `Game` or runs a controller loop itself. 2-player rooms render a classic vertical
layout; 3-4 player rooms render a 2x2 quadrant grid, with you always bottom-left.

**Three pages, branched by path in `main.tsx`** before `<App/>` is chosen, so `useNetworkGame`'s
eager WebSocket never opens for the two network-free ones: `/library` → `LibraryPage`,
`/deck-builder` → `DeckBuilderPage`, everything else → `App` (the game itself). The two
network-free pages are `React.lazy` chunks, each fetched **together with the whole card pool**
and rendered once both are in; the game's own download holds no card definitions at all (see
`cards/cardData.ts` below).

- **`cards/cardData.ts`** — the client's only way to card definitions, which the engine ships as
  32 name-hashed shards, each its own file in the build (engine `cards/card-shards.ts`). A
  **lookup by name** — `peekCard` (sync: the definition, `null` for no such card, `undefined`
  while its shard isn't loaded), `loadCard`, `requestCards` and the `useCardData` hook (re-renders
  as each shard arrives) — fetches only the shard that name hashes to. That serves the game page's
  two extras: an event-log name's tooltip (fetched as the pointer reaches it) and a double-faced
  card's other face in `ZoneViewer`. Everything a game needs to be *played* comes in the server's
  views instead. The **whole pool** — `loadCardPool`, then `cardPool()` (`cards`, `tokens`,
  `byName`, and a `CardRegistry` for the engine's deck rules) — is what the library and the deck
  builder read, synchronously, since `main.tsx` has loaded it before they render. A commander's art
  in the lobby needs no definition at all: the engine's generated `PINNED_ART` holds the few
  printings the pool pins, and everything else resolves on Scryfall by name. A shard that fails
  to load (the network, or a deploy replacing the build while a tab is open) reads as not loaded
  and is asked for again next time; the lazy pages show `cards/PoolLoading.tsx`'s loading state
  and, on failure, a reload offer. `engine/client` doesn't export `BUILTIN_CARDS`,
  `POOL_CARDS`, `TOKEN_CARDS` or `createDefaultRegistry`, and must not start to: any of them puts
  the whole pool back into whichever chunk imported it.

- **`net/useNetworkGame.ts`** — owns the WebSocket connection and the current seat's latest `frame` (`{seq, view, actions}` — one server push, whole), with `view`/`actions` derived from it for bookkeeping that has to be current. Reconnects with exponential backoff; a previously-claimed seat (`clientToken` in `sessionStorage`, per-tab) is reclaimed automatically. `ConnectionStatus` is `connecting` → `no-room`/`room-not-found` → `choosing-seat` → `waiting-for-players` (my seat is claimed but the room is still a `PendingRoom` — other seats are open) → `playing`/`disconnected`. `opponents: readonly PlayerId[]` is every other seat in turn order starting right after your own, wrapping around. `createRoom()` (mints and stores this tab's host token), `isHost`/`botSpeed`/`setBotSpeed(speed)`, `claimSeat(seat, displayName?, deck?)`, `addBot(seat)`, `addSeat()`/`removeSeat(seat)`, `dispatch(action)`, `passTurn()`/`autoPass()`/`toggleManaSkip()`, `ackFrame(seq)`, `nameOf(id)`. `everConnected` distinguishes a first visit to a server that isn't up from a connection actually lost mid-game — both land on `disconnected` (a failed initial socket fires `onerror` then `onclose` without ever reaching `no-room`), and only the wording differs.
- **`net/`** — no `protocol.ts` of its own: the wire types come from the `protocol` workspace (`import type { ServerMessage } from "protocol"`), exactly as on the server.
- **`App.tsx`** — `App` picks a screen off `NetworkGame.status`: `LandingScreen` → `SeatPickerScreen` → `GameScreen`. `GameScreen` renders the topbar/history popup, seat banner, highroll banner, `<Table>`, plus the floating `<Stack>` overlay and `<AnimationLayer>` as siblings. **Everything it draws comes from `usePlayback`'s `shown` view, never `game.view`** — the two differ for as long as an animation is running, and mixing them is what put a card's arrival animation over a board that already had the card on it. `Table` (keyed on `shown.revision`, i.e. one remount per frame actually shown) classifies `actions` into a `mode` (mulligan → commander-replacement → pay-life-for-untapped → choose-copy → choose-enchant → legend-rule → choose-text → choose-modes → sacrifice → scry → assign-combat-damage → put-on-bottom → discard → attackers → blockers → choose-from-zone → choose-x → choose-sacrifice → targeting → priority) and builds the matching `Action` from click handlers. Each decision kind gets its own small UI (e.g. `commander-replacement` shows a move-to-command-zone prompt; `choose-modes` shows Yes/No, one-button-per-mode, or toggle+Confirm depending on shape; `choose-x`/`choose-sacrifice` run before targeting and thread through it). `renderPlayerPanel`/`renderHandAndControls` are shared between the 2-player and quadrant-grid layouts. **`setState` updaters must stay pure** — dispatch happens after `setTargeting`, not inside its updater. State that must *not* reset per frame lives in `GameScreen` and comes in as props — the peekable hand tray's raised flag, which as `Table`-local state slammed the hand shut every time you played a card. For the same reason, anything measured off the layout that changes what's drawn is measured in a `useLayoutEffect` or a callback ref (as the boards' tile width is), never a plain `useEffect`: a freshly mounted `Table` would paint one frame at the default first. The hand's card spacing did exactly that, and the hand jittered through the mulligan each time a bot decided.
- **`lobby/`** — the two screens before a game. **`LandingScreen`** (`landing.css`) is the front door: a hero, then "Start a game" and "Join a game" as two separated panels, then the library/deck-builder pages as footer cards. It is a real page, not `.overlay`/`.overlay-box` — reusing the same box the "Connecting…" dialog draws is why the app's first impression used to be a 368x277 modal on an empty scrim. It asks **no** player count: three "N players" buttons above the CTA left nothing tying the counts to the button under them (all four read as one menu), and the *selected count* was the only accent-coloured thing on the page, so a setting outranked the primary action. The count moved to `SeatBoard` — see below. The join field carries no `maxLength`: the browser applies that to pasted text, which would chop a pasted room *link* to five characters before `parseRoomCode` could read the code out of it; the cap lives in `normalizeCode` instead, and a complete five-character code submits itself. Behind it all, `client/public/menu-backdrop.webp` (a seamlessly-tiling 10x10 grid of the top 100 commanders) drifts diagonally: an outer element holds the angle and clips while an inner one, exactly one tile wider, slides exactly one tile — which lands on an identical repeat, so only a transform animates and no edge is ever dragged into view. Two things there are easy to get wrong and are commented in `landing.css`: the oversize has to add *half the opposite axis* rather than a flat percentage (a fixed 160% covers 16:9 and fails on a wide, short window), and the blur is baked into the image rather than applied as a CSS `filter` — blur strips exactly the high-frequency detail that costs bytes, which took the same 2048px export from 1278KB to 263KB. The shipped file is 1536x2128 at 152KB, from a 241MB 7680x10640 source: `magick src.png -background "#12171b" -alpha remove -alpha off -filter Lanczos -resize 1536x -gaussian-blur 0x3 -quality 72 menu-backdrop.webp`. **`SeatBoard`** (`lobby.css`) is the seat-picker/waiting room. Its table-shaping controls (seats, bots and their decks, bot speed, Start Game) render only for the host; everyone else sees a Host badge on the host's seat, the bot speed as text, and "Waiting for <host> to start". It owns table size via an "Add seat" tile on the end of the row plus a × on any seat nobody is sitting in (2-4, enforced server-side by `PendingRoom`). Its grid gap and the dialog's own side padding share one `--seat-gap` token declared on `.seat-board-box`, because the grid runs the full width of that box and two different numbers there read as an uneven row. A seat's deck starts as the deck builder's active one (`getActiveDeck()`) and can be swapped per seat in `DeckPickerModal`; `claimSeat`/`addBot`/`setBotDeck` send it as a `WireDeck`.
- **`deck-builder/`** — `DeckBuilderPage` (`/deck-builder`, no room server needed to browse/build): search the pool (`cardPool().cards` filtered by `isDeckableCard` — no tokens, no back faces; the result list pages at `POOL_PAGE_SIZE` 100, larger than the library's because a row here is text rather than an image), build a 100-card deck with a commander or a Partner pair (`SavedDeck.commanders` — a deck saved with the older single `commander` is migrated on read; starring a card pairs it with a commander it can partner with, and otherwise replaces them), and see live `validateCommanderDeck` legality — run in-browser from `engine` over `cardPool().registry`, no round-trip. **Right-clicking a card row** opens `CardContextMenu` (portalled to `<body>` and placed from JS, like the hover preview, since the lists are scroll boxes); its one unique item is "Change printing…", which opens `PrintingPicker` over Scryfall's `unique=prints` search (`printings.ts`, a direct browser call — one search for one card, unlike the import's hundred-name batch that needs the server). The choice is stored on `SavedDeck.printings` (card name → Scryfall card id) and travels `WireDeck.printings` → `DeckList.printings` → `viewFor`'s `art`. The server only accepts a bare card id there (`assertPrintingsAreSafe`): the value ends up as an `<img src>` in *every* seat's browser, and `resolveArtUrl` would otherwise take any absolute URL verbatim. Also hosts the **decklist import** panel, which POSTs pasted text to `/import-deck`, streams that endpoint's NDJSON progress lines into a live per-card progress bar, substitutes each unimplemented card's first suggested stand-in, and then opens `ReplacementReview` — a popup that walks the substitutions one at a time as real card faces (the original from Scryfall by name on the left, the up-to-three stand-ins on the right with a match-strength badge and the oracle tags each shares), where clicking a face (or 1-3, with ←/→ between cards) swaps it into the saved deck on the spot; a card the deck already holds is blocked. The report banner above the editor summarises the swaps and reopens the popup, and carries each kept card's `printingId` into the new deck's `printings` — so an imported list keeps the art it was exported with, without anyone opening the picker. `decks.ts` is per-browser persistence in `localStorage` (not `sessionStorage` — a deck should outlive the tab): a named `SavedDeck` list plus an `ActiveRef` pointing at either a saved deck or one of `engine`'s `SAMPLE_DECKS` directly, so a starter deck is playable without duplicating it first. Server-side deck save/share doesn't exist yet.
- **`library/`** — `LibraryPage` (`/library`): the public, read-only card gallery, shaped like a Scryfall search result — a sticky search/filter bar (text, type, colour, sort, a "Tokens" toggle) over a **paginated** responsive grid of whole printed card faces (`PAGE_SIZE` 60; `loading="lazy"` keeps images off the wire but does nothing about node count, which is what costs layout time as the pool grows into the thousands). Its rows are built once from `cardPool()`, the first time the page renders. One sort is **`Popularity`**, off `engine`'s generated `EDHREC_RANK` (which ships in the library's own chunk), with unranked cards (basics) last (`CardImage`, not `CardTile` — nothing here is a game object, so there's no live state to overlay), and a card's own page as an overlay rather than a side pane, so the grid keeps its scroll and filters. One entry per *card*, not per registered definition: a DFC's back face appears as its front's flip side (`isCardFront`), and tokens are excluded unless asked for. `?card=Name` deep links.
- **`ui/`** — `CardTile` (a card face *reassembled* out of DOM — title/cost, Scryfall art crop via `ui/art.ts`, type line, text box, P/T or loyalty badge; props for `highlight`/`selected`/`activatable`/`badge`/`order`/`stackCount`/`compact` — because it has to overlay live game state on it). `CardImage` is the other half of that pair: the whole printed face as one image, for anywhere there's no game state to show (the library gallery). It owns `ui/card-image.css` — one of the two stylesheets a component imports rather than a page, with `Symbols`' `ui/symbols.css` — and skips the art lookup entirely for a token with no pinned printing, since a token's name isn't one Scryfall has ever known. `ui/Symbols.tsx`+`symbols.ts`+`mana.ts` render `{…}` mana tokens as pips (art sliced from a spritesheet, CSS fallback for exotic symbols). A planeswalker loyalty cost opening a line (`[+1]:`, `[-4]:`, `[0]:`, or the bare `+1:` Oracle form) becomes the printed loyalty badge instead: the Mana font's up/down/zero shape with the number laid over it, nudged per shape into the shape's body. That covers every card text and the ability menu at once. A permanent's loyalty is `LoyaltyCounter`, the starting-loyalty shield, in place of a gold box. `ZoneViewer` (takes `ids` + a `resolve(id)` lookup so an unresolvable id renders face-down; optional `castable` prop for graveyard flashback/play-from-graveyard buttons; in `selection` mode — a forced choose-from-zone/scry/surveil decision — a "View board" button hides it via `collapsed`/`onCollapse`, still mounted so picks survive, and `Table`'s `decisionCollapsed` puts a "Show choices" button in the decision strip as the way back; `CreatureTypePicker` shares the same state). `MiniTile` (a battlefield permanent as art + a stat badge) **portals its hover popover to `document.body` and places it from JS** — below the tile, flipped above when near the bottom of the screen, clamped inside the viewport; it can't be a CSS-revealed absolutely-positioned child, since `.quadrant-body` is a scroll box (clips it) *and* a size container (so `position: fixed` wouldn't escape either). Its width is **per board**: `Table`'s `recomputeBoardMiniW` binary-searches the widest `--mini-w-fit` at which that board's rows still fit its quadrant's height, and the `.board` rule caps it at `--card-w-max`, so a sparse board's tiles grow into the room they have and a crowded one's shrink, to a 40px floor past which the board scrolls. It measures the rows' extent, never the board's own box — the board is stretched to the command/library rail's height, which is what used to pin every tile at the floor. A tile's keywords are drawn as the Mana font's Arena ability icons (`ui/abilityIcons.ts`, a `Record` over the engine's `Keyword` union so a new keyword without an icon fails the build). Only the font's woff2 is bundled, registered through `FontFace`, never the package's stylesheet, which drags in every font format. `mana-font` is pinned to an exact version because the glyphs are private-use code points copied from its CSS. `AbilityMenu` (a permanent's activated abilities, as a small menu beside the permanent — portalled and JS-placed for the same reasons `MiniTile`'s popover is, finding its anchor in the live DOM by the tile's `data-obj-id`, flipping to the tile's other side at a screen edge; it used to be a bar docked in the hand strip, a whole screen away from the tile it belonged to). `PhaseTrack`, `TurnBanner`, `PlayerPanel`, `Stack`, `EventLog`. `PlayerPanel`'s header carries the player's counters (poison, energy, experience) right after the name, and a `CommanderDamageChip` per commander that has dealt that player combat damage — the commander's art in a ring of its owner's seat colour plus the total, amber from 15 and red from 18 of 21 — in the header row rather than a row of its own, since a quadrant has no height to spare. `CommanderTile` is the command zone's compact commander: just its art and mana cost (tax included), with name and P/T left to the hover card. Clamped into a rail a few pips wide the name was rarely readable, and the two together overflowed the rail on a short screen and left no room for a second commander. Two Partners get a tile each, `paired` (a shorter art box and tighter spacing), stacked with a gap in `.command-stack` so they read as two cards. The rail is one card wide and height-capped: measured at a 583px-tall viewport, a Partner pair and the library still fit its 165px. In a quadrant the cost stays on one line with its pips shrinking to fit: wrapping put one pip per line and overflowed every rail at 768px. `AnimationLayer` draws the purely cosmetic overlays (a card zooming up when cast or played, an attacker lunging at what it damages, turn/phase banners, a revealed card held up briefly — deliberately not a dismissible modal, since the History log already keeps the permanent record and a tutor-heavy deck would otherwise make an opponent dismiss one every turn) off the cues `usePlayback` publishes — nothing here ever touches game state, and a missed or double-played animation is harmless.
- **`ui/art.ts`** — `resolveArtUrl(art, name, version?, opts?)`: a `CardDefinition.art` link (a bare card id, a Scryfall page/API link, or a direct `cards.scryfall.io` file, whose first path segment is the size and so gets re-pointed at the one asked for) or a by-name Scryfall fallback. `opts.backFace` appends `face=back`, which is the only way to address a DFC's second image when the reference is a card id — pass `VisibleObject.faceIsBack` for it. Names without a pinned printing resolve through a batched `/cards/collection` lookup (`queueArtLookup`), and that name → image-URL cache is **persisted to `localStorage`** (`mtg-engine:art-cache:v1`, 14-day expiry, capped at 4,000 entries) — so a repeat visit to the library renders the faces it has shown before from the browser's HTTP cache without re-asking Scryfall for every URL first. Blocked or full storage just means a cold start. **Every emitted URL is host-checked against `ALLOWED_ART_HOSTS`**, and anything else falls back to the by-name lookup: `art` is also where another player's chosen printing lands after crossing the wire, and this function is what turns a value into an `<img src>`, so an arbitrary host here would be a request from every viewer's browser to whoever picked it. `cssUrl(url)` wraps one for a `background-image` — **always use it there**: an unquoted `url()` token may not contain a quote character and `encodeURIComponent` leaves an apostrophe alone, so every card whose name has one ("Atraxa, Praetors' Voice") silently lost its art.
- **`game/board.ts`** — `computeBoardEntries(view, pid)`: pure layout logic turning one player's battlefield into `BoardEntry[]` (bucketed by type, Auras/Equipment nested as `attachments`, matching untapped/tapped land stacks collapsed).
- **`game/damageAssignment.ts`** — the `assign-combat-damage` bar's model, pure. `groupBlockers` folds the offer's blockers into rows of interchangeable ones (the same in everything the view shows bar summoning sickness, the same lethal, nothing attached), because a token stack blocks as one creature per token and one input each made a twenty-Goblin block taller than the quadrant under it. The rows scroll past a few, and the board takes clicks for the same choice (`clickMembers`: one more to lethal, else spare), each blocker badged with its damage. A click or a row's `+` that needs more than is free takes it from other blockers wherever that kills least: damage past lethal, then damage too little to kill, then the cheapest kills. The answer is still one amount per blocker in offer order, checked by the engine's `damageAssignmentViolations`. Indestructible blockers take lethal (trample needs it) but aren't drawn as dying.
- **`game/usePlayback.ts` + `game/animationBus.ts` + `game/animationSchedule.ts`** — the animation pipeline, Hearthstone-style: **one thing at a time, and nothing may act until it finishes**. `usePlayback(frame, bus, onShown)` queues the server's frames and plays them one at a time — each frame's animations run against the board *before* it (the previous frame's, still on screen), and only when they finish does the new board replace it. It reports `{view, actions, revision, busy}`; `busy` empties `Table`'s action list, and `onShown` (wired to `ackFrame`) is what lets the server hold its bots to the same rule. `scheduleEvents` gives each animate-worthy event its slot (`CARD_STEP_MS` 1800 / `HIT_STEP_MS` 720 / `DEATH_STEP_MS` 420 / `DRAW_STEP_MS` 520 / `TURN_STEP_MS` 1300 / `PHASE_STEP_MS` 700 — the same numbers `AnimationLayer`'s overlay timeouts and App.css's `animation-duration`s are written to, so nothing outlives its slot), with `MAX_FRAME_MS` (6s) as a backstop that *drops* animations rather than clustering them past the ceiling. **Only the animations in `PACED` (a card play, a combat hit, a permanent leaving) hold the game up**; a turn or phase banner is a caption that plays over whatever the board has moved on to, costing nothing — otherwise a land the bot played hangs in the air for the length of an "End Phase" banner before reaching the table. Banners a frame merely passed *through* are dropped too (only the phase it lands in is announced), and `MAX_QUEUED_BANNERS` (3) keeps the banner queue from narrating a turn that finished several turns ago. `AnimationBus` carries cues sideways to `AnimationLayer` (a sibling, since `Table` remounts per frame), and **each cue carries the view it belongs to** — that's what makes a played land draw as it looked when played, rather than as it looks after the bot tapped it. A played card flies out of its owner's `.quadrant-cell` and shrinks back toward it (`flyOrigin` measures the cell off the live DOM and hands the offset to the CSS as `--fly-x`/`--fly-y`), so which side of the table a play came from is readable at a glance. A permanent leaving the board fades out first (`runDeath`, on `permanent-left-battlefield`, whatever the destination) rather than blinking out of existence; a run of them in one frame goes together on one beat. An attacking creature is tapped, so its tile is drawn tilted — the lunge travels on the outer `data-obj-id` box while the inner face straightens up to full size at the moment of impact, instead of sliding across the board at 20 degrees. A `card-drawn` sends a small cardback out of that player's `data-library-of` pile and into their hand — the bottom edge of their cell for you, the top edge for a seat across the table (`drawFlight`) — staggered when several land at once and capped per frame, and unpaced like the banners. `MAX_QUEUED_FRAMES` (4) is the catch-up valve for a backgrounded tab whose timers have been throttled.
- **`format.ts`** — `describeEvent`/`describeTarget` (event log text), `playerLabel` (prefers a chosen display name, falls back to a capitalized seat id), `seatClassOf` (stable per-seat colour by turn-order position, not table position), `isDetailOnlyEvent` (the bookkeeping the history hides by default — priority going round, step boundaries, mana entering a pool and the lands tapping to fill it; it's roughly three quarters of the log by volume, so `EventLog` opens concise and offers "Detailed" as a toggle).
- A rejected `dispatch` surfaces as `NetworkGame.error` → a dismissable red banner.
- Styling is `App.css` for the game table (plus a small `.css` beside each standalone page: `lobby/` — two files, `landing.css` and `lobby.css` — `deck-builder/`, `library/`) — legible dark table, no UI library. `index.css` holds the palette tokens and the element-level baseline for `button` and for text `input`s; that input rule is written as `input:where(…)` so it weighs the same as a bare element selector and every per-page class rule still wins. Card art is the only network dependency. Out of scope: undo.

**Standing UI rules** (settled during the board redesign — see `client/BOARD_REDESIGN_PLAN.md`):

- **No fixed px.** Sizing is `clamp()`/`vw`/`vh`, derived from the shared `--card-w` token for anything card-sized — never a new hardcoded number.
- **`--card-w` is viewport-*width*-derived; cap it against height where height is the real constraint.** A card-shaped box inside a container whose height is a viewport fraction (the quadrants are roughly half of it) needs a height cap too, or it fits on a tall monitor and overflows a short one — the two scale independently, and `--card-w` sits at its 150px ceiling all the way down to a 1667px-wide viewport. `--card-w-max` is the ceiling and `--card-w` is what everything reads, so a height-constrained subtree narrows `--card-w` for itself against that ceiling (the command/library rail does exactly this: `.quadrant-body` is a `container-type: size` container and the rail caps at `32cqh`). That cap is set against the **commander slot alone**, because the library pile below it squashes to whatever is left rather than demanding a full card's height — stacking two full slots plus their labels needs about twice a card's height, which at 768px tall didn't fit at all (a 286px rail in a 269px quadrant, the library count clipped off every cell, and that overflow was what made the boards scroll). The rail also stretches to the quadrant's full height, so its seat-coloured divider runs down the whole board. Note that making `.quadrant-body` a size container also makes it the containing block for `position: fixed` descendants (`contain: layout`), which is why the board's hover popover has to leave the subtree entirely rather than just going fixed.
- **Mana symbols always go through `<Symbols text={…} />`**, which renders `{…}` tokens as sliced-artwork pips with a CSS fallback. Never hand-roll a coloured circle.
- **Columns that must be equal need `minmax(0, 1fr)`, not `1fr`.** A bare `1fr` is `minmax(auto, 1fr)`, so a track whose content has a wide minimum (a row of input-plus-button, a long unbreakable word, an image) takes more than its share and its neighbour takes less. On the landing page that silently gave the join panel 414px against the start panel's 387 while the footer nav below, having no such pressure, split evenly and lined up with neither. The same footgun is why the seat grid and the board rows are written with `minmax(0, 1fr)` too.
- **A child that names its own width inside a padded box will escape that padding.** `.seat-board` at `min(1180px, 90vw)` inside a `.seat-board-box` at `min(1180px, 94vw)` overran the box's content area on a wide screen and pushed the outer seat panels out through its side padding. Let the box own the width and the child fill it (`width: 100%`).
- **The client's only automated tests are a Playwright smoke suite** (`client/e2e/`, `npm run test:e2e -w client`): the landing page, a 2- and a 4-player dev room at 1366x768, and walking into combat. It catches a page that no longer loads or a flow that no longer reaches its decision, not a layout that got worse, so verify any UI change live in the browser, in *both* a 2-player and a 3-4 player room, since the layouts diverge — **and at a short viewport (~768px tall), not just whatever monitor you're on.** Several severe layout bugs (every battlefield tile crushed to its 40px floor, the command/library rail overflowing its quadrant, the hand fan hanging off the bottom of the screen) were invisible at 1440p and obvious at 768p.

## Commands

Run from the repo root unless noted. Workspace scripts: `npm run <script> -w engine` / `-w server` / `-w client`.

**Whole repo** (root scripts fan out with `--workspaces --if-present`):
- `npm run build` — builds `engine` (tsc), then `server` (tsc), then `client` (`tsc -b && vite build`)
- `npm test` — runs `engine` and `server` vitest, each once (the client's Playwright suite is separate: `npm run test:e2e -w client`)
- `npm run lint` — oxlint on `client`
- `npm run typecheck` — `tsc --noEmit` on `engine`, `tsc --noEmit` on `server`, `tsc -b` on `client`

**Engine** (`engine/`):
- `npm run token:art -w engine` (`-- --write` to patch) — finds a real Scryfall printing for every `cards/tokens/` entry. A token can't resolve art by name the way a card does: ours are named for the engine key ("3/3 Beast Token") and Scryfall names printings after the creature alone ("Beast"), so `CardImage` skips the lookup for a token with no `art` and draws a text panel — which made tokens render hit-or-miss. The link comes from Scryfall's `all_parts` (the "Tokens" list on a card page) reached through the pool's own `create-token` effects, then matched on P/T, colours and subtypes. Keywords **rank** rather than filter, because both directions occur: Wurmcoil Engine's two Wurms differ only by deathtouch vs lifelink, while Chandra, Acolyte of Flame's Elemental is a vanilla printing whose haste comes from the spell. A printing carrying *fewer* subtypes than the definition (Oracle errata the physical token predates — "Wurm" vs "Phyrexian Wurm") matches at a lower tier and is flagged for eyeballing.
- `npm run gen:edhrec-rank -w engine` — rebuilds `cards/edhrec-rank.ts` from Scryfall (checked in; rerun as the pool grows, or to refresh the ranking).
- `npm run card:lookup -w engine -- "Card Name"` — the card's authoritative mana cost/type line/Oracle text/rulings and the tokens it makes (`engine/scripts/scryfall-lookup.mjs`), read from the checked-in **Oracle snapshot** (`engine/data/oracle/cards.jsonl` — every Commander-legal card and token, one line each, rulings folded in), so it works offline and in cloud sessions; only a card the snapshot lacks goes to Scryfall. Run this before authoring a new card — see `cards/AUTHORING.md` §1.
- `npm run gen:oracle -w engine` — rebuilds that snapshot from Scryfall's bulk data (Oracle Cards + Rulings, downloaded whole into the git-ignored `engine/.cache/scryfall/`, ~40s); rerun when a set comes out.
- `npm run card:scaffold -w engine -- "Card Name" | --next N [--cards] | --auto-scan [--all]` — writes card files from the snapshot into `engine/src/cards/scaffold/`: the stat block, `text`, rulings, keywords, pairing and tokens, and then whatever `scripts/oracle-parse.mjs` reads of the rules text. It reads two tiers: an ability's structure (cost or trigger, targets, restrictions) and its effect, whenever a whole sentence matches a template. Each line it can't read is left as a `// TODO(scaffold):`. A card whose every line was read goes, finished, into `engine/src/cards/review/`. `--report` writes nothing and lists the unparsed lines that recur most. `npm run card:parse-check -w engine` compares every ability the parser claims to have read with the hand-authored pool, and `test/oracle-parse.test.ts` requires zero disagreements. **Neither folder is registered** — authoring (or checking, with `card:verify -- --dir review`) and then moving the file into `pool/` is what puts a card in the game. `pool.test.ts` fails on a `TODO(scaffold)` in `pool/` or `tokens/`. See `cards/AUTHORING.md` §1.
- `npm run card:verify -w engine` — diffs every `cards/pool/` card's mana cost/colors/types/subtypes/P-T/loyalty against real Scryfall data, batched (`engine/scripts/verify-cards.mjs`). Structural fields only, not ability text. See `cards/AUTHORING.md` §16. **Every card in `pool/` is a real Magic card** — the pool's 27 invented placeholders were replaced with real printings of the same mechanic (see `neededCards-features.md` "E2"), so a `NOT FOUND` from this script now means a made-up or misspelled card, not a known exception. `tokens/` is exempt (token names aren't unique on Scryfall).
- `npm run card:text -w engine` — the same script's `--text` mode: the **rules-text** audit. It splits each card's `text` and Scryfall's `oracle_text` into clauses (one per line, then per sentence), matches every clause of the real card to its closest clause in ours by a set-similarity score over normalised tokens (the card's own name, "this creature", punctuation and reminder text are all normalised away first), and reports what didn't match — `MISSING` for a clause the pool dropped, `EXTRA` for one it has that the real card doesn't; `--similar` also shows the loose matches. Two false-positive classes are suppressed: a bare keyword line already on `def.keywords` (the client renders those from the keyword list) and a typed dual land's `{T}: Add` (implicit in Scryfall's type line, rule 305.6). **`cards/AUTHORING.md` §0 ("faithful, or not at all") is the standard this measures against**: a card whose printed behaviour the engine can't run is not authored at all, so every `MISSING` line should be either a paraphrase of `text` or one of the pre-rule cards on §15's "Known exceptions" debt list — never a new omission. It is still not a hard gate, and it is **blind to a clause that is present but wrong** (Saw in Half's tokens were the wrong size inside a clause it scored as matching), so read the output rather than counting it. `--lines` is the older, narrower check that compares only the number of text lines (the client renders `text` verbatim, so a missing `\n` runs two abilities together).
- `npm run test -w engine` — vitest, single pass (CI mode); `-- path/to/file.test.ts` for one file, `-- -t "name"` for a name match
- `npm run test:watch -w engine` — vitest watch mode
- `npm run build -w engine` / `npm run typecheck -w engine`
- `npm run play:random -w engine` — `engine/scripts/random-demo.mjs`: N random-vs-random games (`-- --games 300`, `-- --log`, `-- --players 3|4`, `-- --progress` to announce each seed on stderr before playing it, `-- --seed 19` to replay exactly one seed, `-- --timeout 60` to set the per-game wall-clock limit in seconds, default 30). This is the engine fuzzer — if `legalActions` ever offers something `dispatch` refuses, or an unbounded loop/object-count blowup happens, it reports `FAILED seed N` and exits non-zero. **Each game runs in a worker thread (`random-game-worker.mjs`) that's killed if it overruns the limit**: a runaway loop *inside* one `tick()` never yields, so neither a timer in the same thread nor `Game.advance`'s tick budget (which only counts ticks that return) can stop it, and before this a single stuck game stalled the whole run silently. A failure no longer aborts the run — every failing seed is collected and listed at the end. **Every seed deals each seat its own 100-card Commander deck from the whole pool** (`engine/scripts/fuzz-decks.mjs`): a commander, then the next window of a fixed walk through the pool's spells and nonbasic lands (the commander chosen, from a random dozen, as the one whose identity fits most of that window), then basics. So a run of seeds sweeps the pool, and a new card is fuzzed with no edit anywhere. A seat only takes the window's cards inside its commander's identity, so at ~5,400 deckable cards 150 two-player seeds reach all but a few dozen, and CI's 38 games about three quarters (BACKLOG). `-- --with "Card Name"` (repeatable) puts a card in every seat's deck, and `-- --coverage` plays nothing and reports how much of the pool the seeds reach. A few cards that mean nothing alone bring a partner along (`PACKAGES`: Skullbriar brings Reanimate). These replaced four hand-kept lists that had grown to 150-500 cards each, where a game drew a given card one time in six and never ran out of library.
- **Bot measurement** (all in `engine/scripts/`, all `worker_threads` pools over `SAMPLE_DECKS`; see `docs/plans/smarter-bots.md`). Seeds come in blocks of `--players` games, one seating per block with the measured seat moving round the table, so deck strength and play/draw cancel (`bot-seating.mjs`, shared). `npm run bot:bench -w engine` — a weight vector's win rate against v1 (`-- --opponent <champion id>|mixed|gauntlet`, `-- --players 4`, `-- --weights JSON`, `-- --games N`). `bot:tune` — a (1+1)-ES over the weights, head-to-head against the incumbent with the gauntlet as a veto. `bot:harvest` then `bot:fit` — the **primary** way weights are set: harvest labelled positions from self-play, then fit them by logistic regression (the ES buys one accept/reject bit per 200 games; the same games hold ~150k labelled positions). `bot:scenarios` — the opponent-independent gate any candidate vector must pass, exits non-zero on a failure. **Diagnostics, which is where most of the real findings came from**: `bot:audit` prices a card by spawning it on a fixed board and printing the score change (`-- --rollout` adds what it's worth once the next turns are *played out*, and the gap between the two columns is the enablement a static score can't price); `bot:plan` prints a planned turn and where it ends up; `bot:rollout-cost` reports rollout cost and whether the candidate gap clears the sampling noise. Every one of these takes `--bot v2|v3` or `--champion <id>` where it makes sense.
- Each major feature has its own dedicated engine test file rather than a standalone demo script (commander, mulligans, legend rule, multiplayer, bounce, X-spells, sacrifice, hand disruption, fight/keywords, counterspell, flash/prowess, proliferate, combat-damage triggers, control-change, base-P/T CDA, clone, animate, text/color, replacements, modal, filters/scopes, tutors, static restrictions, ability costs, ward, cost modification, protection, and one file per "needed-cards" pass — dual-lands, graveyard-recursion, landfall-payloads, count-scaled, trigger-value, token-for-target, token-copy, sacrifice-cost, intervening-if, additional-costs, token-stacking, mdfc, transform, phase10-misc). Read the relevant one for a runnable example of how a mechanic works.

**To check a client change against a known board, use `npm run dev-rooms -w server`** (below) rather than playing up to the position. A git-ignored `scratch.mjs` at the repo root is still the scratch pad for one-off exploration (`node scratch.mjs` after building `engine`/`server`): build a `Game` (often spawning objects directly onto the battlefield), wrap it in a `Room`, and serve it over a raw `ws` `WebSocketServer` on port 4000 for a browser (or `claude-in-chrome`) to connect to at the client dev server's URL with `?room=<CODE>`. `dev-rooms` is that pattern made permanent.

**Server** (`server/`):
- `npm run test -w server` / `test:watch` / `build` / `typecheck`
- `npm run start -w server` — runs the built `dist/index.js`: a real room server on `ws://localhost:4000` (or `$PORT`)
- `npm run dev -w server` — `tsc --watch` + `node --watch dist/index.js` together
- `npm run dev-rooms -w server` — a room server (in place of the real one, on port 4000) preloaded with the board states in `server/scripts/dev-scenarios.mjs`. There is one room per entry, joined at `localhost:5173/?room=<CODE>`, with the first player as the human seat and scripted bots that attack, block and cast only as the scenario says, so the decision under test comes up on cue. Seeded with `TWOAA`/`TWOPW` (2-player combat, with and without a planeswalker), `FOURP` (4-player goad), `KWALL` (every keyword icon and every loyalty badge), `STACK` (token makers in hand to cast for real, since `debugSpawn` can't make a token), `LURES` (a Lure-enchanted attacker, for the block bar), and `SWARM`/`HORDE`/`HORDE4` (one trampler blocked by a crowd: sixteen mostly different creatures, and a twenty-token stack plus three others, at two players and from the four-player seat the decision panel covers). A loopback-only command port, `127.0.0.1:4099`, takes JSON `list`, `state`, `reset`, `spawn`, `move`, `life` and an `eval` escape hatch (`curl -s localhost:4099 -d '{"op":"state","room":"FOURP"}'`). Every change pushes to the room's browsers at once. `reset` rebuilds a room from its scenario and drops the connections, and each tab reconnects and reclaims its seat by itself. Build `engine` first.
- `npm run gen:oracle-tags -w server` — rebuilds `server/data/oracle-tags/index.json` from `allowlist.txt` via Scryfall's search API (most of an hour; run it in the background and watch its stderr)

**Client** (`client/`):
- `npm run dev -w client` — Vite dev server with HMR (build `engine`/`server` first); needs a room server reachable at `ws://<host>:4000` (override with `VITE_SERVER_URL`)
- `npm run build -w client` / `lint -w client` / `preview -w client`
- `npm run test:e2e -w client` — the Playwright smoke suite (`client/e2e/`, config `client/playwright.config.ts`, CI `.github/workflows/e2e.yml`). It starts `dev-rooms` and the Vite dev server itself, or reuses them if they're already up, and resets each dev room it uses through the command port. Build `engine`, `protocol` and `server` first. It runs one test at a time on purpose: a dev-rooms `reset` drops every open connection, not just that room's. `@playwright/test` is pinned to the version whose Chromium the cloud sessions' image ships; elsewhere run `npx playwright install chromium` once.
- To watch it run by hand: start a room server, then `npm run dev -w client` and open two tabs/devices to the same room code.

## Git workflow

- **Standing authorization to commit and push**: once a feature is working (build/lint/typecheck/tests clean, and — for anything UI-visible — checked live in the browser), commit it and push to `origin/main` without asking first each time. Split unrelated work into separate, logically-scoped commits the way the existing history does (see `git log`), rather than one giant commit. This still doesn't cover force-push, history rewrites, or pushing something you haven't actually verified — those still warrant asking.
- **CI** (`.github/workflows/ci.yml`) runs on every pull request and every push to `main`: `npm ci`, the full build, a check that the build left no generated file uncommitted (the engine's prebuild rewrites `cards/generated.ts`), typecheck, lint, both test suites, and a short 2- and 4-player fuzzer pass.
- **Cloud sessions** (Claude Code on the web) start from a bare clone with no `node_modules`, and push to a `claude/…` branch rather than `main`. `.claude/hooks/session-start.mjs`, registered as a SessionStart hook in `.claude/settings.json`, installs dependencies and builds engine, protocol and server before the session starts. It's Node rather than bash because a CRLF checkout breaks a shell script, and it does nothing outside a cloud session.

## Toolchain notes

- **Module systems differ**: `engine`/`server` are ESM + NodeNext, so their own relative imports need explicit `.js` extensions (e.g. `import { x } from "./foo.js"` even though the file is `foo.ts`). `client` is ESM + bundler mode.
- **Engine/server TS config is `erasableSyntaxOnly`** (same as the client): **no `enum`, no `namespace`, no constructor parameter properties**. Use string-literal unions + `as const satisfies` tables instead. Also `verbatimModuleSyntax` → split `import type { … }` from value imports. `strict` + `noUnusedLocals`/`noUnusedParameters`.
- **Client TS config** (`client/tsconfig.app.json`) is strict bundler-mode: `verbatimModuleSyntax`, `erasableSyntaxOnly`, `noUnusedLocals`/`noUnusedParameters`, `allowImportingTsExtensions` (relative imports include the `.tsx`/`.ts` extension). `noEmit` — Vite does the transform.
- **Engine/server tsconfig excludes `src/**/*.test.ts`** from the build; vitest type-checks tests itself.
- **`package-lock.json` is written by npm 11.** npm 10 drops the `libc` fields npm 11 records for platform-specific optional packages, so changing dependencies with npm 10 churns the lockfile. Where the installed npm is older (the cloud sessions' image has 10.9), use `npx npm@11 install …`.
- **Shared dev deps are hoisted to the root** `package.json` (`typescript`, `@types/node`). Don't re-add them to a workspace unless a version needs to diverge.
- **Lint** is oxlint, not ESLint. Config in `client/.oxlintrc.json` (`react`, `typescript`, `oxc` plugins; `react/rules-of-hooks` errors).
- Assets in `client/public/` are referenced by absolute path (e.g. `/favicon.svg`); assets imported from `src/` go through Vite.
- **`game.ts` reads as *binary* to git and grep.** It contains a literal NUL byte — the `"\0none"` sentinel at the `chosenCreatureType` fallback, written as a raw byte rather than the escape — so a plain `grep` over it reports "Binary file matches" and finds nothing. **Use `grep -a`** (the Grep tool hits this too). Don't remove the byte casually: with `core.autocrlf=true` and no `.gitattributes`, being binary is the only reason git stores that file verbatim, and making it text normalises CRLF→LF across all ~10,100 lines in one commit, taking `git blame` with it. See `docs/plans/decision-registry.md`.
- **Windows CRLF/LF drift**: editing an existing pure-LF source file on Windows can leave it with *mixed* line endings (untouched lines stay LF, lines the tool rewrites come out CRLF) — distinct from a file that's already consistently CRLF (harmless). Before committing, if `git diff --stat` on an edited file looks disproportionate to the actual edits, check directly (`git cat-file -p HEAD:<path> | grep -c $'\r'` vs total line count) rather than trusting the diff size. Fix with `sed -i 's/\r$//' <path>`, rebuild/retest, then fold the fix into the same commit via `git commit --amend` if nothing's been pushed yet.
