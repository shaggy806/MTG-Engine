# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

MTG-Engine is a Magic: The Gathering rules engine (`engine/`) with an authoritative multiplayer
room server (`server/`) and a React web client (`client/`) — a real networked 2-4 player game
(Commander-capable), not a local hot-seat demo. The repo is an **npm workspaces monorepo**
(`workspaces: ["engine", "server", "client"]` in the root `package.json`, in that order so
`engine` builds first, then `server`).

**`ROADMAP.md` is the plan of record.** It carried an 11-phase plan for growing the engine to
a "baseline cardpool" (enough coverage for ordinary Commander decks), a dependency spine, and
per-phase file-level notes. **All 11 phases are now done** (Phases 3/4/6/7/9/10 shipped core +
a deferred long tail); ROADMAP's *Where next* section lists candidate directions — the biggest
is a bulk card-authoring pass against a real precon. The "Wave 1/2/3" labels below are the
historical cadence — Waves 1–3 are done. Read ROADMAP's *Architecture constraints* section
before touching the engine, and update this file's engine header as new work lands.

- `engine/` — a TypeScript library package, ESM (`"type": "module"`), NodeNext resolution. Emits to `dist/` with declarations; `package.json` `exports`/`main`/`types` point there. No I/O, no UI — a pure state machine driven entirely through `dispatch`.
- `server/` — a Node + `ws` package: the authoritative multiplayer room host. Owns the one real `Game` instance per room, keyed by a room code; every connected device gets its own redacted `viewFor(seat)` pushed after each dispatch. Imports `engine` the same way `client` does.
- `client/` — a Vite + React 19 + TypeScript app: a **networked** client — each device is one seat, connected over WebSocket to a `server` room, never running a local `Game` or a controller loop itself. Imports `engine` (`"engine": "*"`, the workspace symlink) and consumes only its public seam — `Game`, `viewFor`, `legalActions`, `dispatch`, the `Action`/`LegalAction` types — indirectly, via the wire protocol `server` speaks. Needs `engine/dist/` built (`npm run build` does engine, then server, then client).

## Engine architecture (`engine/src/`)

Implemented — turn/step loop, casting + targeting + fizzle, LIFO stack, SBAs, full combat **with
first strike / double strike / trample / deathtouch / lifelink / menace**, activated abilities,
triggered abilities, the continuous-effects pipeline (layers 1 copy, 2 control, 3 text, 4 type-change, 5 colour, 6 keywords/ability-loss, 7 P/T), **tokens** (minted by
`create-token` effects, cease to exist once they leave the battlefield), **Auras & Equipment**
(attach on resolution / via an `attach` effect, a static `"attached"` scope, sorcery-speed-only
abilities, and an Aura fall-off SBA), **Commander** (cast from the command zone with an
escalating `{2}` tax, **commander replacement as the owner's choice** (rule 903.9a — when a
commander is put into a hidden zone the game pauses on a `commander-replacement` decision;
`AutomaticController` says "command zone"), commander combat damage tracked toward a 21-damage
loss, the legend rule keeping the oldest of two same-named legendary permanents a player
controls), **mulligans** (an opt-in London
mulligan — see `GameConfig.mulligans` — draw 7, shuffle back and redraw as many times as wanted,
then bottom one card per mulligan taken; **every player decides simultaneously, not in turn
order** — the `mulligan` `AwaitingDecision` carries `hands: Record<player, {taken, step}>` and
anyone still in it may act, rule 103.4), **2-4 players** (attackers choose any non-eliminated
opponent; `declare-blockers` asks each attacked defender in turn, one at a time; APNAP trigger
ordering rotates through every non-active player, not just "the one other player"), **every
decision as a dispatched action** (`declare-attackers` / `declare-blockers` / `order-blockers` /
`discard` / `choose-from-zone` / `mulligan` / `put-on-bottom` / `choose-targets` alongside the
priority actions — a triggered ability / a suspended spell picks targets via a dispatched
`choose-targets` decision, not a controller callback, since ROADMAP Phase 11 EG-1),
**`legalActions(player)`** enumerating what is playable right now with per-slot target options,
and **`viewFor(player)`** producing a redacted, self-contained snapshot for one seat.
**Wave 1 additions** — `return-to-hand` / `exile` / `mill` / `discard` (targeted) one-shot
effects, a `sequence` effect combinator (Blightning), **`{X}` in a spell's mana cost** (chosen
at cast time via `cast-spell.xValue`, folded into generic when paid, stored on the stack object
as `GameObject.xValue`, exposed to effects as `ResolutionContext.x` / `EffectAmount = number | "x"`),
**sacrifice as an activated-ability cost** (`AbilityCost.sacrifice: "self" | "creature-you-control"`),
and a spell resolving into a decision owed by a *non-active* player (Mind Rot on an opponent —
`passPriority` now routes priority to `awaiting.player`).
**Wave 2 additions** — the `fight` effect (`{a, b, oneSided?}`); `counter` effect + the
`spell` / `creature-spell` / `noncreature-spell` target specs (`legalTargets` now enumerates
the stack); `proliferate` effect (simplified: proliferates *everything* eligible, no "choose
any number"); the `indestructible` / `hexproof` / `flash` keywords (SBA skip / opponent-target
block / instant-speed casting respectively); the `cast-spell` `TriggerSpec` (prowess); and the
`deals-combat-damage-to-player` `TriggerSpec` with `PendingTrigger.autoTargets` (a saboteur's
first target slot is auto-filled with the player it hit — `damage-dealt` now carries `combat`).
**Wave 3 (in progress)** — **layer 2 control-change** (modeled by reassigning
`GameObject.controller`, *not* a computed characteristic): the `gain-control` effect (Act of
Treason — `controlEndsAtCleanup` reverts it in cleanup), `CardDefinition.controlEnchanted` (Mind
Control — a `recomputeControl` SBA pass keeps a control-Aura's host under the Aura controller,
latest timestamp wins; `moveObject` reverts to owner on any zone change); **layer 7b**
(`StaticAbility.setBasePtFromCount` — a `"self"` CDA sets base P/T from a live `CountSpec`,
before 7c/7d); and **layer 1 copy** (Clone — also modeled by a stored field, not a computed
characteristic: `GameObject.copyOf` + a `printedCardName(object)` selector every characteristic /
ability / face read resolves through; `CardDefinition.copyOnEnter` triggers a `choose-copy`
decision as the permanent enters; `moveObject` clears `copyOf` on any zone change, rule 707.2);
**layer 4 type-change** (man-lands — an `animate` effect pushes one `PtModifier` carrying
`addTypes`/`addSubtypes`/`setSubtypes` (layer 4), `setPt` (layer 7b, after a CDA), `setColors`
(layer 5), `loseAbilities` (layer 6), and `keywords` (layer 6);
`creatureDef` / the creature-death SBA / `sourceHasKeyword` / the view's `isCreature` now test
*computed* types, so an animated `Mishra's Factory` attacks / blocks / dies as a creature and
reverts when the "until end of turn" modifier expires — `planManaPayment` learned an `avoid` id
so a man-land doesn't tap itself to pay its own `{1}: becomes a creature` cost); **layer 3
text-change** (`PtModifier.textSubstitution {from, to}` rewrites a creature-type word in a
permanent's own subtypes *and* its lord clause — Artificial Evolution on Goblin Chieftain,
Goblin → Bear, makes it pump Bears; a `choose-text` decision picks the words; the view rewrites
the displayed text too); **layer 5 colour-change** (`PtModifier.setColors`/`addColors`,
`Characteristics.colors` / `VisibleObject.colors`, a `nonblack-creature` `TargetSpec` reading
computed colour — Doom Blade can't hit a black creature but can once it's Turn-to-Frogged
blue); and **layer 6 ability-loss** (`PtModifier.loseAbilities` — Turn to Frog: keywords
cleared, and `manaSources` / `whyCannotActivateAbility` / `detectTriggers` /
`collectStaticEffects` skip a permanent that lost its abilities; the view blanks its text).

**ROADMAP Phase 4** (done) — **mana-system depth**. **4a**: `parseManaCost` parses `{C}` into
`ManaCost.colorless` (paid with colorless mana specifically); `manaValue` counts it.

(Treasure). `planManaPayment` is a greedy solver returning `{ source, mana, sacrifice, pain }[]` —

`addManaAbility` / `painLand` / `fetchLand` / `entersTappedStatic` / `checkLandStatic`

- **`characteristics.ts`** — `computeCharacteristics(state, registry, id)` / `game.characteristics(id)` → `{ power, toughness, keywords: Set, types, subtypes, colors: Set, controller }`. Folds printed → **layer 3** (`effectiveSubtypes` — a `PtModifier.textSubstitution` rewrites a creature-type word) → **layer 4** (`setSubtypes` replaces / `addSubtypes` unions / `addTypes` unions) → **layer 5** (`effectiveColors` — `setColors` replaces / `addColors` unions) → layer 6 (keyword grants from `static` abilities + modifiers; a `loseAbilities` modifier zeroes the permanent's *own* printed keywords + statics, external anthems still apply) → **layer 7b** (a `"self"` static's `setBasePtFromCount` replaces base P/T with a live `countValue` — cards / creature-cards in all graveyards, lands you control — then an `animate` modifier's `setPt` *sets* base P/T, latest wins, still applies through `loseAbilities`) → layer 7c (counters) → layer 7d (P/T grants + modifiers), timestamp-ordered (`GameObject.timestamp`, from `state.timestampSeq`, set in `moveObject` on entering the battlefield). `Characteristics.restrictions` (`ReadonlySet<CombatRestriction>` — Phase 3b) and `.protectionFrom` (`{ colors, types }` — Phase 3) collect `StaticAbility.restrictions` / `.protection` from `collectStaticEffects` (external Pacifism + a permanent's own `"self"` Juggernaut / White Knight clause). `staticAffects` (exported — also drives `Game.grantedActivated`) resolves the `"attached"` scope as `source.attachedTo === target.id`, `"lands-you-control"` as a same-controller land check, matches a lord's `subtype` clause against the *target's* `effectiveSubtypes` after `substituteWord`-ing the *source's* own text change onto it, and skips a source with `hasLostAbilities`. Layer 1 (copy) is handled upstream of the layer fold: `const def = registry.get(printedCardName(object))` resolves a Clone to the copied card before any layer runs. `effectiveSubtypes` / `effectiveColors` / `hasLostAbilities` are exported and self-contained (no recursion into `computeCharacteristics`). `staticConditionMet(state, registry, source, condition)` (exported — Phase 11 EG-3) evaluates a `StaticAbility.condition` gate from `source`'s controller's perspective; every static-consuming site checks it *after* confirming the static reaches its target (so an unreachable static never runs its condition), and a module-level `conditionInProgress` set short-circuits a re-entrant call (two mutually-conditional permanents). **Full text-change beyond a creature-type word, and dependency ordering, are not implemented.**

The base classes implement `act` by delegating to `chooseDiscards` / `declareAttackers` / `declareBlockers` / `orderBlockers` / `assignCombatDamage` (EG-4a — one amount per blocker; base classes return `standardDamageAssignment`) / `chooseFromZone` / `mulligan` / `chooseBottomOfLibrary` / `commanderReplacement` / `chooseCopy` / `chooseText` / `chooseModes` / `chooseSacrifices` / `chooseScry` / `chooseTargets` (all reached via `answerAwaited` when `state.awaiting` is set — `chooseTargets` answers a `choose-targets` decision since ROADMAP Phase 11 EG-1; the engine no longer calls any controller method directly). `AutomaticController` passes, never attacks/blocks, and always keeps its opening hand (0 mulligans) — chosen specifically so adding mulligans didn't change any existing test's behavior. `ScriptedController` plays a `{action, when?}` queue plus assignable `*Fn` callbacks (what the tests use); `RandomController` picks uniformly from `legalActions()` — including a random `xValue` up to `xCost.maxX` (on a `cast-spell` *or* an `activate-ability` — Phase 11 EG-3), a random `sacrifice` from `sacrifice.choices`, a random `choose-copy` (90% copy something / 10% nothing), and a random `choose-text`, a random `choose-modes` (a random count in range, distinct indices), a random `sacrifice`, a random `scry` (each looked-at card 50/50), a random `choose-targets` (Phase 11 EG-1), a random legal `assign-combat-damage` (Phase 11 EG-4a), and (Phase 11 EG-4c) honouring `declare-blockers`'s `mustBlock` — and is the engine fuzzer (see `random-demo.mjs`). `toAction` (all three controllers) echoes a `LegalAction`'s `face` back onto the dispatched `play-land` / `cast-spell` (Phase 10a).
- **`primitives.ts`** — branded `PlayerId`/`ObjectId`, seeded `Rng` (mulberry32; `rng.seed` = stream position), `shuffle`.
- **`auto-settle.ts`** — `isSettled(state)` (game-over, an `awaiting` declaration, or someone holding priority) / `autoSettle(game)`: cascades `advanceUntil(isSettled)` past every "dead" priority window (the holder's only legal action is `pass-priority`) in one go. `autoSettle` is what `RoomManager.create` calls once, right after `Game.create`, to settle a fresh room to its first real decision — `Room`'s own per-dispatch `settle()` deliberately does *not* call it mid-game (see `room.ts`): its loop advances `isSettled` one stopping point at a time instead, because auto-pass/skip-mana-only are per-seat, one-shot-per-call decisions that `autoSettle`'s uninterrupted cascade would blow straight past.

Snapshot/restore: `game.snapshot()` → `structuredClone(state)`; `Game.fromSnapshot(snap, env)` rebuilds (re-supply `registry`/`controllers` via `env`). Determinism: same seed + same controllers ⇒ identical replay.

## Server architecture (`server/src/`)

The authoritative multiplayer host. One process can run many rooms; each room owns exactly one
real `Game` and pushes every connected seat its own `viewFor` after each settle. Transport-agnostic
at the `Room` level (a `Connection` is just "something we can push a `ServerMessage` to"), so it's
unit-testable without a real WebSocket — `ws-server.ts` is the only place that touches `ws` itself.

- **`room.ts`** — `Room` wraps one `Game` plus a `Seat` per `turnOrder` entry (`clientToken`, `connection`, `autoPassUntil`, `skipManaOnly`, `displayName`). `claimSeat(player, clientToken, connection, displayName?)` binds a connection to a seat — a seat already claimed by a *different* token is rejected even while offline (so a dropped connection can't hand the seat to a stranger mid-reconnect; `ws-server.ts` follows a rejection with a fresh `room-joined`), the same token reclaims it; `displayName`, when given, is trimmed and capped at 20 characters and only overwrites what's already stored if it's non-empty (so a silent reconnect never blanks out a name chosen earlier). `dispatch(connection, action)` resolves which seat owns `connection` and forwards to `Game.dispatch`, then calls `settle()`. `settle()` (built on the engine's `isSettled` primitive, one stopping point at a time — deliberately *not* `autoSettle`, see `auto-settle.ts`) auto-passes a seat's own dead priority windows, windows where tapping for mana is the only option (if that seat opted into `skipManaOnly`), or an entire turn/until-my-turn stretch (if `requestPassTurn`/`requestAutoPass` armed it) — one settle-step per call, so a just-reached stopping point is never skipped over. `seatStatuses()` → `SeatStatus[]` for the wire.
- **`room-manager.ts`** — `RoomManager.create(config: GameConfig)` mints a room code, builds a `Game.create(config)`, and calls the engine's `autoSettle(game)` once to settle it to its first real decision (game over the instant it's created otherwise isn't possible, but with `mulligans: true` this correctly stops right at the first mulligan prompt rather than resolving it). `get(id)` looks a room up. No player-count assumption — it just forwards whatever `decks` array it's given.
- **`ws-server.ts`** — `attachRoomServer(wss, manager)` wires a `WebSocketServer` to a `RoomManager`: parses each connection's messages as `ClientMessage`s, dispatches to the matching `Room`/`RoomManager` call, and pushes `ServerMessage`s back (a `state` broadcast to every connected seat after `claim-seat`/`dispatch`/`pass-turn`/`auto-pass`/`toggle-mana-skip`). `create-room` clamps an optional `players` (2-4, default 2), slices `decks.ts`'s `SEATS` array to that many decks, and rolls a random `startingPlayer` among them (the "highroll") — independent of the shuffle `seed`, so it doesn't shift the deterministic draw order tests/replays rely on.
- **`protocol.ts`** — the wire protocol, duplicated (not imported) in `client/src/net/protocol.ts` since they're independent workspaces — keep the two in sync by hand. `ClientMessage`: `create-room {seed?, players?}`, `join-room`, `claim-seat {seat, clientToken, displayName?}`, `dispatch {action}`, `pass-turn`, `auto-pass`, `toggle-mana-skip`. `ServerMessage`: `room-created`, `room-joined {seats}`, `state {seat, view, actions, seats, autoPassing, skipManaOnly}`, `error`. `SeatStatus` carries `{player, claimed, online, displayName}`. Doesn't cover `/import-deck` (see `import-deck.ts` below) — that's a plain HTTP route, not a room-based WS message.
- **`decks.ts`** — `SEATS: SeatDeck[]`, up to four named seats (`ALICE`/`BOB`/`CAROL`/`DAVE`) in seating order, sliced by `create-room`'s `players` count. Each is a ~60-card **deliberately-illegal "good stuff" pile** (colour identity ignored; Command Tower / rocks / Evolving Wilds keep the splashes castable) that shows off a broad slice of the pool — alt-cast zones, cascade / storm, extra turns, planeswalkers, replacements, tutors, board wipes, man-lands. Commanders: Alice `Ureni of the Unwritten`, Bob `Ashmark, Mardu Vanguard`, Carol `Sarova, the Undying Current`, Dave `Seraphine, Dawnherald`. `COMMANDERS`/`DECKS` re-derive Alice's/Bob's entries by name for tests. Not run through `validateCommanderDeck` — the sparse test decks in `room.test.ts` cover the pass-turn/auto-pass behaviour that a shuffle-dependent castable hand would otherwise perturb.
- **`deck-validation.ts`** (ROADMAP Phase 9) — `validateCommanderDeck({ commanders, cards, size }, registry)` → `{ legal, violations, identity }`: singleton (basics exempt), colour identity within the commander(s)' (`engine`'s `colorIdentityOf` / `withinIdentity`), deck size, "each named commander is a legendary creature/planeswalker", "two commanders require Partner". Only checks *implemented* cards (feasibility is `import-deck.ts`'s job). `import-deck.ts`'s `formatCheck` guesses the commander as the first legendary creature in a pasted list and runs it; `index.ts` folds the result into the `/import-deck` response as `format`.
- **`import-deck.ts`** — a decklist feasibility audit, unrelated to any room: `parseDecklistText(text)` parses a pasted plain-text decklist export (Moxfield's "Export" feature — `"N Card Name"`, optionally with a `"(SET) collector-number"` printing suffix and a `*F*`/`*E*` foil/etched marker; split-card names are tolerated too), and `evaluateDecklist(entries, registry)` cross-references each unique name against the engine's `CardRegistry` by exact match — implemented cards are reported straight from their local `CardDefinition` (no network call), everything else is looked up on Scryfall (`lookupScryfall`, with a `" // "`/front-face-name fallback for split cards) for its real mana cost/type line/Oracle text so a human can review feasibility. This is the only thing automated — it never guesses whether an unimplemented card *could* be. Scryfall calls are throttled well under its 10 req/sec limit with 429-aware retry (a first, tighter throttle attempt actually tripped a real rate-limit block partway through an 89-card deck). Wired up in `index.ts` as a plain `POST /import-deck` HTTP route (not the WS protocol) — `index.ts` now builds an explicit `http.Server` shared between that route and the `WebSocketServer`, instead of the `WebSocketServer` making its own internal one via `{ port }`. Live-fetching a Moxfield URL server-side was tried and abandoned (403s in testing) — pasted export text only.

`server/scripts/smoke.mjs` (`npm run smoke -w server`) is the server's own eyeball check — spins up
a real room server in-process, has two WebSocket clients create a room, claim both seats, and trade
passes, printing every pushed `state` message — the same role `engine/scripts/play.mjs` plays for
the engine alone.

## Client architecture (`client/src/`)

A **networked** client: each device is one seat, connected over WebSocket to a `server` room. It
never owns a `Game` or runs a controller loop itself — the human's choice is sent as a `dispatch`
message, and the server pushes back the settled `state` for every connected seat. 2-player rooms
render a classic vertical layout (opponent row above your own); 3-4 player rooms render a 2x2
quadrant grid instead, with you always bottom-left.

- **`net/useNetworkGame.ts`** — owns the WebSocket connection and the current seat's `PlayerView`/`actions`/`seats`; never runs a local `Game`. Reconnects with exponential backoff, and a previously-claimed seat (its `clientToken` in `sessionStorage`, keyed by room id — per-tab on purpose, so two seats claimed from two tabs of the same browser don't stomp each other) is reclaimed automatically on load. A claim is only written to `sessionStorage` once the server *confirms* it with a `state` (`pendingClaimRef`), so a rejected claim never poisons the auto-reclaim; a rejected claim also drops any stored token for the room, and the server answers a rejection with the error **plus** a fresh `room-joined` so the picker's seat list can't get stuck showing a taken seat as open. `opponents: readonly PlayerId[]` is every other seat *in turn order starting right after your own, wrapping around* — not raw `turnOrder` array order minus you, which only coincidentally matches "next player after you" when you happen to be seated first — so a seating layout can rely on "next opponent, then the next" regardless of where you actually sit. `createRoom(seed?, players?)`, `claimSeat(seat, displayName?)`, `dispatch(action)`, `passTurn()`/`autoPass()`/`toggleManaSkip()` (server-side standing preferences, mirrored back in `autoPassing`/`skipManaOnly`), `nameOf(id)` (card names, from `view.objects`).
- **`net/protocol.ts`** — mirrors `server/src/protocol.ts` exactly (see there for the message shapes); duplicated by hand since `server` and `client` are independent workspaces. Also carries `ImportedCardReport`, which instead mirrors `server/src/import-deck.ts`'s `CardReportEntry` — the response shape of the plain HTTP `/import-deck` route, not part of the room protocol above.
- **`App.tsx`** — `App` picks a screen off `NetworkGame.status`: `LobbyScreen` (create — with a 2/3/4-player picker — or join by code; also an "Import a decklist" link, unrelated to rooms — see below) → `SeatPickerScreen` (an optional "Your name" field and a single Join button that claims the next open seat, no per-seat button; a blank name defaults to `"Player N"` — N from that seat's position — rather than silently falling back to the seat's own Alice/Bob/... label) → `GameScreen` once a seat's claimed and a view has arrived. `GameScreen` renders the topbar (title, a "History" button toggling a popup around `<EventLog>`, room code, Leave), the seat banner, a dismissible "🎲 X won the highroll and goes first" banner while `view.turn.number === 0`, `<Table>`, and — as siblings, not part of `Table`'s own layout — the floating stack overlay (`<Stack>`, mounted only while `view.zones.stack.length > 0`) and that History popup. `Table` is keyed on `game.revision` in the parent so every in-progress selection resets when the game state moves on. It classifies `actions` into maps (land/cast by card, abilities by source) and a `mode` (`mulligan` → `commander-replacement` → `pay-life-for-untapped` → `choose-copy` → `choose-text` → `choose-modes` → `sacrifice` → `scry` → `assign-combat-damage` (EG-4a — a per-blocker number input + a "→ defender" trample readout) → `put-on-bottom` → `discard` → `order-blockers` → `attackers` → `blockers` → `choose-from-zone` → `choose-x` → `choose-sacrifice` → `targeting` → `priority`); click handlers build the matching `Action`. `commander-replacement` shows a "<commander> would go to your <zone> — move it to the command zone instead? [Command zone] [Leave in <zone>]" prompt (903.9a, raised *before* the move). `pay-life-for-untapped` (a shock land) shows "<land> — pay N life to have it enter untapped? [Pay N life] [Enter tapped]". A hand card with `CardDefinition.cycling` gets a "Cycle {cost}" button (next to Suspend / Foretell). `choose-modes` shows Yes/No for an optional single mode ("you may"), one button per mode for "choose one", or toggle-then-Confirm for "choose N". `sacrifice` highlights the eligible permanents on the board (select `count`, Confirm); `scry` opens a `ZoneViewer` selection popup over the revealed top cards. `choose-x` (an X spell *or* an `{X}` activated ability — Phase 11 EG-3 — a number input 0..`xCost.maxX` in the controls bar; `pendingX` holds a `CastAction | AbilityAction`) and `choose-sacrifice` (a `"creature-you-control"` ability cost — one button per candidate; auto-resolves for a `"self"` cost or a single choice) run *before* target selection and thread `xValue` / `sacrifice` through the `Targeting` state into the dispatched action. A `choose-targets` decision (Phase 11 EG-1 — a triggered ability / a suspended spell) drives the *same* `targeting` flow, `activeTargeting` derived from the decision (only the running `ctPicks` are in state, so a state refresh mid-choice re-derives it) with no Cancel button. A targeted modal spell (Phase 11 EG-2) inserts a `choose-cast-modes` controls step (mode toggles — a mode with an un-fillable target slot is disabled — then Confirm) *before* the targeting flow; `confirmModes` threads the chosen `modes` into `Targeting` and the union of their target specs. A stack object (a spell being countered) isn't clickable on the board, so the `targeting` controls bar shows a "<name> (on the stack)" button per legal stack target. The discard control reads `view.awaiting.fromEffect` to say "Discard N cards" vs "Discard to hand size". `renderPlayerPanel(pid)` (works for opponents *and* your own seat — a commander's card tile it renders via `commandZoneTile` shows a "+N" tax badge once `commanderCastCount > 0`; also passes `wentFirst` for the persistent 🎲 badge) and `renderHandAndControls()` (the ability menu, `controls`, and your hand — including the mulligan/keep decision) are shared between the two layouts: `opponents.length === 1` (a 2-player game) keeps the classic pinned-top/board-rows/pinned-bottom structure; 2-3 opponents render a `.quadrant-grid` instead, with cells in a fixed `[opponents[0], opponents[1], seat, opponents[2]]` order (top-left, top-right, bottom-left-always-you, bottom-right — a 3-player game just leaves the last cell blank) and your hand/controls in a `.hand-strip` below the grid rather than inside your own cell. Either way, the whole page is one fixed-viewport-height flex column (not a scrolling document) — the banners and your hand-strip size to their own natural content and are always fully visible, while only the board area between them (`.table`) scrolls internally if there isn't room for everything (a card tile's height varies with its rules text, so no fixed pixel reservation could work reliably here). Opponent hands don't render on the board at all — `PlayerPanel`'s existing hand-count becomes a click target (`onOpenHand`, skipped for your own seat) opening the same `ZoneViewer` popup graveyard/exile browsing uses. Declaring an attacker against 2+ legal defenders (opponents *and* their planeswalkers) supports a redirect: selecting a creature defaults it to the first legal defender and focuses it (shown with a "?" marker); clicking a different opponent's panel — or a highlighted opponent planeswalker tile — while focused reassigns it. A loyalty ability is just an `activate-ability` action, so it flows through the existing ability menu / targeting. Targeting: click highlighted `targetOptions[slot]` (a `CardTile` or a `PlayerPanel`); multi-slot picks accumulate then dispatch. **`setState` updaters must stay pure** — dispatch happens after `setTargeting`, not inside its updater (React double-invokes updaters in dev). Attackers/blockers/discard/order-blockers/mulligan/choose-from-zone: select-then-confirm (order-blockers = click the blockers in damage order, or "keep default"). `ImportDeckScreen` (reached from the lobby, not gated behind `NetworkGame` at all) POSTs pasted decklist text directly to the server's `/import-deck` HTTP endpoint with a plain `fetch` — bypasses `useNetworkGame`/the WS protocol entirely, since it has nothing to do with a room — and renders each card's implemented/not-yet/not-found badge plus (for anything not implemented) its Oracle text via `Symbols`.
- **`ui/`** — `CardTile` renders a full card face: title bar (name + mana cost pips, plus a `+N` tax marker via the optional `extraGenericCost` prop), Scryfall `art_crop` image (via `ui/art.ts` — `obj.art` pins a specific printing, else a by-name lookup; colour-tinted fallback on load error), a type line, a text box (keywords in bold + rules text, minus text that only restates the keywords), and a P/T box (or, for a planeswalker, a gold loyalty badge — `obj.loyalty`) in the bottom-right corner like a real card. `ui/Symbols.tsx` + `ui/symbols.ts` + `ui/mana.ts` turn `{…}` tokens (in costs and rules text) into small pips — the WotC symbol artwork (`<img>` from `public/mana/<token>.svg`, sliced from `scripts/mana-spritesheet.svg` by `npm run slice-mana -w client`; covers generic 0–20, X/Y/Z, WUBRG, snow, the 10 hybrids, 5 twobrids, 5 Phyrexian, tap/untap; plus a hand-authored `C.svg` for `{C}` colorless, which the sheet lacks) with a CSS-pip fallback for anything still without art (exotic symbols) — also reused (outside any game) by `ImportDeckScreen` to render a looked-up card's mana cost/Oracle text. Props: `highlight` = must-pick, `selected`, `activatable` = dashed marker, `badge` = ⚔/🛡/Commander/etc., `order` = damage-order ordinal, `stackCount` = land-stack size badge (`×N`, only shown when > 1), `compact` = shrink via CSS `zoom` (an attached Aura/Equipment nested under its host, or a non-top stack entry). Tiles are 138×190 (min-height — taller for a long rules-text card); tapped ones rotate 90° + scale to stay in their slot. `ZoneViewer` takes `ids` + a `resolve(id)` lookup (not a pre-resolved card list) so an id `resolve` can't find renders as a face-down placeholder instead of being silently dropped — needed for an opponent's hand, only partially knowable. Its optional `castable { ids, label, onCast }` prop (Phase 6) puts a "Cast (flashback)" button on graveyard cards that have a `via: "flashback"` cast in `legalActions` — the browse popup for your own graveyard passes it, threading through the same `beginCast` / targeting path as a hand cast. Also `PhaseTrack`, `TurnBanner`, `PlayerPanel` (life/mana/zone counts; `targetable` for player targets; `wentFirst` for the highroll 🎲 badge; all three take an optional `seats` prop to resolve a player's chosen display name), `Stack` (the floating overlay described above), `EventLog` (compact `#seq — text` rows, auto-scroll, rendered inside the History popup).
- **`lab/`** — the **card lab**, a dev-only page (`npm run lab -w client` → `card-lab.html` on port 5174). `vite.lab.config.ts` aliases `engine` to its TS *source*, so editing a card file under `engine/src/cards/pool/` hot-reloads the lab (a *new* card file still needs `npm run gen:cards -w engine`); the main client/server keep consuming `engine/dist`. `CardLab.tsx` — searchable gallery of `BUILTIN_CARDS` + a detail pane with `Tile` (a faithful `CardTile` from `defToVisible`, plus a full-card-image toggle — where `art` overrides show), `Structure` (`cardFeatures.ts`'s feature chips + the pretty-printed def), and `Sandbox` tabs. `Sandbox.tsx` + `useSandbox.ts` drive `engine`'s `createSandbox` locally (mirrors the useful slice of `useNetworkGame`; `sandboxAdvance` clears the opponent's windows after each of your actions). Reuses `CardTile` / `Symbols` / `EventLog` / `art.ts`.
- **`ui/art.ts`** — `resolveArtUrl(art, name, version?)` turns a `CardDefinition.art` link (a Scryfall card-page / API / image URL, or a bare card UUID) into an image URL, falling back to the by-name Scryfall lookup when `art` is `null`. Used by `CardTile` and the lab.
- **`game/board.ts`** — pure layout logic, no React: `computeBoardEntries(view, pid)` turns one player's battlefield into the `BoardEntry[]` a board renders — permanents bucketed by `bucketOf` (single most-expansive type: an artifact creature buckets as creature), Auras/Equipment pulled out and nested as `attachments` on whatever they're `attachedTo`, and otherwise-identical untapped/tapped land stacks collapsed into one entry with `ids.length > 1`.
- **`format.ts`** — `describeEvent(event, nameOf)` / `describeTarget`, the TS sibling of `scripts/format.mjs`, for the event log. `playerLabel(id, seats?)` prefers a player's chosen `displayName` (looked up in the room's `SeatStatus[]`) and falls back to the seat id capitalized ("alice" → "Alice") when none is set or `seats` isn't passed. `seatClassOf` assigns one of four stable per-seat colors (`seat-a`..`seat-d`) by position in `turnOrder`, not table position, so a player reads as the same color on every device.
- A rejected `dispatch` (e.g. a lone blocker on a menace attacker) surfaces as `NetworkGame.error` → a dismissable red banner; the blockers UI also disables its confirm button while a menace attacker has exactly one blocker.
- Styling is one `App.css` — legible dark table, no UI library. Card art is the only network dependency (Scryfall, hotlink-friendly, browser-cached). Out of scope: animation, undo.

A git-ignored `scratch.mjs` at the repo root is a scratch pad for ad-hoc exploration (`node scratch.mjs` after `npm run build -w engine` and `-w server`) — the pattern used throughout this project's history for live client/server verification is a small script that builds a `Game` (often spawning objects directly onto the battlefield to bypass normal setup), wraps it in a `Room`, and serves it over a raw `ws` `WebSocketServer` on port 4000 for a browser (or the `claude-in-chrome` tools) to connect to at the client dev server's URL with `?room=<CODE>`.

**Server** (`server/`):
- `npm run test -w server` — vitest, single pass
- `npm run test:watch -w server` — vitest watch mode
- `npm run build -w server` — `tsc` → `server/dist/`
- `npm run typecheck -w server` — `tsc --noEmit`
- `npm run start -w server` — runs the built `dist/index.js`: a real room server on `ws://localhost:4000` (or `$PORT`), the same one the client's dev server talks to by default
- `npm run dev -w server` — `tsc --watch` + `node --watch dist/index.js` together, for iterating on the server itself
- `npm run smoke -w server` — `server/scripts/smoke.mjs`, an in-process two-client round-trip sanity check (see Server architecture above)

**Client** (`client/`):
- `npm run dev -w client` — Vite dev server with HMR (build `engine` and `server` first, or run `npm run build` from the root once); needs a room server reachable at `ws://<host>:4000` (override with `VITE_SERVER_URL`) to actually do anything
- `npm run lab -w client` — the **card lab** (`card-lab.html`, port 5174): a searchable card gallery + a solo in-browser sandbox, no room server needed. Aliases `engine` to source so card-file edits hot-reload (a new file still needs `gen:cards`). Build `engine` once first for types. See `client/src/lab/` and `engine/src/cards/AUTHORING.md`.
- `npm run build -w client` — type-check (`tsc -b`) then `vite build`
- `npm run lint -w client` — oxlint (currently clean, warnings included)
- `npm run preview -w client` — serve the production build
- No client tests yet. To watch it run: start a room server (`npm run start -w server`, or a `scratch.mjs`), then `npm run dev -w client` and open two browser tabs/devices to the same room code — there's no single-device hot-seat mode anymore.

## Git workflow

- **Standing authorization to commit and push**: once a feature is working (build/lint/typecheck/tests clean, and — for anything UI-visible — checked live in the browser), commit it and push to `origin/main` without asking first each time. Split unrelated work into separate, logically-scoped commits the way the existing history does (see `git log`), rather than one giant commit. This still doesn't cover force-push, history rewrites, or pushing something you haven't actually verified — those still warrant asking.

## Toolchain notes

- **Module systems differ**: `engine`/`server` are ESM + NodeNext, so their own relative imports need explicit `.js` extensions (e.g. `import { x } from "./foo.js"` even though the file is `foo.ts`). `client` is ESM + bundler mode.
- **Engine/server TS config is `erasableSyntaxOnly`** (same as the client): **no `enum`, no `namespace`, no constructor parameter properties**. Use string-literal unions + `as const satisfies` tables instead. Also `verbatimModuleSyntax` → split `import type { … }` from value imports. `strict` + `noUnusedLocals`/`noUnusedParameters`.
- **Client TS config** (`client/tsconfig.app.json`) is strict bundler-mode: `verbatimModuleSyntax`, `erasableSyntaxOnly`, `noUnusedLocals`/`noUnusedParameters`, `allowImportingTsExtensions` (so relative imports include the `.tsx`/`.ts` extension, e.g. `import App from './App.tsx'`). `noEmit` — Vite does the transform.
- **Engine/server tsconfig excludes `src/**/*.test.ts`** from the build (tests are not emitted to `dist/`); vitest type-checks tests itself.
- **Shared dev deps are hoisted to the root** `package.json` (`typescript`, `@types/node`). Don't re-add them to a workspace unless a version needs to diverge.
- **Lint** is oxlint, not ESLint. Config in `client/.oxlintrc.json` (`react`, `typescript`, `oxc` plugins; `react/rules-of-hooks` errors).
- Assets in `client/public/` are referenced by absolute path (e.g. `/favicon.svg`); assets imported from `src/` go through Vite (the app currently imports none — `src/assets/` was removed with the starter template).
- **The server drives the engine synchronously.** `Game.dispatch()` itself fully resolves (the stack, no-priority turn-based actions) before returning; `Room.dispatch()` calls it and then its own `settle()` on top. There is no async and no controller callback in the human path. Every player decision is a `dispatch`ed action a room forwards and a client renders — including targets for a triggered ability / a suspended spell, a `choose-targets` decision since ROADMAP Phase 11 EG-1 (the engine no longer calls any `PlayerController` method directly; the base controllers' `chooseTargets` etc. only run for test/fuzz seats).
- **Windows CRLF/LF drift**: editing an existing pure-LF source file on Windows can leave it with *mixed* line endings (untouched lines stay LF, lines the tool rewrites come out CRLF) — a real, observed issue on this machine, distinct from a file that's already consistently CRLF throughout (harmless). Before committing, if `git diff --stat` on an edited file looks disproportionate to the actual edits, check directly (`git cat-file -p HEAD:<path> | grep -c $'\r'` vs total line count) rather than trusting the diff size. Fix with `sed -i 's/\r$//' <path>`, rebuild/retest, then fold the fix into the same commit via `git commit --amend` if nothing's been pushed yet.
